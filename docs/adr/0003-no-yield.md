# ADR 0003: 裏の構築は CPU を譲る仕組みを持たない

- **Status**: 採用。ADR 0002 の Decision 5（負荷のあるときの動きは行 S4 で決める）への答え
- **Date**: 2026-11-12
- **Issue**: #421（行 S4）。設計は #414 と #422

## Context

行 C3a・C3b の計測で、1e9 点の索引の構築が 1〜3 分のあいだ平均 8.5 コアを使うと分かった。行 S4 は、構築が同じ機械のほかの処理に CPU を譲る仕組みを作る行だった。要件 N-12 は「全論理プロセッサを使う競合の速さが、構築中も 90 % 以上」を仮の値として置いていた。

2 つの方式を実装して測った。計測は `docs/benchmarks/s4-yield.md` にある。

- **優先度を下げる方式**（PR #418 の設計）: 競合の速さは 97 % 以上だったが、競合の横で、別のスレッドからの `GC.Collect()` が 2.1〜2.2 秒かかった（1e8 点）
- **混み具合を測って休む方式**（PR #423 の設計、ブランチ `feat/421-yield`）: 競合の速さは 100〜107 % だった。しかし 1e9 点の構築は、休みの段の上限がいちばん低い 1 でも 786 秒と 1,179 秒かかった。上限が 2 と 3 の回は、4 回のうち 3 回が 25 分で終わらなかった
- **何もしないプール**: 競合の速さは 79〜80 %、構築は 97 秒と 104 秒、16.7 ms を超えたフレームは 0、`GC.Collect()` は最大 45 ms と 80 ms だった

休む方式で構築が遅くなる理由は、突き止めていない。ワーカー 8 本の延べ 6,285 秒のうち、走っていたのは約 310 秒、休みは 300 秒だった。残りは、休みから起きた後に CPU が回ってくるのを待つ時間と見ているが、確かめていない。

## Decision

1. **譲る仕組みは作らない**: ワーカーは通常の優先度で走り、CPU の配分は OS に任せる。休む仕組みも、優先度を下げる仕組みも持たない（オーナーの決定、2026-11-12）
2. **要件 N-12**: 「競合が 90 % 以上を保つ」と「空いた機械で +10 % 以内」を取り下げ、ワーカーの走り方と、何もしないプールの実測（競合 79〜80 %、16.7 ms を超えたフレーム 0）を書く。実測は保証する値ではない
3. **CPU を抑えたい利用者**: 本数の少ないプール（`PlotWorkerPool(int threadCount)`）を作って渡す。新しい口は足さない
4. **負荷のある機械での構築の時間**: これまでどおり保証しない（要件 P-2・P-15 の条件、ADR 0002 の Decision 4）
5. **休む方式の実装**: main に入れない。ブランチ `feat/421-yield`（コミット `2c83dc7`）に、計測の場面と一緒に残す

## 退けた案

- **休む方式を直して続ける**: 遅くなる理由が分かっておらず、直る見通しがない。何もしないプールの害（競合が 20 % 遅くなる）は、フレームにも GC にも出ていない
- **休む方式を入れて、既定では使わない**: 構築が 8〜11 倍遅くなる動きを公開 API に残すことになる
- **既定のワーカーの本数を減らす**: 空いた機械でも遅くなる。競合が全コアを使えば、少ない本数でも同じだけ取り合う
