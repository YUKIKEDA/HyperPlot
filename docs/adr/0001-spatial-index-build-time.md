# ADR 0001: 空間タイル索引の構築の時間（要件 P-15）と `Dispose` の待ち

- **Status**: 採用
- **Date**: 2026-11-11
- **Issue**: #405（行 C3a）。設計は Issue #401 の決定 7

## Context

設計書 §9 は、要件 P-15（1e9 点の散布図の空間タイル索引の構築）の値と、`Dispose` が処理中の仕事を待ってよい時間を、行 C3a の最初の計測から 1 つの ADR で決めるとしていた。計測は `docs/benchmarks/c3a-spatial-index.md` にある。参照機で、1e9 点の `float` の x と y（メモリマップ）を、一様な分布と、外れ値のある塊の分布で測った。

構築の時間（ワーカー 8 本、3 周 × ページキャッシュに載っていない・載っている）:

| 分布 | 全体 | 粗いスナップショットの公開まで |
| --- | --- | --- |
| 一様（水準 9、走査 1 回） | 48.1〜58.3 秒 | 3.9〜8.3 秒 |
| 塊（水準 32、走査 8 回） | 122.6〜144.2 秒 | 2.9〜7.3 秒 |

- 計測の間、同じ機械でほかのプロジェクトのビルドと試験が 0.6〜5.6 コアを使っていた。塊の構築は、ほかのプロセスが 0.7 コア以下の 3 回で 122.6〜126.6 秒、2.3 コア以上の 9 回で 131.6〜144.2 秒だった
- 一様は全体の 7 割前後、塊は 4〜5 割が書き込みの段である

`Dispose` の待ち（書き込みを始めた直後に呼ぶ）:

| 状態 | `Dispose` |
| --- | --- |
| 修正の前 | 25〜44 秒。.NET のアクセサが、消す一時ファイルにページを書き出して待つ |
| ビューのハンドルを先に閉じて、書き出さずに外す | 1.3〜2.9 秒。ビューを外してファイルを閉じる時間 |
| 外して閉じる仕事をスレッドプールに渡す | 0.9〜3.7 ms。40 回のうち 1 回は 1,399 ms で、書き込みの最初の単位の終わりを待った |
| 待つ前に構築を止め、書き込みの単位が 256 行ごとに確かめる | 1.1〜3.8 ms（24 回） |

- 書き込みの段の最初の 8 つの単位は、1 つ 0.56〜3.3 秒かかる（そのほかの単位は p99 で 6.6〜39 ms）
- Linux で `fallocate` のないファイルシステム（WSL2 の 9p）に一時ファイルを置くと、glibc の `posix_fallocate` は 12 GB の確保に 17.4 分かかった（1 MB あたり 67〜87 ms）。ext4 と Windows は 2.5〜15 ms である。確保は 1 つの仕事で、`Dispose` はその終わりまで待っていた

## Decision

1. **要件 P-15 の値**: ワーカー 8 本で、一様な分布は 75 秒以内、外れ値のある塊の分布は 180 秒以内。粗いスナップショットは 10 秒以内に公開する。実測の最大（58.3 秒、144.2 秒、8.3 秒）に 2〜3 割の余裕を置いた値である。ほかのプロセスが CPU を使っている機械で測った値を含むので、同じ状態の機械でも満たす（オーナーの決定、2026-11-11）
2. **`Dispose` の待ち**: `Dispose` が待つのは、処理中の仕事が止まったことに気づくまでの時間である。1e9 点で 0.01〜6.1 ms だった。秒の単位で待つ道は、次の 3 つで閉じた（オーナーの決定、2026-11-11）
   - 写しのビューを外してファイルを閉じる仕事は、.NET のスレッドプールに渡す。`Dispose` は待たない。ビューのハンドルをアクセサより先に閉じ、ページをファイルに書き出さない
   - `Dispose` とプールの `Dispose` は、待つ前に構築を止める。書き込みの単位は 256 行（`StopCheckRows`）ごとに確かめ、止まっていれば残りを書かない
   - Linux の確保は、まず `fallocate` を 1 回呼ぶ。`EOPNOTSUPP` のファイルシステムでだけ、`posix_fallocate` を 1 MB（`ReservePiece`）ずつ呼び、合間に構築が止まったかを確かめる。確保を走査のような単位の仕事には分けない。そのファイルシステムでは確保に 12 GB で 17 分かかるままで、その間、索引は空のスナップショットである
3. **`RowsPerUnit`**: 16,384。全体の時間は 16,384 から 1,048,576 のどれでも変わらず、数え上げの単位の中央値（0.77〜1.49 ms）が、1 チャンクのピラミッドの構築（762 µs）にいちばん近い（オーナーの決定、2026-11-11）
4. **`TableShare`**: 0.02 のまま。表は元データの 0.14 %（一様）と 0.28 %（塊）で、`MaxTableRows` に届かなかった

## 退けた案

- **P-15 を 60 秒・150 秒にする**: 実測の最大にほぼ等しく、ほかの負荷のある機械では、コードが変わっていなくても超える
- **P-15 を一様な分布だけにする**: 塊の分布で遅くなっても要件で気づけない
- **`fallocate` のないファイルシステムでは確保せずに進める**: 空きがなくなると、写像への書き込みでプロセスが終わる（設計書 §3.4 の「一時ファイル」）
- **`fallocate` のないファイルシステムでは `IOException` にする**: 17 分の待ちはなくなるが、そのファイルシステムでは索引を作れなくなる
