# S1: 系列ごとの M4 の並列とサンプル

行 S1（Issue #54）の計測の記録。設計書 §5.5.1・§8.1 の `M4Batch` と、`samples/` の 2 つのサンプルを、要件 §5 の参照機で測った。

## 系列ごとの並列（BenchmarkDotNet）

`M4BatchBenchmarks`: 1e7 点の `float`（NaN まばら、`KernelData.Walk`）の系列を、1,920 列で全体の表示に抽出する。「1 つずつ」は呼び出し側のスレッドで `M4.Extract` を系列の数だけ、「プールで」は `PlotWorkerPool.Shared.Extract`（ワーカー 15 本と呼び出し側）。JIT、コアに固定しない（ワーカーを使う場面、`bench.mdc`）。同じ回の 3 ラウンドの値。

| 系列 | 1 つずつ | プールで | 比 |
| --- | --- | --- | --- |
| 1 | 0.97〜1.10 ms | 1.01〜1.18 ms | 1.0〜1.09 |
| 10 | 13.3〜14.0 ms | 2.40〜2.46 ms | 0.17〜0.18 |
| 16 | 21.6〜22.0 ms | 3.29〜3.32 ms | 0.15 |

- 確保は、どの場面も 0 B（BenchmarkDotNet の 0〜1 B は B1 で確かめた計測の枠の分）。`M4BatchTests.Extract_SteadyState_AllocatesNothing` も 0 バイトを示す
- 1 系列のコア 1 つの時間: P コア（論理プロセッサ 2）に固定して 16 系列で 21.5〜21.6 ms（1 系列 1.34 ms）、E コア（論理プロセッサ 12）に固定して 32.8〜33.4 ms（1 系列 2.07 ms）
- プールで並べた時間は、いちばん遅い仕事で決まる。1 系列では呼び出し側が 1 つを受け持つだけで、1 つずつと同じ。10 系列（参照機の物理コアの数）で 2.4 ms は、E コアの 1 系列（2.07 ms）と近い。16 系列は物理コアより仕事が多く、1 つの物理コアに 2 つの仕事が乗る。10 系列から 16 系列で 2.4 ms が 3.3 ms に伸びるのは、このためと読める（スレッドがどのコアに乗ったかは記録していない）
- 予想（Issue #54）: 16 系列を順に 15〜18 ms、プールで 1.5〜3 ms。順は 21.6〜22.0 ms で予想より遅い（コアに固定しない回で、B1 の固定した 0.95〜1.05 ms より 1 系列が遅い）。プールの 3.3 ms は現実的な範囲の外、最悪（8 ms）の内
- 最初の回（1 つずつ 22.7〜24.4 ms、プール 3.97〜4.25 ms）は別の回で、比べない（`bench.mdc`）

## サンプル

### `HelloPlot`（NativeAOT、要件 P-10）

- `dotnet publish samples/HelloPlot -c Release -r win-x64` の警告は 0。`HelloPlot.exe` は 1,664,512 バイト（1.66 MB）で、配るファイルはこの 1 つ（`.pdb` と `.xml` は配らない）。要件 P-10（10 MB 以下）を満たす
- 4 系列 × 1e6 点の生成、ピラミッド、`M4Batch`、描画、PNG まで、ハードウェアで 204〜226 ms、WARP で 82 ms（3 回と 1 回、プロセス全体の時間）

### `BillionSeries`（1e9 点、メモリマップ）

`BillionSeries --dir <folder>`（NativeAOT、2 系列 × 1e9 点、ファイルはキャッシュに載った状態）:

| 段 | 時間 |
| --- | --- |
| データのファイルを作る（1 系列 4 GB、初回だけ） | 3.0 s |
| 2 系列のピラミッドの構築 | 0.69〜0.74 s |
| 全体の表示の `Extract`（2 系列、1,840 列） | 4.9〜6.9 ms |
| 中ほどの 100 万分の 1 の拡大の `Extract` | 0.06〜0.26 ms |

- 全体の表示の 2 系列で 4.9〜6.9 ms は、1e7 点の 1 系列（1.0 ms 前後）より長い。1e9 点のピラミッドは約 163 MB（B1）で、1e7 点の約 1.6 MB と違って L3 に収まらない。ただし、この時間の内訳は測っていない。1e9 点のフレームの時間（要件 P-1）は行 S2 が測る
