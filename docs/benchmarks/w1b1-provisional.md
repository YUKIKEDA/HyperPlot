# W1b1: 暫定のフレームの計測

行 W1b1（Issue #291）の計測の記録。1e9 点の系列のピラミッドを作っている間に、`PlotEngine.RenderFrame` が待たずに描く暫定のフレームの CPU 時間と確保を、作り終えた後のフレームと比べた。

## 条件

| 項目 | 値 |
| --- | --- |
| 機械 | 参照機（要件 §5）: Core i5-13400F（16 スレッド）、GeForce RTX 3060 Ti、Windows 11 |
| ビルド | NativeAOT の Release（スクラッチのハーネス、この PR の作業ツリー。測った後にデータと一緒に消した） |
| 描画先 | 1,920 × 1,080、ハードウェア、倍率 1、`Theme.Light`（軸のタイトルとタイトルあり） |
| データ | y は `float` のメモリマップのファイル（`samples/Shared/WalkFile.cs` のランダムウォーク、1e9 点で 4 GB、ページキャッシュに載っている）、x は `UniformColumn`。線の層が 1 つ |
| ワーカー | `PlotWorkerPool.Shared`（15 本）。比べに 8 本と 4 本。プロセスの優先度は High |
| 慣らし | 同じタイトルの 1,000 点の線を 10 フレーム描いてから、1e9 点の仕様を置く（プロセスの最初のフレームは、フォントの読み込み、文字の整形、GPU のパイプラインの作成で 300 ms ほどかかる。下の「最初のフレーム」） |
| 1 度目の構築 | 仕様を置いてから、16.7 ms ごとにフレームを描き、暫定でないフレームが出るまで。暫定のフレームは、学び直して全体表示を抽出し直す |
| 後のフレーム | 続けて 330 フレーム、全体表示を 1 画素ずつ左右にパンする（全体表示の抽出をし直す、暫定のフレームと同じ仕事）。最初の 30 を捨てて 300 |
| 2 度目の構築 | 全体表示に戻し、列全体を `Invalidate` して、暫定でないフレームが出るまで（温まったバッファで、データを書き換えたときの形） |
| 測る範囲 | CPU は `RenderFrame` の 1 回（`Stopwatch`）、確保は `GC.GetAllocatedBytesForCurrentThread()` の差 |
| 回 | 3 回（プロセスを 3 度） |

## 結果

時間は中央値 / p95 / 最大（ms）。暫定のフレームの確保は、1 度目の構築では最初のフレームを除いた和、2 度目の構築では全部の和。

| 回 | 1 度目の構築 | 暫定のフレーム（数） | 暫定のフレーム | 暫定の確保 | 後のフレーム | 後の確保（300） | 2 度目の構築 | 2 度目の暫定のフレーム（数） | 2 度目の確保 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 0.36 s | 21 | 5.0 / 10.3 / 11.7 | 623,736 B | 4.76 / 5.10 / 6.83 | 8,352 B | 0.15 s | 8: 6.0 / 31.9 / 31.9 | 0 B |
| 2 | 0.35 s | 19 | 5.2 / 42.1 / 42.1 | 615,112 B | 4.82 / 5.22 / 5.61 | 8,456 B | 0.17 s | 8: 8.7 / 32.7 / 32.7 | 0 B |
| 3 | 0.35 s | 19 | 5.2 / 34.8 / 34.8 | 620,224 B | 4.82 / 5.23 / 5.82 | 8,456 B | 0.15 s | 7: 7.7 / 32.8 / 32.8 | 0 B |

ワーカーの数を変えた比べ（各 2 回）:

| ワーカー | 1 度目の構築 | 暫定のフレーム | 2 度目の暫定のフレーム（最初の 1 フレーム） |
| --- | --- | --- | --- |
| 15（`Shared`） | 0.34〜0.38 s | 4.8〜5.2 / 9.8〜42.1 | 22〜32 ms |
| 8 | 0.44 s | 4.0〜4.4 / 6.8〜9.0 | 13〜23 ms |
| 4 | 0.64〜0.66 s | 3.3〜3.6 / 5.6〜6.0 | 1.1〜2.0 ms |

- **暫定のフレームは待たない**: どの回も、1e9 点の構築の間に 19〜21 フレームが描かれた（main は最初のフレームが構築の終わりまで待ち、0.33 s かかる）。暫定のフレームの中央値（4.8〜5.2 ms）は、作り終えた後のフレーム（4.8 ms）と同じ程度
- **フレームが伸びていく**: 1 度目の構築の暫定のフレームは、2 ms ほどから始まり、構築が進むにつれて 7 ms ほどまで伸びる（各フレームの時間を並べて確かめた）。作られたチャンクが増えると、M4 がピラミッドの段から読む範囲が増えるため。統計もピラミッドもまだないチャンクは、何も読まない
- **遅いフレーム（p95 と最大）**: 1 度目の構築の最初のフレーム（11〜42 ms）は、層とピラミッドを作るフレームである。2 度目の構築の最初の 1〜2 フレーム（約 32 ms）は、15 本のワーカーが一度に作り直しを始めた直後に当たる
  - 計画の段に時間を測る口を一時的に入れると、2 度目の構築のフレームの計画の段（コンパイル・準備・抽出・記録）は合わせて 1〜10 ms で、残りは計画の外（バックエンドの描画）だった
  - ワーカーを 4 本にすると、2 度目の構築の最初のフレームは 1〜2 ms で、暫定のフレームの p95 は 6 ms を切る。8 本では間に入る
  - したがって、遅いフレームは UI のスレッドがワーカーと CPU を取り合う分である。ワーカーのスレッドは通常の優先度で、UI のスレッドと同じ。ワーカーの優先度を下げるかどうかは、この行で決めず、Issue #293 にした
- **確保**: 1 度目の構築の暫定のフレームで、約 620 KB を確保した
  - 時間を測る口と同じ形で確保を段ごとに数えると、確保は暫定の最初の 4 フレームの記録（160〜355 KB）と準備（7〜53 KB）にあった。暫定の線の点が増えるにつれて、記録のバッファと、配置の新しい目盛りのラベルの項目が育つ分である
  - 同じエンジンで列全体を `Invalidate` して作り直す 2 度目の構築では、暫定のフレームの確保は 3 回とも 0 B だった。つまり、1 度目の確保はプロットごとに 1 度だけ育つ分で、温まった後の暫定のフレームは確保しない（不変条件 3。Core のテスト `ProvisionalFrames_AllocateNothingOnceWarm` も、暫定のフレームが温まった後 0 B であることを見る）
  - 後のフレーム（パン）の 300 フレームで 8,352〜8,456 B（ほとんどのフレームで、準備の段の 48 B）。同じハーネスを main に向けても同じ 8,352 B だったので、この行の変更ではない。Issue #292 にした
- **最初のフレーム**: 慣らしをしないと、プロセスの最初のフレームは 350〜377 ms かかり、その間に 1e9 点の構築が終わる。時間を測る口で、計画の段は 112 ms（準備の段の最初の文字の整形が主）、残りがバックエンドの最初の描画と分かった。待っているのではない
