## 場面の測り方の欠け

記録を書きながら、場面の出力について次のことが分かった。直しと流し直しは Issue #528 に書いた。

- **GPU 時間が 2 フレーム後ろに付く**: 場面は GPU 時間を `time.Frame - rendered` のフレームに置き、`rendered` は暖機と最初の表示で呼んだ `RenderFrame` の数である。`PlotEngine` を作るたびに `HeadlessRenderer` が `CreateRenderTarget` を呼び、`D3D11Backend.CreateRenderTarget` は番号を取る一番外のフレームを 1 つ開く。場面はエンジンを 2 つ作るので、フレーム f の GPU 時間は f + 2 の欄に入る。出力でもそう読める。密度から生の点に変わった最初の 2 フレームの GPU 時間は密度の値（0.20〜0.22 ms）で、生の点の値は 3 フレーム目から出る
  - 密度だけの回では、600 フレームの GPU 時間の分布は、暖機の最後の 2 フレームが入り、最後の 2 フレームが抜けるだけである。場面が出す「1 フレームの CPU 時間と GPU 時間の和の p95」は、フレーム f の CPU 時間と f − 2 の GPU 時間を足している。そこで P-3 の判定には、CPU 時間の最大と GPU 時間の最大の和も並べる（どのフレームの和もこれ以下）
  - 下の「切り替え」の表は、出力を 2 フレームずらして読んだ値である
- **GPU 時間が来ないフレーム**: 塊の分布の回は、どれも 600 フレームのうち 592 フレームにだけ GPU 時間が来た（一様な分布は 600）。場面は 1 フレームに `LastFrameTime` を 1 つ読むので、1 回の読み出しで 2 つの時間が来たフレームでは古い方を落とす。4 組のクエリの輪が埋まって測らなかったフレームもありうる。場面はどちらで落ちたかを出さない

## 要件 P-15: 粗い密度、確定の公開、密度タイル

- **粗い密度**: 画像の命令を記録した最初のフレーム。どの回も、索引が粗いスナップショットを公開したのを見たフレームと同じだった
- **確定の公開**: 索引が確定のスナップショットを公開したのを見たフレーム（P-15 の構築の時間）

## 切り替え

### 1e8 点、一様な分布

`switch`（`Auto`、しきい値は既定の 1e7 点）を 2 回。2 回とも、暖機の後の 600 フレームのうち密度が 52、生の点が 548 フレームだった（場面の数え方。下の GPU 時間の欄は 2 フレームずらして読んだ）。

入れ替わりは 2 回とも 5 回で、1 回は暖機の中（14 フレーム目）、残りの 4 回は 1 周に 2 回（拡大で密度から生の点へ、戻りで生の点から密度へ）だった。行ったり来たりはしていない。

| 入れ替わり | 画面の幅（範囲に対して） | 前の 10 フレーム CPU / GPU | 後の 10 フレーム CPU / GPU |
| --- | --- | --- | --- |
| 密度 → 生の点（314、614 フレーム目） | 0.2604 | 0.35〜0.94 / 0.19〜0.26 ms | 最初の 2 フレームが 6.0〜9.9 ms、その後 0.44〜0.86 ms / 11.2〜11.7 ms から、8 フレーム目に 3.8〜4.1 ms へ下がる |
| 生の点 → 密度（288、588 フレーム目） | 0.3153 | 最後の 3 フレームが 6.5〜11.6 ms、その前 0.44〜10.6 ms / 8.6〜37.9 ms | 0.43〜1.59 ms / 0.19〜0.79 ms（時間が来たフレーム） |

- **0.8 倍の幅は効いている**: 台本の 1 フレームで、画面の幅はこのあたりで約 9 % 変わる。拡大では 13 フレーム目（幅 0.2866）まで密度で、14 フレーム目（0.2604）で生の点に変わった。戻りでは、その鏡の 287 フレーム目（0.2866）まで生の点で、288 フレーム目（0.3153）で密度に戻った。同じ幅 0.2866 の表示を、行きは密度、帰りは生の点で描いたのが、0.8 倍の帯である。一様な分布の画面内の点の数（1e8 × 幅²）は、幅 0.2604・0.2866・0.3153 で 6.78e6・8.21e6・9.94e6 で、切り替えに使う上限はこれ以上である。どちらの向きでも、帯の端（0.8e7 と 1e7）をまたいだ最初のフレームで変わった。幅の比 1.21（面積で 1.47 倍）が帯の 1.25 倍より大きいのは、台本の 2 フレーム分の刻みで変わったからである
- **生の点から密度に戻る前の GPU 時間（8.6〜37.9 ms）**: 4 か所とも、GPU は低いクロックの段にいた。そのフレームの前後の標本は、1 回目の 288 フレーム目の前で 225〜300 MHz、588 フレーム目の前で 420 MHz、2 回目の 288 フレーム目の前で 210 MHz、588 フレーム目の前で 375 MHz（P8 と P5）である。生の点を描く深い表示の間、GPU の仕事は軽く（生の点のフレームの GPU 時間の p50 は 0.73〜0.75 ms）、クロックは上がらないか、1,665 MHz から下がっていた。そこへ、画面の幅が 1 フレームに約 9 % ずつ広がり、画面内の点が 1e7 近くまで増える。行 R3a の 1e7 点の全体表示（8.5〜13.9 ms）は 1,575〜1,695 MHz の値である。ただし、この低い段の中では時間はクロックに比例していない（210 MHz で最大 36.5 ms、420 MHz で最大 34.9 ms）。クロックの段の分と、描く点の数（ページは丸ごと描くので、画面の外の点も含む）の分は分けていない。行 R3b2 に送った（下の「判定」）
- **密度から生の点に変わった後の GPU 時間（11.2〜11.7 ms から、8 フレーム目に 3.8〜4.1 ms）**: 最初のフレームの値は 4 か所でほぼ同じで、2 回目の 2 か所は P0（1,665 MHz）の標本の中だった。その後は、画面の幅が狭まり点が減るにつれて下がる
- **入れ替わりの前後の CPU 時間**: 密度から生の点に変わった最初の 2 フレーム（6.0〜9.9 ms）と、生の点から密度に戻る前の 3 フレーム（6.5〜11.6 ms）は、生の点のフレームの p50（0.55〜0.79 ms）の 10 倍ほどである。2 回目の周でも同じで、ページはどれも予算に入っている（終わりに 158 ページ、約 124 MB、密度の面は 32 面）。どの段の時間かは段ごとに分けて測っていないので、Issue #528 で分ける（確保したフレームの最後の 587 フレーム目も、この 3 フレームに入る）
- 生の点のフレーム全体（548 フレーム）は、CPU 時間の p95 が 2.75 ms と 1.87 ms、GPU 時間の p95 が 8.07 ms と 8.16 ms だった

### 1e8 点、塊の分布

`switch` を 2 回。600 フレームとも密度で描き、入れ替わりはなかった。CPU 時間の p50 / p95 / p99 / 最大は 0.668〜0.691 / 0.884〜0.899 / 1.011〜1.178 / 1.356〜1.407 ms、GPU 時間は 1.553〜1.555 / 1.935〜1.992 / 3.487〜3.598 / 4.073〜5.012 ms（P8）。

台本は、塊の分布の範囲（±1e9）の 1e-4 の幅（2e5）まで拡大する。生成器の塊（`PointFiles.MakeClusters`、種は上と同じ）から、台本の各表示に入る点の割合の期待値を求めると、最も少ないのはいちばん深い表示（148 フレーム目）で、8.97 % だった。1e8 点では 8.97e6 点で、しきい値の 0.8 倍（8e6）を下回らないので、生の点に戻らない。この表示には、重さ 6.2 % の塊（中心 (512803, 425988)、標準偏差 1,271）が入る。

### 1e9 点、`Auto`

- 一様な分布は、拡大の途中で画面内の点がしきい値の 0.8 倍を下回り、生の点を描く。1e9 点の写しは、終わりに 310 ページ（約 244 MB）が GPU にあり、予算（256 MB、密度の面と分け合う）にほぼ届く。拡大で表示が動くたびに、予算から古いページを追い出して新しいページを 1 フレーム 4 MB まで読むので、29 フレームが暫定だった。生の点のフレームの CPU 時間の p95（6.19 ms）は、この読み出しを含む
- 生の点のフレームの GPU 時間の p99 と最大（25.4 ms、39.0 ms）は、上の 1e8 点と同じく、生の点から密度に戻る前のフレームで、この回の GPU のクロックも 210〜1,665 MHz を動いた（P8 の標本が半分）
- 生の点のフレームは要件 P-3 の対象でなく（P-3 は密度の表示）、P-4 の 16.7 ms と比べる場面である。低いクロックで 16.7 ms を超えるフレームは、行 R3b2 に送った（下の「判定」）

- プロセスのプライベートなメモリは 3.36〜3.37 GB だった。大きいものは、部分の x と y の列（8 部分で 1e8 点、800 MB）、その索引のメモリの写し（1 点 12 バイトで 1.2 GB。部分の列はメモリの上にあるので一時ファイルを作らない、§5.5.2）、場面がカテゴリの列を作るのに使う 1e8 の文字列の配列（800 MB）である

## 確保

UI のスレッドで、`SetView` と `RenderFrame` の前後の `GC.GetAllocatedBytesForCurrentThread()` の差を、フレームごとに数えた。台本は 300 フレームで 1 周するので、最後の 300 フレームは前に描いた表示だけである。

| 場面 | 暖機の後の 600 フレーム | 確保したフレーム（最後） | 最後の 300 フレーム |
| --- | --- | --- | --- |
| 1e9 点・一様・`zoom`・`Density`（3 回） | 1,951,016 B | 149（296 フレーム目） | 0 B |
| 1e9 点・塊・`zoom`・`Density`（3 回）と `Auto`（1 回） | 24,992 B | 20（254 フレーム目） | 0 B |
| 1e8 点・塊・`switch`（2 回） | 29,392 B | 21（254 フレーム目） | 0 B |
| 1e8 点・`categories`（4 回） | 0 B | 0 | 0 B |
| 1e9 点・一様・`zoom`・`Auto`（1 回） | 2,046,296 B | 153（575 フレーム目） | **22,552 B** |
| 1e8 点・一様・`switch`（2 回） | 2,031,088 B | 155（587 フレーム目） | **22,552 B** |

- **密度だけの場面は、2 周目から 0 B**: 確保は台本の 1 周目（296 フレーム目まで）だけで、前に描いた表示に戻った 2 周目は 0 B である。どの回も同じ数だった。1 周目は、拡大で新しい目盛りのラベルが出続ける。コードでは、整形のキャッシュ（§5.6、`TextEngine.Shape`）は新しい文字列ごとに項目を 1 つ作り（約 570 バイト）、8,192 項目でいっぱいになるまで確保する。使い回す配列（計画の `_cells`・`_pieces`、記録のリスト）も、1 周目のいちばん大きいフレームまで伸びて縮まない。一様な分布の範囲は [0, 1e6) で、台本は幅 100 の表示まで拡大するので、目盛りのラベルは 6 桁の数が細かく変わる。塊の分布の範囲は ±1e9 で、いちばん深い表示でも幅は 2e5 あり、ラベルの種類は少ない。これが 1,951,016 B と 24,992 B の差と読めるが、1 周目のバイトを段に分けては数えていない。段ごとの内訳は Issue #528 で数える
- **生の点を描く場面は、2 周目にも 22,552 B**: 一様な分布で生の点に切り替わる 3 回は、どれも最後の 300 フレームで 22,552 B を確保した。点の数（1e8 と 1e9）によらず同じ数で、先行の計測（ヘッド `5739b02`）の同じ場面も同じだった。定常状態のフレームの確保で、不変条件 3 に反する。Core の確保 0 の試験（`Frames_DensityAndTheSwitch_AllocateNothing`、偽のバックエンド）は 0 B で通るので、実機のバックエンドかエンジンの道にある。Issue #528 に出した
- 塊の分布の 1e8 点（29,392 B）と 1e9 点（24,992 B）の 1 周目の差 4,400 B も、段に分けて数える（Issue #528）

## 判定

- **要件 P-3**: 1e9 点の拡大して戻る台本を密度で描いたフレームは、1 フレームの CPU 時間と GPU 時間の和の p95 が、一様な分布で 2.64〜3.64 ms、外れ値のある塊の分布で 2.46〜3.70 ms だった（3 回ずつ、1,920 × 1,080、GPU は P8 の 210 MHz）。CPU 時間と GPU 時間のそれぞれの最大の和でも 4.40〜6.47 ms で、16 ms に収まる。生の点を描くのは、画面内の点の上限がしきい値（1e7）以下のときだけである（切り替えの帯は上の「切り替え」のとおり効いている）
- **要件 P-15**: 粗い密度は 14 回とも 10 秒以内（3.21〜8.34 秒）。ほかのプロセスが 2 コア以下の回の確定の公開は、一様 48.61〜68.35 秒、塊 147.80〜152.20 秒で、値に収まる。密度タイルが付くまでは、どの回も 10 秒以内（2.91〜6.34 秒）
- **超えた場面と送り先**
  - 生の点から密度に戻る前の、画面内に 1e7 点近くの生の点を描くフレームは、GPU が低いクロックの段（P8・P5、標本で 210〜465 MHz）にいて、GPU 時間が 16.7 ms を超える（最大 37.9 ms、1e9 点の `Auto` で 39.0 ms）。生の点の重さと予算を扱う行 R3b2 に送った（`docs/roadmap.md` の行 R3b2）
  - 負荷のある機械での確定の公開（一様 89.97 秒、塊 192.22 秒、ほかのプロセス 4.2 コア）は、P-15 の保証の外である（N-12、行 S4）
  - 8 カテゴリに分けた層の粗い密度は、前の部分の構築を待つ（1e8 点の塊で 7.6〜8.0 秒）。行 R3d3 の「1 つの索引」で解く。それまでは §5.5.2 の限界（オーナーの決定、2026-11-14）
- **確保**: 密度だけの場面は、2 周目から 0 B。生の点に切り替わる場面は 2 周目にも 22,552 B を確保し、Issue #528 に出した
