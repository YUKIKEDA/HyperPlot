# R4: 線の結合・端・破線の模様の計測

行 R4（Issue #132）の計測の記録。設計書 §5.1・§5.3 の、丸でない結合と端と 3 区間以上の破線（画素の中の 32 点の覆い）の時間を、行 R2 と同じ場面で要件 §5 の参照機で測った。

## 条件

| 項目 | 値 |
| --- | --- |
| 機械 | 参照機（要件 §5）: Core i5-13400F、GeForce RTX 3060 Ti、Windows 11 |
| ビルド | NativeAOT の Release（スクラッチのハーネス）。この PR の作業ツリーと main（`d71cb40`、`.dev/r4-base`）を同じハーネスで |
| 線 | 行 R2 の場面: 1,920 列の M4 の出力を模した折れ線（1 列に 4 点、7,680 点）を 16 本。xorshift64* で高さ 1,080 の中を歩く。太さ 1.5、不透明 |
| 描画先 | 1,920 × 1,080、ハードウェア |
| 測る範囲 | GPU はフレームのタイムスタンプのクエリ（`IGpuBackend.LastFrameTime`）。CPU は 16 本の `DrawPolyline`（記録）と `Draw`。1,200 フレームのうち最初の 30 を捨てた 1,170 フレームの中央値 / p95。100 フレームごとに `ReadPixels` で GPU を待つ |
| GPU のクロック | 測っている間 P0（`nvidia-smi` で 500 ms ごと。123 回のうち P0 が 122 回、P8 の 1 回は始まる前） |

毎フレーム `ReadPixels` で GPU を待たせた最初の回は、GPU が休んでクロックが下がり、丸の線が 2.2 ms と出た（`bench.mdc` の PR #47 の記録と同じ）。上の表は読み戻しを 100 フレームごとにした回である。

## 結果

丸の線と 2 区間の破線（行 R2 の道）は、main とこの PR を交互に（main、PR、PR、main を 3 回）:

| 場面 | GPU（main） | GPU（PR） | 記録（main） | 記録（PR） |
| --- | --- | --- | --- | --- |
| 丸 | 681〜684 / 929〜958 µs | 680〜685 / 936〜1,019 µs | 447〜449 µs | 450〜457 µs |
| 丸・2 区間の破線 | 676 / 932 µs | 676 / 930 µs | 449 µs | 455 µs |

- 丸の線の GPU 時間は変わらない（行 R2 のシェーダと定数の値のまま）
- 記録は 0.9 % 増えた（中央値の平均で 448 → 453 µs）。PR の回の中央値の幅（450〜457 µs）と同じ大きさで、原因は分けていない（候補は、丸の線と部品の線の振り分け、8 区間を持つようになって大きくなった `LineStyle` を値で持つ `PolylineRecord` の書き込み、`ValidateStyle` の区間の検査）。丸の線のループ（`RecordSegments`）は行 R2 と同じ

32 点の覆いの線（この PR だけ。2 回）:

| 場面 | GPU | 記録 | 部品 |
| --- | --- | --- | --- |
| 実線・丸の結合・平らな端 | 2,161〜2,190 / 2,631〜2,652 µs | 1,347 µs | 結合ごとの円 |
| マイター | 2,904〜2,936 / 3,497〜3,530 µs | 1,642〜1,678 µs | 結合ごとのマイターか面取り |
| 面取り | 2,904〜2,929 / 3,515〜3,519 µs | 1,355〜1,372 µs | 結合ごとの面取り |
| 2 区間の破線・平らな端 | 3,629〜3,655 / 4,254 µs | 2,244〜2,248 µs | 区間の中の結合ごとの円 |
| 8 区間の破線・丸の端 | 4,697〜4,731 / 5,348〜5,495 µs | 4,204〜4,215 µs | 区間の中の結合ごとの円、区間の端 |

- **GPU**: 実線で丸の線の約 3.2 倍、マイターと面取りで 4.3 倍、破線で 5.3〜6.9 倍。M4 の線は 1 画素に 4 つの線分があり、線分の四角形（太さの半分と 1 画素だけ広げたもの）が同じ画素に何枚も重なるので、画素の 32 点の判定が重なりの数だけ走る。丸の線は画素ごとに距離を 1 回求めるだけである
- **記録**: 丸でない線は、線分ごとに向きを求め（平方根と割り算）、結合ごとに部品を 1 つ書く。M4 の線は線分ごとに結合があるので、部品が線分と同じ数（16 本で約 12 万）になる。破線はさらに、結合ごとに破線の区間の位置を判定する（`DashAt`）。8 区間の破線の記録のプロファイル（Visual Studio の収集器と `xperf`、NativeAOT）では、`DashAt` が 43 %、線分ごとの向き（`AddSegmentPieces`）が 28 %、結合の部品が 14 % だった
- この場面は丸でない線の費用が最も出る形である（ほぼ画素ごとに結合がある）。結合の少ない太い線（step・rule・segment・矩形の縁）では、部品も四角形の重なりも少ない

## 詰めたこと

最初の実装からの変化（同じ場面、この PR の中で前後を測った）:

| 場面 | GPU | 記録 |
| --- | --- | --- |
| マイター | 3,902 → 2,904 µs | 2,503 → 1,678 µs |
| 8 区間の破線 | 48,198 → 4,697 µs | 10,366 → 4,204 µs |

- 部品の記録を配列の要素へ直接書き、32 バイトにそろえた。28 バイトの記録をスタックで作って重なる 16 バイトの半分で写す形は、ストアの転送（store forwarding）で止まり、マイターの記録の 52 % を占めていた（プロファイルと `dumpbin /disasm` で確かめた）
- 破線の周期の中の位置を `%`（CRT の `fmodf`）でなく floor で求めた（シェーダと同じ式）。`fmodf` が 8 区間の破線の記録の 24 % を占めていた。区間の端の位置は折れ線ごとに 1 回だけ求める
- シェーダは、線分から太さの半分と √2 / 2 より遠い画素を 32 点を数える前に捨て、実線で四角形の中にすっぽり入る画素は 32 点すべてを立てる
- 破線のシェーダは、画素の線に沿った範囲にかかる区間を画素ごとに 1 回集め（4 つまで）、点ごとにはその区間だけを判定する。候補が 1 つの画素（周期が太さより長い普通の破線ではほとんど）は、実線と同じ短いループで判定する。候補の多い道を点のループの中に置いていた形は 3 倍遅かった（同じ形の実線の模様（オン 100,000）で 7.8 ms と 2.5 ms）

## NativeAOT

| サンプル | main（`d71cb40`） | この PR |
| --- | --- | --- |
| `HelloPlot` | 1,805,824 B | 1,843,200 B（+37,376 B） |
| `SpecPlot` | 2,247,168 B | 2,285,568 B（+38,400 B） |

どちらも警告 0。`SpecPlot` はハードウェアと WARP、倍率 1 と 1.5 で 3 枚の PNG を書いた。`HelloPlot` の PNG は main のものと画素まで同じだった（丸の線の道）。

ILC の map ファイル（`IlcGenerateMapFile`）の節の長さを名前で分けると、`HelloPlot` の増分は、32 点の覆いのシェーダのバイトコード（`LineMask.hlsl` の 5 つ）が +19,448 B、Core の節（部品の記録、`LineDash` の 8 区間、検査）が +9,224 B、D3D11 の節（覆いの段、マスクのテクスチャ）が +4,338 B、ランタイムと BCL が +1,675 B、メタデータが +1,161 B で、節の和は +35,846 B である。ファイルの増分との差 +1,530 B は PE の節の揃えである。`SpecPlot` は Core の節が +11,439 B（`LineBuilder` の口を含む）で、ほかは同じ大きさ、節の和は +38,125 B、揃えの差は +275 B である。
