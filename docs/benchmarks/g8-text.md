# G8: text の Geom の計測

行 G8（Issue #188）の計測の記録。設計書 §5.5.3 の text の Geom で、プロットの上限の 4,096 個のラベルを 1 フレームに描く時間を、要件 P-1（CPU と GPU がそれぞれ p95 で 8 ms 以下）と比べた。要件 §5 の参照機で測った。

## 条件

| 項目 | 値 |
| --- | --- |
| 機械 | 参照機（要件 §5）: Core i5-13400F、GeForce RTX 3060 Ti、Windows 11 |
| ビルド | NativeAOT の Release（スクラッチのハーネス、この PR の作業ツリー。測った後に消した） |
| 描画先 | 1,920 × 1,080、ハードウェア、倍率 1、`Theme.Light`（軸・グリッド・目盛りのラベルつき） |
| ワーカー | `PlotWorkerPool.Shared` |
| データ | 4,096 行。x と y は [0, 100] の一様な乱数（シード 8） |
| 場面 | **数**: 数の列（10,000 + 1.37 i）を書式 "F2" で書いたラベル（8 文字、たとえば "10001.37"）、中央の揃え。**名前**: 64 カテゴリの名前（"name0000" など 8 文字）のラベル、中央の揃え。**左揃え**: 数の場面を `Left` の揃えにしたもの（ラベルを測らない）。**パネルの外**: 数の場面で y の domain を [200, 300] にし、どの行も描かないもの（行を写す仕事だけ）。**なし**: 同じプロットに層がないもの |
| フレーム | y の domain を毎フレーム変える（64 通り、0.1 ずつ広げる）。配置と記録を毎フレームやり直す。2 秒描いて温めた後、500 フレーム |
| 測る範囲 | CPU は `HeadlessRenderer.Render(PlotSpec)` の 1 回（記録と、バックエンドの整形のキャッシュの引き当て・アトラス・グリフの記録・描画）。GPU はフレームのタイムスタンプのクエリ。確保は `GC.GetAllocatedBytesForCurrentThread()` の `Render` の前と後の差 |
| 回 | 場面の順に 1 回ずつを 3 回 |
| GPU のクロック | 最初の 3 回の間、`nvidia-smi --query-gpu=timestamp,clocks.gr,pstate` を 150 ms ごとに記録した（108 標本）。P0 が 95、P3 が 12 で、クロックは 975〜1,965 MHz（平均 1,725 MHz）だった |

## 結果

中央値 / p95（µs）。各欄は 1 回目、2 回目、3 回目。

| 場面 | CPU | GPU |
| --- | --- | --- |
| なし | 201 / 242、194 / 311、201 / 319 | 173 / 182、172 / 180、173 / 181 |
| パネルの外 | 276 / 453、252 / 305、260 / 469 | 172 / 180、172 / 176、172 / 176 |
| 左揃え | 1,825 / 2,535、1,898 / 2,993、1,756 / 2,131 | 310 / 432、313 / 439、306 / 334 |
| 数 | 2,183 / 2,652、2,025 / 2,316、2,024 / 2,325 | 431 / 878、329 / 857、308 / 847 |
| 名前 | 1,994 / 2,400、1,981 / 2,299、1,964 / 2,189 | 459 / 907、442 / 866、314 / 840 |

- **要件 P-1**: 4,096 個のラベルの 1 フレームは、CPU が p95 で約 2.3〜3.3 ms、GPU が p95 で約 0.9 ms で、どちらも 8 ms に収まる
- **CPU の内訳**（場面の差から）
  - **行を写す仕事**（パネルの外 − なし）: 約 60 µs。4,096 行の x と y を写し、パネルの中かを確かめる
  - **ラベルの記録と描画**（左揃え − パネルの外）: 約 1.55 ms。4,096 個の `DrawText` の記録と、バックエンドが描くときの整形のキャッシュの引き当て、32,768 グリフ（8 文字 × 4,096）のアトラスの引き当てとグリフの記録である。グリフ 1 つあたり約 47 ns
  - **揃えのために測る仕事**（数 − 左揃え）: 約 0.2 ms。中央の揃えは、記録の段で 4,096 個を `TextEngine.Measure` で測る（整形のキャッシュに当たる、1 個あたり約 50 ns）
  - 名前の場面は、カテゴリの名前を列からそのまま記録し、文字列を作らないので、数の場面と同じ桁である
- **GPU**: ラベルの分は、なしの場面との差で約 0.14 ms（中央値、32,768 グリフの四角）。中央の揃えの場面の p95 と、別の走りの中央値に約 0.85 ms の山がある。追加の走りで、フレームを y の domain の 64 通りに分けて中央値を見ると、どの domain もほぼ同じで（左揃えで 874〜915 µs、数で 461〜510 µs、2 つの domain だけ 846 µs）、山は domain によらず走りによって入れ替わった。同じ場面の中央値が走りによって約 0.31 ms と約 0.85 ms に分かれ、その比（約 2.7）がクロックの記録の 975 MHz と 1,965 MHz の比（約 2）に近いので、低いクロックのときの値と読む（行 G7c の計測と同じく、上限として読む）
- **転送**: 1 フレームのグリフの記録は 32,768 × 48 B = 約 1.6 MB で、設計 §5.5.3 の見積もりどおり
- **整形のキャッシュ**: 4,096 のラベルと軸の文字列は、上限 8,192 のキャッシュに収まり、温まった後のフレームは整形しない（テスト `TextGeomTests.Cache_HoldsTheLabelsAndTheGuides`）
- **確保**: どの場面も 500 フレームで 8,352 B（1,000 フレームで 16,568 B）だった。層のない「なし」の場面でも同じ量で、y の domain を固定しても変わらないので、text の層の確保ではない。フレームあたり約 17 B で、フレームの数に比例する。原因は分けていない。温まったフレームの確保を追う Issue #141 に、この数を書いた
