# R3f: 大きさと形のチャネルの計測

行 R3f の計測の記録。設計書 §9 の「大きさと形のチャネル」の場面を、要件 §5 の参照機で測る。行 R3f は 2 本の PR に分かれていて、「注釈のマーカー 1,024 個」と「確保」は 1 本目（Issue #454、6 つの形と注釈の移行）、「CPU の道の大きさと形」と「索引の道の 6 つの形」は 2 本目（Issue #456、`SizeBy`・`ShapeBy`）の分である。

## 条件

| 項目 | 値 |
| --- | --- |
| 機械 | 参照機（要件 §5）: Intel Core i5-13400F（16 スレッド）、48 GB、GeForce RTX 3060 Ti、Windows 11 |
| ビルド | `HyperPlot.E2E` の NativeAOT Release（win-x64、発行の警告 0）。ブランチ `feat/454-marker-shapes` は 3,769,344 B。比べる `main`（`344aabc`）は、同じ場面のファイルを足した作業ツリーで発行して 3,767,296 B。プロセスの優先度は高 |
| 場面 | `annotations`: 1,000 点の線の層 1 つと、マーカーの注釈 1,024 個を `PlotEngine` で 1,920 × 1,080 に描く。定義域は [0, 100]² |
| データ | 注釈の位置はシードつき（`Random(7)`）の一様。半径は 3〜6 DIP を順に。形は、引数の数だけを列挙の先頭から順に（3 なら円・正方形・十字） |
| 台本 | 行 R3a の `points` と同じ。1 周 300 フレーム: 動く中心のまわりで、全体から 10 分の 1 の幅まで拡大して戻る。暖機 30 フレームの後の 600 フレーム（2 周）を測る |
| フレームの間隔 | 16.7 ms 以上空ける（`timeBeginPeriod(1)` と `Thread.Sleep`） |
| GPU のクロック | 軽い場面なので上がらない。計測の直後の `nvidia-smi` は 210 MHz だった。GPU 時間は、このクロックでの値である |

## 再現

```powershell
$env:PATH = "C:\Program Files (x86)\Microsoft Visual Studio\Installer;" + $env:PATH
dotnet publish benchmarks/HyperPlot.E2E -c Release -r win-x64 -o .dev/e2e
.dev/e2e/HyperPlot.E2E.exe annotations 3 600
.dev/e2e/HyperPlot.E2E.exe annotations 6 600
```

`main` の値は、`main` の作業ツリーに `benchmarks/HyperPlot.E2E/AnnotationsScene.cs` と `Program.cs` を写して発行した（場面は 3 つの形だけを使うので、`main` でも動く）。

## 注釈のマーカー 1,024 個

前は、注釈のマーカーを形ごとの命令で描いていた（円は扇形、正方形は矩形、十字は折れ線 2 本）。後は、点の層と同じ `DrawMarkers` で描く。3 つの形の場面を、前と後で交互に 3 回ずつ流した。

| | CPU p50 | CPU p95 | CPU 最大 | GPU p50 | GPU p95 | GPU 最大 |
| --- | --- | --- | --- | --- | --- | --- |
| 前（`main`、3 つの形、3 回） | 1.67〜2.00 ms | 2.51〜3.38 ms | 3.69〜4.58 ms | 1.20〜1.26 ms | 9.28〜9.58 ms | 11.36〜12.97 ms |
| 後（3 つの形、3 回） | 0.65〜0.68 ms | 1.06〜1.13 ms | 1.39〜1.60 ms | 1.29〜1.32 ms | 2.66〜3.10 ms | 4.12〜5.44 ms |
| 後（6 つの形、3 回） | 0.64 ms（1 回だけ読んだ） | 1.02 ms（同じ） | 1.33 ms（同じ） | 1.33〜1.38 ms | 2.87〜3.13 ms | 4.05〜5.47 ms |

- CPU 時間は、p50 で約 0.4 倍、p95 で約 0.3〜0.4 倍になった。前は、注釈 1 つが命令 1 つか 2 つ（扇形の呼び出し、矩形、折れ線 2 本）を記録していた。後は、点 1 つの記録（32 バイト）で、続く `DrawMarkers` は 1 回の描画にまとまる
- GPU 時間の p50 は変わらない（1.2〜1.4 ms）。p95 は 9.3〜9.6 ms から 2.7〜3.1 ms に下がった。どのフレームが p95 に当たるかを分けて読んでいないので、下がった理由は確かめていない。この PR の効果の大きさとしては、CPU 時間だけを挙げる
- 6 つの形の GPU 時間は、3 つの形と同じである。別に流した 6 つの形の 1 回は、GPU p50 が 0.27 ms、p95 が 1.63 ms と低かった。同じ場面をその後 3 回流すと 1.33〜1.38 ms で、3 つの形と並んだ。低い 1 回は、PR #455 のレビューの後に同じ場面（6 つの形を 4 回、3 つの形を 2 回）を流し直して再現しなかった（GPU p50 1.30〜1.38 ms、どの回も前後の GPU のクロックは 210 MHz か 1,905 MHz）。理由は確かめていない。表の 6 つの形の行は、再現した 3 回の値である
- 6 つの形の CPU の列は、最初の 1 回の値だけを読んだ。後の 3 回は、GPU と確保の行だけを残した

## 確保

- 暖機の後の 600 フレームで、52,256 B か 52,360 B。行 R3a の台本と同じく、1 周目に新しく出る目盛りのラベルの分である（`docs/benchmarks/r3a-points.md`）
- 最後の 300 フレーム（2 周目）は、16 回のうち 11 回が 0 B、5 回が 104 B だった。104 B の内訳は、前（`main`）の 6 回のうち 1 回、後の 10 回のうち 4 回である。合計が 52,360 B の回は、104 B がどこかのフレームで 1 回出た回で、52,256 B の回は 1 回も出ていない
- 104 B は、行 G4 の記録（`docs/benchmarks/g4-geoms.md` の「PR #125 のレビュー」）にある形と同じ大きさで、同じ線の層を持つ場面で、1 回の実行に多くて 1 回だけ出る。そこでは、計画の `M4Batch` のロックを初めて本当に待つフレームの 104 B と突き止めている。この場面で段ごとに数え直してはいない。`main` でも出るので、`main` と共有する Issue #141（`M4Batch.Wait` の確保）に、回数とあわせて書いた

## CPU の道の大きさと形（Issue #456）

`points 131072 6 1 uniform 600 <カテゴリ> zoom <チャネル>`: 131,072 点の一様な層、直径 6 DIP、不透明、行 R3a の拡大の台本。チャネルなし（`color` でカテゴリ 0）、`SizeBy`（行の番号を 101 で割った余り）、6 カテゴリの `ShapeBy`、その両方の 4 通りを、続けて 1 回ずつ流すのを 1 巡とした。ビルドは `feat/456-size-shape`。

最初の 2 巡で、`SizeBy` の層が目立って遅かった。点の大きさを 1 点ずつ列から読んで写していた（`DifferenceAt` と `SizeScale.Diameter`）のを、フレームの点をまとめて読み（`ReadDifferences`）、まとめて写す形（`SizeScale.Diameters`）に替えて、もう 2 巡流した。

| | チャネルなし | `SizeBy` | `ShapeBy` | 両方 |
| --- | --- | --- | --- | --- |
| 直す前、1 巡目（CPU p50 / p95） | 1.78 / 2.25 ms | 4.37 / 6.96 ms | 3.50 / 4.78 ms | 4.51 / 7.14 ms |
| 直す前、2 巡目 | 2.15 / 2.99 ms | 6.18 / 7.24 ms | 3.10 / 4.27 ms | 7.01 / 8.14 ms |
| 直した後、1 巡目 | 1.74 / 2.42 ms | 2.94 / 4.10 ms | 2.69 / 3.27 ms | 3.28 / 3.84 ms |
| 直した後、2 巡目 | 2.89 / 4.02 ms | 5.02 / 6.09 ms | 5.02 / 6.04 ms | 5.98 / 7.13 ms |

- 巡ごとの揺れが大きい（チャネルなしの p50 が 1.74〜2.89 ms）ので、同じ巡のチャネルなしとの比で読む。`SizeBy` は、直す前が 2.5 倍と 2.9 倍、直した後が 1.7 倍と 1.7 倍だった。`ShapeBy` は 1.4〜2.0 倍、両方は直す前が 2.5 倍と 3.3 倍、直した後が 1.9 倍と 2.1 倍である
- 直した後の 2 巡目は、4 つの場面のどれもが 1 巡目より遅い。巡の間で機械の状態が変わったと見ているが、確かめていない
- 残りの差（`SizeBy` で 1.2〜2.1 ms）は、点ごとに直径と形を写す記録の段のループと、点ごとの見た目を取る `DrawMarkers` の口の分である。段ごとには分けて測っていない
- GPU 時間の p95 は 3.4〜5.7 ms で、CPU 時間との和は、どの場面も p95 で 13.3 ms 以下だった（P-4 の 16.7 ms の内）
- 確保: どの場面も 2 周目の 300 フレームは 0 B。1 周目の確保（48〜49 フレーム）は、行 R3a と同じく新しい目盛りのラベルの分である

## 索引の道の 6 つの形（Issue #456）

`points 10000000 6 0.6 uniform 600 <カテゴリ> whole <チャネル> [形]`: 1e7 点の一様な層、直径 6 DIP、不透明度 0.6、全体表示。6 カテゴリは行ごとに順に替わる。GPU のクロックは、どの回も実行の前後で 1,785〜1,935 MHz だった（最初の回の前だけ 210 MHz）。

| 場面（GPU p50 / p95） | 1 回目 | 2 回目 | 3 回目 |
| --- | --- | --- | --- |
| 6 つの色に分けた層（円） | 15.53 / 16.08 ms | 15.76 / 15.93 ms | 16.08 / 16.36 ms |
| 6 つの形に分けた層（色は 1 つ） | 17.29 / 17.55 ms | 17.47 / 17.72 ms | 18.04 / 18.53 ms |
| 同じ列で色と形の両方に分けた層 | 15.44 / 15.85 ms | | |
| 6 つの色に分けた層（どれも正方形） | 18.14 / 18.66 ms | | |
| 6 つの色に分けた層（どれも斜めの十字） | 16.42 / 16.75 ms | | |

1 つの部分の 1e7 点を、1 つの形で描いた GPU 時間（p50 / p95）:

| 円 | 正方形 | 十字 | 三角形 | ひし形 | 斜めの十字 |
| --- | --- | --- | --- | --- | --- |
| 11.10 / 11.34 ms | 12.61 / 12.91 ms | 10.00 / 10.22 ms | 10.62 / 10.91 ms | 10.33 / 10.57 ms | 12.28 / 12.59 ms |

- **P-4**: 6 つの形に分けた層は、GPU 時間の p50 だけで 17.3〜18.0 ms で、16.7 ms を超える。6 つの色に分けた層も 15.5〜16.1 ms で、CPU 時間（p95 0.8〜1.1 ms）との和は 16.7 ms を超える回がある。設計 §9 のとおり、行 R3b に送る（行 R3a の 8 カテゴリの 17.5〜17.6 ms と同じ扱い）。ロードマップの行 R3b に書いた
- 形に分けた層が色に分けた層より 1.7〜2.2 ms 遅い。1 つずつ変えて確かめた: 同じ列で色と形の両方に分けた層（部分の分け方と形は、形に分けた層と同じで、色だけが部分ごとに違う）は 15.44 ms で、色に分けた層と同じだった。したがって差は形の違いからではなく、6 つの部分がどれも同じ色であることから来ている。同じ色の部分が続くと GPU 時間が延びる理由は、GPU の中で確かめていない
- 1 つの形で描いた時間は、形ごとに 10.0〜12.6 ms で違う。正方形と斜めの十字が長い。6 つの色に分けた層を正方形で描くと 18.14 ms で、円の 15.5〜16.1 ms より 2 ms あまり長い
- 確保: どの場面も 2 周目の 300 フレームは 0 B
- 6 つの形に分けた層の GPU のフレームの数（`frames`）は 132〜269 で、600 より少ない。GPU 時間がフレームの間隔より長く、問い合わせが追いつかないフレームを数えないためである
