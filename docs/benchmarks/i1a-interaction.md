# I1a: 対話のフレームの計測

行 I1a（Issue #274）の計測の記録。1e9 点の系列を `PlotEngine` に置き、入力の台本（ホイールの拡大と、ドラッグのパン）を流したときの 1 フレームの CPU と GPU の時間、確保、入力 1 つの処理の時間を、要件 P-1（1 フレームの p95 が 8 ms 以下）と照らした（設計 §9 の「対話（行 I1a）」）。

## 条件

| 項目 | 値 |
| --- | --- |
| 機械 | 参照機（要件 §5）: Core i5-13400F、GeForce RTX 3060 Ti、Windows 11 |
| ビルド | NativeAOT の Release（スクラッチのハーネス、この PR の作業ツリー。測った後にデータと一緒に消した） |
| 描画先 | 1,920 × 1,080、ハードウェア、倍率 1、`Theme.Light`（軸のタイトルとタイトルあり） |
| ワーカー | `PlotWorkerPool.Shared`。プロセスの優先度は High |
| データ | y は `float` のメモリマップのファイル（`samples/Shared/WalkFile.cs` のランダムウォーク、1e9 点で 4 GB、ページキャッシュに載っている）、x は `UniformColumn`（0 から 1 刻み） |
| 時刻 | 手で進める `TimeProvider`。各イベントの前に 16.7 ms 進め、イベント 1 つに 1 フレームを描く |
| 台本 | パネルの真ん中でホイールを 60 目盛り（1 目盛り 1.2 倍、ズームのアニメーション 150 ms）、続けて左ボタンを押し、300 回動かし（左へ 2 画素ずつ、上下に ±20 画素）、離す。362 フレーム |
| 慣らし | 整形のキャッシュを 8,192 個の別の文字列で満たし、台本を 1 度流してから全体表示に戻し、2 度目を測る（1 度目の確保は 47 KB: ズームで出る新しいラベルの整形のキャッシュの項目、境界の配列、履歴の容量） |
| 測る範囲 | CPU は `RenderFrame` の 1 回、入力は `OnWheel`・`OnPointer` の 1 回（フレームとは別）、GPU はフレームのタイムスタンプのクエリ、確保は各イベントとフレームの `GC.GetAllocatedBytesForCurrentThread()` の差の和 |
| 回 | 3 回（プロセスを 3 度） |

## 結果

フレームと入力は中央値 / p95 / 最大。

| 回 | フレームの CPU（ms） | フレームの GPU（ms） | 入力（µs） | 確保（362 フレーム） |
| --- | --- | --- | --- | --- |
| 1 | 1.002 / 3.866 / 9.190 | 0.182 / 0.209 / 0.274 | 4.4 / 7.8 / 17.9 | 0 B |
| 2 | 0.873 / 3.838 / 7.587 | 0.182 / 0.211 / 0.265 | 3.5 / 7.9 / 97.8 | 56 B |
| 3 | 0.875 / 4.361 / 8.442 | 0.182 / 0.214 / 0.268 | 3.7 / 8.3 / 14.0 | 0 B |

ホイールの 60 フレームとドラッグの 302 フレームに分けた CPU（中央値 / p95、ms）:

| 回 | ホイール | ドラッグ |
| --- | --- | --- |
| 1 | 2.541 / 8.224 | 0.956 / 1.233 |
| 2 | 2.607 / 7.076 | 0.830 / 1.116 |
| 3 | 2.894 / 7.897 | 0.827 / 1.103 |

- **P-1 との比べ**: 全体のフレームの CPU の p95 は 3.8〜4.4 ms、GPU の p95 は 0.21 ms で、どちらも 8 ms を下回る。拡大の後の表示は 1e9 点の約 17,700 点の幅（1.2^60 ≈ 5.6 万倍）
- **ホイールのフレーム**: 2 ms を超えたフレーム（36〜43 個）はどれもホイールの 60 フレームの中で、全体表示に近い広い範囲を引く最初の十数フレームに当たる（台本の初めから数えた各フレームの時間を別の実行で並べて確かめた。広いほど遅く、5〜8 ms）。広い範囲の取り出しは 1 系列を 1 つのワーカーの 1 つの仕事で引くので、行 G6a・G6b・G6c の 1 枚の図の全体の表示（p95 5.1〜7.4 ms、`docs/benchmarks/g6c-figures.md`）と同じ形で、最大の 9.2 ms（1 回目）もここに当たる。1 系列を画素列の範囲で分けるかの判断は、設計 §5.5.1 の未決のとおり
- **ドラッグのフレーム**: p95 1.1〜1.2 ms。x と y の両方が毎フレーム動き、新しい目盛りのラベルが出続ける
- **入力**: 1 つの処理は p95 で 8.3 µs 以下。2 回目の最大 97.8 µs は 362 個のうち 1 つで、ほかの回の最大は 18 µs 以下
- **確保**: 測った台本で 0 B。2 回目の 56 B は、NativeAOT が初めて `Lock` を待つときの初期化の確保で（不変条件 3 の除外）、プロセスに 1 度だけ出る。慣らしの 1 度目の 128 KB は、ズームで出る新しいラベルの整形のキャッシュの項目と境界の配列と履歴の容量
- **最初のフレーム**: 375〜383 ms（ピラミッドの構築を待つ、§4.8 の待ち方）

## 計測で見つけて直したこと

最初の計測では、ホイールのフレームが 0.2 ms と軽く、ホイールを止めた後の 3 フレームが 5〜8 ms だった。ホイールを 1 フレームごとに回すと、新しい目盛りのたびにアニメーションが前のフレームで描いた値から始め直し、その時刻の値（t = 0）を描くので、回している間ビューが動かず、止めた後に全体表示から一気に動いていた。操作が来たときに、まずアニメーションをその時刻まで進めてから新しい補間の起点にするよう直した（`HistoryAnimationTests.Animation_WheelAtEachFrame_MovesEachFrame`、設計 §6.2）。上の表は直した後の値
