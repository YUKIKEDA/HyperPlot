# W1a: WPF のホストの計測

行 W1a（Issue #286）の計測の記録。設計 §9 の「WPF のホスト」のとおり、次の 3 つを測った。

- 描画先を共有テクスチャへ写す GPU の時間
- 読み出しの経路の CPU の時間
- `HyperPlotView` の 1 回の tick の CPU の時間

あわせて、1 フレームの確保と、その出どころを数えた（設計 §7.2 の「確保」）。

## 条件

| 項目 | 値 |
| --- | --- |
| 機械 | 参照機（要件 §5）: Core i5-13400F、GeForce RTX 3060 Ti、Windows 11（10.0.26300） |
| ビルド | `samples/WpfPlot` の Release、JIT（WPF は NativeAOT に対応しない、`.cursor/rules/aot.mdc`）。.NET 10.0.14、x64 |
| 再現 | `dotnet run --project samples/WpfPlot -c Release -- --measure`（この PR の作業ツリー） |
| 描画先 | 1,920 × 1,080、倍率 1 |
| 写すフレーム | 時系列のタブの仕様（1e7 点の 2 系列、time の x、`Theme.Light`）を、そのバックエンドの `PlotEngine` で描いた描画先。背景の色で塗っただけの描画先は使わない（GPU が圧縮しうるので、下の「写しの時間」） |
| GPU の時間 | 写しだけを入れたバックエンドのフレームの `LastFrameTime`（タイムスタンプのクエリ）。フレームごとに `TryTakeCompleted` が真になるまで待つ |
| CPU の時間 | `Stopwatch`。読み出しは、`Present` と、読めた `TryRead` の 1 回の和（読めるまでの待ちは入れない） |
| tick | 時系列のタブのビューを 1,920 × 1,080 画素の大きさにし、`CompositionTarget.Rendering` の先頭のハンドラで 1 画素パンし、tick のハンドラがすべて終わったところ（`Send` の優先度の操作）までの時間。ビューのハンドラは、計測のハンドラの後ろにつながる |
| 標本 | 各 330 回。最初の 30 回を捨てて 300 回。各標本で gen 0 の回収の回数を見た |
| 回 | 3 回（プロセスを 3 度） |

## 結果

中央値 / p95（ms）。

| 回 | 写し GPU（ハードウェア） | 写し GPU（WARP） | 読み出し CPU（ハードウェア） | 読み出し CPU（WARP） | エンジンのフレームだけ CPU | 写しと受け取り CPU | ビューの tick CPU |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 0.033 / 0.037 | 1.548 / 2.240 | 1.428 / 2.105 | 1.410 / 1.931 | 2.612 / 3.414 | 0.327 / 0.518 | 2.509 / 3.406 |
| 2 | 0.034 / 0.042 | 1.296 / 1.860 | 1.480 / 2.184 | 1.144 / 1.638 | 2.425 / 3.088 | 0.293 / 0.410 | 2.716 / 3.934 |
| 3 | 0.033 / 0.034 | 1.273 / 2.035 | 1.426 / 2.148 | 1.139 / 1.563 | 2.733 / 3.728 | 0.339 / 0.515 | 2.528 / 3.280 |

- **写しの時間**: ハードウェアの 0.033 ms は、8.3 MB を読んで書く（16.6 MB）と約 500 GB/s で、RTX 3060 Ti のメモリの帯域（448 GB/s）を超える。描画先の大部分が背景の 1 色なので、GPU が圧縮した分である。確かめるため、乱数の色の画像（1,920 × 1,080 の RGBA のラスタを image の層で、軸もグリッドもなし）を描いた描画先を写すと、中央値 0.049 ms / p95 0.052 ms（約 340 GB/s、帯域の内）になった。どちらにしても、1 フレームの時間に比べて小さい
- **読み出しの時間**: 読めた `TryRead` を `Map` と行の写しに分けて測ると、`Map` は中央値 0.002 ms、行の写し（8.3 MB）は中央値 1.6〜1.7 ms で、時間のほとんどは行の写しである。背景の色で塗っただけの描画先で先に測ったときは、全体が中央値 0.6〜0.75 ms だった。違いは行の写しの速さ（約 5〜14 GB/s）の違いで、その原因は分けていない
- **tick の内訳**: ビューの tick（中央値 2.5〜2.7 ms）は、エンジンのフレーム（同じ仕様と大きさを WPF なしで、中央値 2.4〜2.7 ms）と、写しと受け取り（中央値 0.29〜0.34 ms）と、`D3DImage` の更新からなる。エンジンのフレームは、全体表示の 1e7 点の 2 系列を毎フレーム M4 で引くもので、行 I1a の計測のホイールのフレーム（全体表示に近い広い範囲で遅い、`docs/benchmarks/i1a-interaction.md`）と同じ形である（1 系列を画素列の範囲で分けるかは設計 §5.5.1 の未決）。要件 P-1（p95 8 ms 以下）は、tick の p95（3.3〜3.9 ms）でも下回る
- **最大**: エンジンのフレームだけで 7.2〜12.4 ms、読み出しで 6.1〜6.6 ms、tick で 3.9〜4.9 ms。どの最大の標本でも、その間に gen 0 の回収はなかった（GC ではない）。それより先の原因は分けていない

## 確保

テスト（`tests/HyperPlot.Wpf.Tests`、デバッグのビルド、階層化コンパイルなし）で、温まった後に 20 フレームずつ、1 画素ずつパンしながら数えた。

- **HyperPlot のコード**: エンジンの描画、写し、受け取り、読み出しは、WPF のない STA のスレッドで 0 B（`SurfaceTests.HostFrame_AllocatesNothingOnceWarm`、WARP）
- **WPF の API**: ビューのフレームを段ごとに数えると、確保は WPF の呼び出しの中だけにあった
  - `D3DImage.Lock` が 1 回 32 B
  - `D3DImage.SetBackBuffer` が約 40 B（2 枚を交互に渡すので、受け取るたびに呼ぶ）
  - 読み出しの経路では、`WriteableBitmap.Lock` が 1 回 42 B
  - `AddDirtyRect` と `Unlock` は 0 B
- **WPF のスレッドで数えられる分**: WPF のウィンドウのあるスレッドでは、エンジンの描画の中で、20 フレームに 0〜350 B が数えられた。同じエンジンを同じ仕様で、WPF のない STA のスレッドで回すと、2 回目からは 0 B だった。その間に dispatcher の操作は走っていない（`Dispatcher.Hooks` で数えた）
- **tick へのつなぎ**: `CompositionTarget.Rendering` へつなぐたびに WPF の処理の一覧を作り直して確保する（20 フレームで 1 万数千 B）。そこで、フレームが続く間はつないだままにした（設計 §7.2 の「フレームの時機」）

WPF の API の分と WPF のスレッドの分は、不変条件 3 の例外にした（オーナーの決定 2026-11-07、設計 §7.2 の「確保」）。
