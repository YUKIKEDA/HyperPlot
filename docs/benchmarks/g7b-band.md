# G7b: カテゴリの bar の計測

行 G7b（Issue #163）の計測の記録。設計書 §5.5.3 のカテゴリの x の bar で、ワーカーがカテゴリごとの最小・最大とその上のピラミッドを作る時間と、1 フレームの時間を測った。場面はロードマップの G7b の行のとおりで、要件 §5 の参照機で測った。

## 条件

| 項目 | 値 |
| --- | --- |
| 機械 | 参照機（要件 §5）: Core i5-13400F、GeForce RTX 3060 Ti、Windows 11 |
| ビルド | NativeAOT の Release（スクラッチのハーネス、この PR の作業ツリー。測った後に消した） |
| 描画先 | 1,920 × 1,080、ハードウェア、倍率 1 |
| ワーカー | `PlotWorkerPool.Shared`（15 スレッド）。プロセスの優先度は High、コアに固定しない |
| データ | `float` の Y を `Column.Wrap`、カテゴリの列を `Column.Categorical`（名前は "Category 000000" の形、与えた順）。行 i のカテゴリは、乗算のハッシュ (i · 2654435761) mod n で散らした。値はカテゴリごとの正弦波に一様な雑音 |
| 仕様 | `Bar(Cat("c"), Col<float>("y"))`、`Scale.Band()`、y は `WithDomain(−10, 10 + 0.1 · j)`（j = 0〜63 を順に。毎フレーム、スケールの段から記録まで走る） |
| ワーカーの最小・最大 | 1e8 行、カテゴリ 10 と 1e5、ガイドなし（`ShowAxes`・`ShowGrid` が偽、`Padding` 0）。Y の列を `Invalidate()` した直後の 1 フレーム（版が変わり、最小・最大とピラミッドを作り直して待つ）を 20 回、その間に普通のフレームを 100 回測った |
| 1 フレーム | 1e6 行、カテゴリ 50 と 1e5、`Theme.Light`（軸・グリッド・DirectWrite のラベルつき）。2 秒描いて温めた後、3,100 フレームのうち最初の 100 を捨てた 3,000 フレーム。100 フレームごとに `ReadPixels` で GPU を待つ（測る範囲の外） |
| 測る範囲 | CPU は `HeadlessRenderer.Render(PlotSpec)` の 1 回。GPU はフレームのタイムスタンプのクエリ（`IGpuBackend.LastFrameTime`）。確保は `GC.GetAllocatedBytesForCurrentThread()` を `Render` の前と後で読んだ差 |
| 回 | 場面の順に 1 回ずつを 3 回 |
| GPU のクロック | `nvidia-smi --query-gpu=timestamp,clocks.gr,pstate` を 150 ms ごとに記録した（下） |

## 結果

中央値 / p95（µs）。各欄は 1 回目、2 回目、3 回目。

### ワーカーの最小・最大（1e8 行）

| カテゴリ | 作り直すフレーム | 普通のフレーム |
| --- | --- | --- |
| 10 | 65,431 / 70,643、66,952 / 70,070、64,396 / 68,030 | 39 / 130、48 / 159、34 / 111 |
| 1e5 | 187,281 / 203,128、212,697 / 241,734、169,974 / 184,293 | 926 / 1,520、917 / 1,524、906 / 1,530 |

- 作り直すフレームから普通のフレームを引いた分が、最小・最大とピラミッドを作る時間である。10 カテゴリで約 65 ms、1e8 行を 1 秒に約 15 億行。1 行に Y の 4 B とカテゴリの番号の 4 B を読むので、約 12 GB/s になる
- **1e5 カテゴリが約 3 倍かかる理由**: ワーカーはチャンク（2^20 行）ごとに、カテゴリの数の長さの最小と最大の作業用の配列（1e5 カテゴリで 2 本で 1.6 MB）を持ち、行ごとにそのカテゴリの位置を読み書きする。行のカテゴリを散らしたこの場面では、読み書きが配列の中を飛び、コアの L2（1.25 MB）に収まらない。同じ 1e5 カテゴリで、行をカテゴリの順に並べる（行 i のカテゴリを ⌊i · n / 1e8⌋ にする）と、3 回とも 58 ms だった（58,061、58,098、57,871 µs）。チャンクの結果を合わせる段（ロックの中で 1e5 カテゴリを 96 チャンク分）とピラミッドは、どちらの並びでも同じだけ働くので、差は作業用の配列への飛び飛びの読み書きである
- 1e5 カテゴリの普通のフレーム（約 0.9 ms）は、band が 1 画素より狭いので画素列ごとにまとめる道（§5.5.3）で、1,920 画素列ごとに最小と最大のピラミッドへ 1 回ずつ問い合わせる。ピラミッドの最下段のバケットは 64 要素なので、1 列の約 52 カテゴリはバケットの中の元の値を順に読む。同じ道で、カテゴリが 2,000・5,000・20,000 のフレームは 359・366・459 µs（中央値、行をカテゴリの順に並べた 1 回ずつ）で、1 列のカテゴリの数とともに伸びる。2,000 カテゴリ（1 列に約 1 カテゴリ）の約 360 µs が、3,840 回の問い合わせと矩形の記録の固定分である

### 1 フレーム（1e6 行、ガイドつき）

| カテゴリ | CPU | GPU |
| --- | --- | --- |
| 50 | 175 / 222、178 / 226、181 / 234 | 176 / 187、176 / 187、176 / 187 |
| 1e5 | 1,120 / 1,238、1,061 / 1,218、1,104 / 1,246 | 352 / 377、345 / 369、353 / 375 |

- **CPU**: 1e5 カテゴリは、上の画素列ごとの道（約 0.9 ms）に、軸とグリッドが加わる。軸のラベルは 21 個で、測ったラベルは整形のキャッシュに入っており、温まった後は測らない。この計測は、ラベルの間の 0.5 em の下限（PR #164 のレビュー）を入れる前のもので、そのときは隣のラベルが接して並んだ。下限で k が増えてラベルは減るが、温まった後は測らないので、変わるのは軸のラベルと目盛りとグリッドの記録の数だけである（測り直していない）
- **GPU のクロック**: 50 カテゴリの回は、3 回ともすべての標本が P0（1,965 MHz）だった。1e5 カテゴリの回は、回の時間の 6〜8 割が P3（1,140〜1,275 MHz）、残りが P0（1,305〜1,665 MHz）だった。フレームの CPU の時間が GPU の仕事より長く、GPU が休むためである。温めずに 500 フレームを測った前の回では、1e5 カテゴリの回の標本はすべて P0（1,665〜1,965 MHz）で、GPU は 228 / 236、238 / 246、227 / 235 µs だった（50 カテゴリの回はその時 P8 の 210 MHz から上がる途中で、使わない）。1e5 カテゴリの GPU の時間は、矩形が多い（最大で画素列の 2 倍の 3,840）分だけ 50 カテゴリより長い
- **転送**: 1 フレームに GPU へ送る矩形は、1e5 カテゴリで画素列の 2 倍以下（3,840 × 32 B = 123 KB 以下）、50 カテゴリで 100 本。どれも画素とカテゴリの数のうち小さい方で抑えられ、行の数によらない（要件 R-1）
- **確保**: 捨てたフレームの後、6 回の 3,000 フレームのどれも 0 バイト

## NativeAOT

| サンプル | main（`de59e97`） | この PR |
| --- | --- | --- |
| `HelloPlot` | 1,881,088 B | 1,881,088 B（±0） |
| `SpecPlot` | 2,362,880 B | 2,401,280 B（+38,400 B） |

どちらも警告 0。`HelloPlot` と `SpecPlot`（ハードウェア、4 枚）の PNG は、main のものと画素まで同じだった（`cmp` でバイトまで一致）。`HelloPlot` は仕様を使わないので変わらない。`SpecPlot` の増分を ILC の map ファイル（`IlcGenerateMapFile`）の節の長さで名前ごとに分けると（PR #164 のレビュー）、Core の節が +34,126 B、メタデータが +399 B、ランタイムと BCL が +888 B で、D3D11 とサンプルの節は変わらない（節の和は +36,784 B、ファイルの増分との差 +1,616 B は PE の節の揃え）。Core の増分の多くは新しい型のコードではない。`SpecPlot` の列は `float` と `long` だけだが、カテゴリの bar が最小・最大の `double[]` を `Column.Wrap` で包んでピラミッドを作るので、`Column<double>` と `MinMaxPyramid<double>` が生き、`double` の列に付く総称の実体化が入る: `MinMaxPyramid<double>` +10,773 B、M4 の `Extract`・`Run` の `double` の組 +9,906 B、ピラミッドとチャンクの統計のカーネル +5,610 B、`Column<double>` +2,032 B など。新しい型では `BandTicks` が +1,351 B（`SpecPlot` はカテゴリの列を作らないので、`CategoricalColumn` の多くと `CategoryExtremesWork` は刈り込まれる）、変えた型は `PlotPlan` +870 B、`LayerPlan` +377 B、`PlotWorkerPool` +997 B など（減った型の和は −1,923 B）である。
