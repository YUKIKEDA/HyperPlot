# G7c: 色のチャネルの計測

行 G7c（Issue #172）の計測の記録。設計書 §5.5.3 のカテゴリで分けた層の道（区間の道と集める道）と、§4.1 の要素ごとの連続の色を測った。場面はロードマップの G7c の行のとおりで、要件 §5 の参照機で測った。

## 条件

| 項目 | 値 |
| --- | --- |
| 機械 | 参照機（要件 §5）: Core i5-13400F、GeForce RTX 3060 Ti、Windows 11 |
| ビルド | NativeAOT の Release（スクラッチのハーネス、この PR の作業ツリー。測った後に消した） |
| 描画先 | 1,920 × 1,080、ハードウェア、倍率 1 |
| ワーカー | `PlotWorkerPool.Shared`（15 スレッド）。プロセスの優先度は High、コアに固定しない |
| データ | 1e8 行。X は `Column.Uniform(0, 1, 1e8)`、Y は `float` の `Column.Wrap`（カテゴリ c の正弦波 + c + 雑音、シード 5）、カテゴリは `Column.Categorical`（名前 "s000" など、与えた順）。混ざる場合は行 i のカテゴリを乗算のハッシュ (i · 2654435761) mod n、区間の場合は ⌊i · n / 1e8⌋ にした |
| 分けるワーカーの仕事 | 8 カテゴリの線を `ColorBy` で分け、軸とグリッドを隠す。新しいカテゴリの列で最初に描いた時間（区間を調べる仕事、集める仕事、ピラミッド、1 フレーム）と、Y を `Invalidate` した直後の描画（10 回）、その間の普通のフレーム（50 回） |
| 1 フレーム（線） | 混ざる 8・16・32・64・256 カテゴリの線を `ColorBy` で分け、`Theme.Light`（凡例にカテゴリの行）。x の domain を毎フレーム、幅 9e7 のまま 1e5 ずつずらす（64 通り、M4 を引き直す）。2 秒描いて温めた後、測るフレームの 1 割（最大 50）を捨てた |
| 1 フレーム（rect） | 512 × 256 の格子の rect 131,072 個を sin · cos の値で `ColorBy`（viridis の sequential、カラーバーつき）。y の domain を毎フレーム変える（64 通り、記録をやり直す）。比べる場面は同じ rect を定数の `Fill` で塗ったもの |

## 結果

中央値 / p95（µs）。各欄は 1 回目、2 回目、3 回目。

### 分けるワーカーの仕事（1e8 行、8 カテゴリ）

| 道 | 最初の描画 | Y を `Invalidate` した後 | 普通のフレーム |
| --- | --- | --- | --- |
| 区間 | 44,829、46,532、43,475 | 15,466 / 18,236、14,464 / 15,067、13,949 / 14,945 | 733 / 1,102、635 / 979、711 / 957 |
| 混ざり | 253,336、252,919、270,970 | 171,363 / 176,381、165,386 / 171,977、173,360 / 181,955 | 5,016 / 5,911、4,866 / 5,601、5,024 / 5,706 |

- **区間の道**: `Invalidate` の後は Y のピラミッドを作り直すだけで、約 14 ms（1e8 行の `float`、行 B1 のピラミッドの速さ）。最初の描画は、それに区間を調べる仕事（番号 1e8 個、400 MB を 1 度なめる）が加わり、差の約 30 ms がその仕事である。区間を調べる仕事は列ごとに 1 回で、2 度目の描画からは走らない
- **集める道**: `Invalidate` の後は、8 カテゴリの X（`double`）と Y（`float`）を 1e8 行ぶん集め直し（1.2 GB を書く）、集めた Y の 8 本のピラミッドを作り直す。ピラミッドは合わせて区間の道と同じ行数（約 14 ms）なので、集める仕事は約 155 ms である。最初の描画は、それに区間を調べる仕事（約 30 ms）と、集める列の 1.2 GB のネイティブのメモリを最初に書くときのページの割り当てが加わる
- **集める道のメモリ**: 1e8 行 × (X の 8 B + Y の 4 B) = 1.2 GB と、集めた Y のピラミッド（§3.3 の約 4.1 %、約 16 MB）。設計 §5.5.3 の式どおり、データと同じ桁である
- **普通のフレーム**: どちらも y の domain を変えて M4 を引き直す。区間の道は 0.7 ms で、分けない 1e8 行の線と同じ桁である。8 系列はそれぞれ x の 1/8 の区間にだけ行を持つので、M4 が点を出す画素列は 8 系列で合わせて約 1,873 列になる。混ざりの道は 8 系列がどれも全幅に行を持ち、M4 が 8 × 1,873 列で働くので、約 7 倍の 5 ms になる（下の線の場面の 8 カテゴリと同じ）

### 1 フレーム（分けた線、混ざる 1e8 行）

| カテゴリ | CPU | GPU |
| --- | --- | --- |
| 8 | 4,933 / 5,381、4,866 / 5,125、4,963 / 5,453 | 1,085 / 2,607、1,187 / 1,786、1,160 / 2,051 |
| 16 | 6,226 / 8,892、6,153 / 8,809 | 1,679 / 2,326、1,635 / 2,771 |
| 32 | 10,412 / 12,625、10,568 / 12,707、10,467 / 13,245 | 3,374 / 4,960、3,168 / 4,810、3,375 / 4,807 |
| 64 | 18,282 / 20,045 | 6,046 / 8,836 |
| 256 | 49,040 / 51,845、49,873 / 54,990、49,852 / 53,849 | 16,744 / 18,163、15,234 / 18,091、16,076 / 18,741 |

- **系列の数に比例する**: CPU の中央値は、8 から 256 カテゴリまで、系列 1 本あたり約 0.17 ms 増える（64 から 256 で 30.8 ms / 192）。1 系列ごとに M4 が 1,873 画素列を引き（4W 点）、折れ線を記録するので、仕事は系列の数 × 画素である（設計 §4.1、不変条件 2）
- **要件 P-1 との関係**: P-1（1 系列で、CPU と GPU がそれぞれ p95 で 8 ms 以下）に収まるのは、この場面で約 12 系列までである（16 カテゴリで p95 8.8 ms）。P-1 は 1 系列の要件なので、分けた層の上限（256）は変えず、この費用を XML と設計 §4.1 に書いた（オーナーの決定、PR の本文）
- **転送**: 256 カテゴリでは、1 フレームの線分が約 200 万（256 × 4 × 1,873）で、約 39 MB を GPU へ送る（設計 §4.1 の見込みどおり）
- **確保**: 3 回の 8 カテゴリと 16・32・64 カテゴリの回は、1 回の走りに 0 B か 56 B。256 カテゴリは 1 回の走りに 680 B（200 フレーム）と 736 B（400 フレーム）で、フレームの数によらない。どちらも 1 フレームごとの確保ではない（行 G10 の記録の Issue #141 の 56 B と同じ桁で、原因は分けていない）。最初の計測では、仕様を毎フレーム作り直すと分けた層が子のノードを作り直し、1 系列あたり約 350 B を確保していた。見た目が同じノードなら作り直さないよう直し、テスト（`ColorChannelTests.Warm_AllocatesNothing`）に新しいノードの描き直しを足した

## NativeAOT

| サンプル | main（`657e0e3`） | この PR |
| --- | --- | --- |
| `HelloPlot` | 1,881,088 B | 1,882,112 B（+1,024 B） |
| `SpecPlot` | 2,401,280 B | 2,650,112 B（+248,832 B） |

どちらも警告 0。`HelloPlot` と `SpecPlot`（ハードウェア、4 枚）の PNG は、main のものと `cmp` でバイトまで同じだった。

ILC の map ファイル（`IlcGenerateMapFile`）の節の長さを名前で分けると、`SpecPlot` の増分（節の和 +239,672 B、残りは PE の揃え）は次のとおり。`SpecPlot` は色のチャネルを使わないが、分けた層の道はコンパイルの中で列の種類によって選ばれるので、ILC は刈り込めない。

- **集める道の総称の実体化、約 121 KB**: 集める列はソースの列と同じ要素型（`float`・`double`・`int`・`long`・`byte`）で作るので（設計 §5.5.3）、`SpecPlot` が使わない型の M4（+73,390 B）、`MinMaxPyramid<byte・long・int>`（+28,685 B）、`Column<byte・long・int>`（+6,687 B）、M4 の仕事（+8,530 B）、統計とピラミッドのカーネル（+3,903 B）が入る
- **色の写像の表、+17,016 B**: viridis など 5 つの 768 個の `int` と、ColorBrewer の 7 つの `double`。最初は matplotlib の数を文字列で持ち、起動のときに解析していたので、固定の文字列が +81,776 B と数の解析のコードが入り、`SpecPlot` は +318,464 B だった。表にして約 70 KB 縮めた（値はテストで matplotlib とバイトまで一致する）
- **分けた層・凡例・検査などのコード**: `SplitPlan` +13,411 B、`LayerPlan` +5,492 B、`PlotGuides` +4,615 B、`PlotPlan` +3,650 B、`PlotWorkerPool` +3,707 B、`M4Batch` +4,194 B など
- **ランタイムと BCL、メタデータ**: +12,185 B と +2,869 B（`ArrayPool<int>` の実体化、型の表など）

集めた列を要素型によらず `double` で持てば、総称の実体化の多く（約 120 KB）は入らないが、集めた `float` の Y のメモリが倍（4 B から 8 B）になる。設計の決定（データと同じ型、メモリはデータと同じ桁）のままにした（PR の本文で確認）。
