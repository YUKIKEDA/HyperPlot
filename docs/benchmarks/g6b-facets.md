# G6b: ファセットの計測

行 G6b（Issue #242）の計測の記録。1e9 点の系列を 8 カテゴリで分けた wrap を、同じ系列の 1 パネルと比べ、作る時間と 1 フレームの CPU と GPU の時間と確保を、要件 P-1（1 フレームの p95 が 8 ms 以下）と照らした。カテゴリが行に混ざる場合は、集める列が 1e9 行で約 12 GB になるので 1e8 点で測った（設計 §4.6、Issue #238 の Decision 12）。要件 §5 の参照機で測った。

## 条件

| 項目 | 値 |
| --- | --- |
| 機械 | 参照機（要件 §5）: Core i5-13400F、GeForce RTX 3060 Ti、Windows 11 |
| ビルド | NativeAOT の Release（スクラッチのハーネス、この PR の作業ツリー。測った後にデータと一緒に消した） |
| 描画先 | 1,920 × 1,080、ハードウェア、倍率 1、`Theme.Light`（軸・グリッド・軸のタイトル・タイトルあり） |
| ワーカー | `PlotWorkerPool.Shared`（15 スレッド）。プロセスの優先度は High |
| データ | y は `float` のメモリマップのファイル（`samples/Shared/WalkFile.cs` のランダムウォーク、1e9 点で 4 GB）、x は `UniformColumn`（0 から 1 刻み）、カテゴリは 8 つ（A〜H） |
| 区間に並ぶ場合 | 1e9 点。行 i のカテゴリは ⌊8i / n⌋（8 つの区間） |
| 混ざる場合 | 1e8 点。行 i のカテゴリは i mod 8（どのカテゴリも区間に並ばず、パネルごとに x と y を集める） |
| 場面 | **1 パネル**: line 1 本。**wrap**: 同じ line を `FacetWrap(region, columns: 3)`（3 列 3 行に 8 パネル、`Fixed`） |
| 作る時間 | 最初の `Render` の 1 回（区間の表を調べる仕事、集める仕事、ピラミッド、学習、配置、取り出し、描画） |
| 測る範囲 | 2 秒描いて温めた後の 300 フレーム。y の domain を毎フレーム変える（前もって作った 7 つの仕様を順に。仕様はどれも別々に作り、ノードはフレームごとに新しい）。x は全体を表示する。CPU は `HeadlessRenderer.Render` の 1 回、GPU はフレームのタイムスタンプのクエリ、確保は `Render` の前後の `GC.GetAllocatedBytesForCurrentThread()` の差の和 |
| 回 | 場面の順に 1 回ずつを 3 回 |

## 結果

作る時間は ms、フレームは中央値 / p95（µs）。各欄は 1 回目、2 回目、3 回目。

### 区間に並ぶ 1e9 点

| 場面 | 作る時間 | フレームの CPU | フレームの GPU | 確保（300 フレーム） |
| --- | --- | --- | --- | --- |
| 1 パネル | 2,740、138、138 | 6,180 / 8,850、3,397 / 4,917、4,307 / 5,225 | 1,457 / 3,303、617 / 679、666 / 771 | 0 B、0 B、0 B |
| wrap | 339、341、347 | 856 / 1,069、695 / 794、820 / 979 | 278 / 319、275 / 316、280 / 322 | 56 B、56 B、0 B |

### 混ざる 1e8 点

| 場面 | 作る時間 | フレームの CPU | フレームの GPU | 確保（300 フレーム） |
| --- | --- | --- | --- | --- |
| 1 パネル | 27、25、27 | 1,971 / 2,508、2,007 / 2,511、1,950 / 2,594 | 225 / 554、224 / 238、224 / 240 | 0 B、0 B、0 B |
| wrap | 253、272、268 | 2,516 / 2,806、2,504 / 2,694、2,568 / 2,903 | 771 / 834、750 / 822、558 / 806 | 56 B、0 B、0 B |

- **作る時間（区間）**: wrap は 1 パネルより約 200 ms 長い。カテゴリの列の番号 1e9 個をワーカーが 1 度なめて、カテゴリごとの区間を調べる仕事（§5.5.3、列ごとに 1 回で、列が持つ）の分である。ピラミッドは列の全体の 1 つを全パネルで共有し、写さない。1 回目の 1 パネルの 2,740 ms は、y のファイルがまだページキャッシュに載っていなかった分を含む（2 回目からは 138 ms）
- **作る時間（混ざる）**: wrap は 1 パネルより約 240 ms 長い。区間を調べる仕事に加え、1e8 行の x と y をパネルごとの列に集める仕事（約 1.2 GB を書く）と、集めた y の 8 つのピラミッドを作る分である
- **フレーム（区間）**: wrap は 1 パネルより速い。`Fixed` の x では各パネルが x の全体を表示し、そのパネルの区間は x の 1/8 しか占めないので、M4 が引く画素列は全パネルで約 8 × 75 列になり、1 パネルの約 1,840 列より少ない。GPU も、描く線の頂点がその分少ない
- **フレーム（混ざる）**: wrap は 1 パネルより CPU が約 0.5 ms、GPU が約 0.3〜0.5 ms 長い。どのカテゴリも x の全体に散るので、8 パネルがそれぞれパネルの幅の約 600 列を引き、全体で約 4,800 列になる。32 の M4 の組（8 パネル × 4 つのスケールの組）は 1 回の取り出しで並んで走る（行 G6a の `ExtractTogether`）
- **P-1 との比べ**: wrap はどの回も p95 が 8 ms を十分に下回る。1 パネルの 1 回目の p95 8.85 ms は、ページキャッシュが温まる前の回である（2 回目からは 4.9〜5.2 ms）
- **確保**: wrap で、ある回に 56 B が 1 度だけ出る。M4 の組の待ち（`M4Batch.Wait`、組ごとのオブジェクトの `Monitor.Wait`）が、その組で初めて実際に待ったときに、NativeAOT の Monitor が待ちのための物を 1 度だけ作る分である。wrap は組が 32 あり、温める 2 秒の間に一度も待たなかった組があると、計測の間に出る。3,000 フレームでも 56 B か 0 B で、フレームの数で増えない（フレームごとの確保ではない）。フレームごとに新しいノードで仕様を作っても、同じ値のファセットは並べ直さない（最初の実装は並べ直して 1 フレーム 272 B を確保していた。`FacetTests.Warm_AllocatesNothing` が今は新しいノードで確かめる）
