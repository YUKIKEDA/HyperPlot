# I4b: 計測の計測

行 I4b（Issue #394）の計測の記録。設計 §9 の「計測（行 I4b）」の項のとおり、3 つを測った。統計の問い合わせは要件 P-5（p99 1 ms 以下）、範囲の計測を置いたマウスだけのフレームは要件 P-6（p95 2 ms 以下）、バケットの和を足したピラミッドの構築は main と比べる。

## 条件

| 項目 | 値 |
| --- | --- |
| 機械 | 参照機（要件 §5）: Core i5-13400F（16 スレッド）、GeForce RTX 3060 Ti、Windows 11 |
| ビルド | NativeAOT の Release。統計とフレームはスクラッチのハーネス（公開の API だけを使う）、構築は `benchmarks/HyperPlot.DataPath` の `build` の場面を、この PR と main の両方で発行した。測った後にデータと一緒に消した |
| 描画先 | 1,920 × 1,080、ハードウェア、倍率 1、`Theme.Light` |
| データ | 1e9 点の `float` の線が 1 本と 4 本（`samples/Shared/WalkFile.cs` のランダムウォーク、系列ごとに 4 GB のメモリマップのファイル、ページキャッシュに載っている）。x は `UniformColumn`。構築は行 B1 の材料（`HyperPlot.DataPath generate`） |

| マウスだけのフレーム | x の中央の半分（[2.5e8, 7.5e8]）の範囲の計測を置き、行 I2b のホバーの台本（330 フレーム）を 2 度流して、2 度目の最初の 30 を除く 300 フレーム。CPU 時間は移動と `RenderFrame`、GPU 時間は `LastFrameTime` |

## 計測で見つけて直したこと

最初の計測では、統計の問い合わせの p99 が 1 本で 0.50〜1.60 ms、4 本で 5.4〜6.7 ms あり、要件 P-5 を超えた。範囲は平均でおよそ 300 チャンクにまたがり、2 つの理由で、範囲にまるごと含まれるチャンクごとの仕事が大きかった。

- min / max の問い合わせ（`MinMaxPyramid.Query`）が、チャンクの統計を使わず、チャンクごとにピラミッドを降りていた
- 和と件数の足し上げが、もう 1 度チャンクを回っていた

まるごと含まれるチャンクは、チャンクの統計（件数・和・min・max）を 1 度読むだけにし、端の 2 チャンクだけをピラミッドとバケットの和で求める 1 つの走査（`MinMaxPyramid.Summary`）に直した。直した後は p99 が 1 本で 0.033 ms 以下、4 本で 0.27 ms 以下になった（上の表）。直す前と後で範囲は同じで、時間がチャンクの数に比例していた部分が消えたことが、原因の確かめになった。
