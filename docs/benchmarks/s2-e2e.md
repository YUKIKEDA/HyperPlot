# S2: End-to-end のフレームと P-1

行 S2（Issue #62）の計測の記録。設計書 §9 の End-to-end（`benchmarks/HyperPlot.E2E`）で、要件 P-1 を要件 §5 の参照機で測った。

結論: 1 系列で、フレームの CPU 時間の p95 は 4.4〜5.8 ms、GPU 時間の p95 は 0.18 ms で、どちらも 8 ms 以下。P-1 を満たす。

## 場面

- 1e9 点の `float` のメモリマップの列（`samples/Shared/WalkFile.cs` のシードからのランダムウォーク）、X は `UniformColumn`。ピラミッドは構築済み、ファイルはページキャッシュに載った状態
- 1 フレームは `samples/BillionSeries` と同じ手順: `PlotWorkerPool.Extract`（`M4Batch`）→ 系列ごとの Y の範囲（`GetMinMax`）→ 画素へ写して `RenderList` に記録 → `Clear` と `Draw`（1 つの `FrameScope` の中）。描画先は 1,920 × 1,080、プロットの領域は 1,840 × 1,020、格子の線 49 本
- 台本: 全体から中央へ 1 フレームに 2^(1/8) 倍ずつ、100 万分の 1（1,000 点）まで拡大し、2 倍ごとにスパンの 1/20 ずつ 10 フレーム右へパンし、同じ刻みで全体へ戻る。531 フレーム
- 台本を 3 回続けて流し、最初の 30 フレームを捨てた 1,563 フレームの p50・p95・最大を取る
- NativeAOT Release（`HyperPlot.E2E.exe` 1,780,736 バイト、発行の警告 0）、参照機のハードウェア、優先度は高。ワーカーはコアに固定せず OS に任せる（`bench.mdc`）
- GPU のクロックは `nvidia-smi --query-gpu=timestamp,clocks.gr,pstate -lms 100` で記録し、フレームを流した時刻の範囲のサンプルだけを数える

## 結果

1 → 4 → 16 系列 → 1 → 4 → 16 系列の順に 1 回ずつ流した。各欄は 1 回目 / 2 回目の値。

| 系列 | CPU の合計の p95 | うち抽出の p95 | GPU の p95 | フレームの間のクロックの段 | 温まった後の確保 |
| --- | --- | --- | --- | --- | --- |
| 1（P-1） | 5.77 / 4.43 ms | 5.42 / 4.20 ms | 0.176 / 0.175 ms | P0 30 / P0 18・P8 3 | 0 / 0 B |
| 4（参考） | 5.28 / 6.51 ms | 4.82 / 5.93 ms | 0.407 / 0.430 ms | P0 29・P5 2 / P0 28・P3 7・P8 2 | 56 / 56 B |
| 16（参考） | 11.92 / 13.07 ms | 10.06 / 10.93 ms | 1.84 / 2.21 ms | P0 62・P3 4・P5 5 / P0 62・P3 5・P5 9・P8 3 | 56 / 0 B |

- 1 系列の CPU の p50 は 1.22 / 0.92 ms。段ごとの p95 は、Y の範囲 0.01 ms 以下、記録 0.06 ms、描画の命令 0.23 ms 前後で、残りは抽出
- 1 系列の 1 回目は、フレームの間ずっと P0（1,665 MHz）だった。2 回目の GPU の p95 も同じ 0.175 ms なので、P8 のサンプル 3 つは流し始めと終わりの境目のものと読む
- 同じ日の前の 2 回（台本 3 回分ずつ、時刻の記録なし）の 1 系列の CPU の p95 は 4.01・4.43 ms と 4.57・4.93 ms。回によって 4.0〜5.8 ms の幅がある
- 予想（Issue #62）との比べ: 1 系列の CPU の p95 は現実的な範囲（3〜7 ms）の内。GPU の p95 0.18 ms は現実的な範囲（0.05〜0.2 ms）の内。16 系列の CPU の p95 12〜13 ms は現実的な範囲（6〜12 ms）の上の端を少し超え、最悪（30 ms）の内

### p95 を決めるのは広い表示の抽出

表示の幅で分けた、1 系列の 2 回目のフレームの時間（ms）:

| 表示の点の数 | フレーム | 抽出の p50 | 抽出の p95 | 合計の p95 |
| --- | --- | --- | --- | --- |
| 1e8〜1e9 | 252 | 3.55 | 5.04 | 5.29 |
| 1e7〜1e8 | 252 | 1.86 | 2.65 | 2.88 |
| 1e6〜1e7 | 246 | 1.13 | 1.86 | 2.09 |
| 1e5〜1e6 | 282 | 0.54 | 0.84 | 1.01 |
| 1e4〜1e5 | 246 | 0.29 | 0.43 | 0.59 |
| 1e3〜1e4 | 252 | 0.07 | 0.18 | 0.33 |
| 1e3 未満（100 万分の 1 の拡大） | 33 | 0.06 | 0.09 | 0.23 |

抽出の時間は、表示の幅とともに増える。台本の約 1/6 が 1e8 点より広い表示で、その抽出が p95 を決める。1 回目（p95 が遅い回）では、この区分の抽出の p50 が 4.83 ms、p95 が 6.98 ms で、8 ms を超えたフレームは 1,563 のうち 2 つ。この抽出の中身は、CPU のプロファイルで分けた（次の節）。

### 広い表示の抽出の中身（CPU のプロファイル）

`HyperPlot.E2E --series 1 --rounds 30 --min-span 1e8`（1e8 点より広い 94 の表示だけを 30 回、2,820 フレーム）を、NativeAOT Release（コミット 75dda96）で、Visual Studio のコレクタ（4,000 Hz）で標本を取り、`xperf` で読んだ（`.agents/skills/cpu-profile`）。プロセスの標本は 72,733 で、うちピラミッドの構築（ワーカー）が 20,244、フレームの抽出（呼び出し側のスレッドの `M4.Run`）が 38,507（約 9.6 s、1 フレーム約 3.4 ms で、この区分の p50 と合う）。

`M4.Run` の 97%（37,441）は、画素列ごとの区間の min / max（`MinMaxPyramid.Query` → `QueryChunk`）だった。境界の要素を読む `Column.GetValue` と、出力を書く部分は 1% に満たない。`QueryChunk`（36,931 = 100%）の内訳:

| 関数 | 割合 | していること |
| --- | --- | --- |
| `Locate` + `FirstEqual` | 45.7% | 最小と最大が最初に現れる位置を、水準を下って探し、最後に生の値（最大 64 個）をスカラーのループで探す |
| `QueryChunk` 自身 | 19.0% | 区間を、両端の生の値の並びと、その間のいちばん粗いバケットで覆う |
| `NumberOf` | 13.7% | バケットの NaN でない値の数を読む |
| `PyramidKernel.MinMaxFloating` | 12.3% | 両端の生の値の並び（各 63 個まで）の min / max（SIMD） |
| `NextPiece` | 6.1% | 次に覆う並びかバケットを決める |
| `Mins` / `Maxs` | 3.0% | 水準の min / max の配列を取る |

`QueryChunk` の下にカーネル（ページフォールト）の標本は 1 つだけで、ファイルはページキャッシュに載っていた。広い表示の時間は、ページを読む時間でなく、ピラミッドを引く CPU の時間である。生の値を読むのは `FirstEqual` と `MinMaxFloating` で、合わせて約 3 割。

### 1 系列を画素列の範囲で分けるか（設計 §5.5.1）

分けない（オーナーの判断 2026-10-29、`design-decisions.md`）。1 系列では呼び出し側のスレッドが 1 つの仕事を受け持ち、ワーカーは空いているが、p95 は 8 ms に対して 2 ms 以上の余裕がある。分けると、広い表示の抽出が短くなる見込みはあるが、仕事の分け方と結果のつなぎ目の扱いが増える。P-1 の内なので、今は入れない。

### 4 系列と 16 系列

- 16 系列の CPU の p95 は 12〜13 ms で、8 ms を超える（参考で、目標はない）。1 回目の 1e8 点より広い表示の抽出が p50 9.0 ms、p95 14.3 ms で、記録の p50 も 1 ms 前後になる（16 本の M4 の点を写す）
- GPU の時間は系列とともに増える（1 系列 0.18 ms、16 系列 1.8〜2.2 ms）。系列ごとに Y の範囲が違うので、どの線も描画の領域全体にかかり、線ごとの 3 回の描画（R2）がそれぞれ領域全体を覆う

## 確保とメモリ

- 温まった後の確保は、6 回のうち 3 回が 56 バイト、3 回が 0 バイト。56 バイトは 1 回に 1 フレームだけ（例: 4 系列の 1 回目のフレーム 1,296）で、フレームの番号は回ごとに違う
- この 56 バイトは、`PlotWorkerPool` の `_gate`（`System.Threading.Lock`）で、スレッドが初めて待ったときに、NativeAOT のランタイムが待ちのイベントを作る分である。スクラッチのプログラム（NativeAOT）で、新しい `Lock` を別のスレッドが持っている間に `EnterScope` で待つと、待った側のスレッドで 5 回とも 56 バイトを数えた。1 つの `Lock` に 1 回だけで、2 回目からは 0 バイト。呼び出し側のスレッドが初めて待つのが温まった後になった回にだけ数えられる。`object` に `lock` をかけた場合は、初めて待ったときに 120 バイトだった（`M4Batch` の `_sync` がこれに当たる）。6 回とも、120 バイトのフレームはなかった
- プロセスで 1 回だけの確保なので、この 56 バイトは直さずに記録にとどめる（オーナーの判断、PR #63）
- メモリ: 1 系列で作業セット 4,015 MB、プライベート 243 MB。作業セットの 4 GB は、ページキャッシュに載ったファイルの写像のページ。16 系列で作業セット 63 GB、プライベート 2.76 GB。ファイルは 4 つ（`--files 4`）で、16 系列はそれぞれを 4 回ずつ写像するので、作業セットは 16 本分の写像の 64 GB 前後になる。プライベートは主にピラミッド（1 系列約 163 MB、B1）

## 再現の手順

```powershell
dotnet publish benchmarks/HyperPlot.E2E -c Release -r win-x64 -o .dev/e2e
.dev/e2e/HyperPlot.E2E.exe --dir <データのフォルダ> --series 1 --rounds 3 --csv <フレームごとの CSV>
nvidia-smi --query-gpu=timestamp,clocks.gr,pstate --format=csv,noheader -lms 100   # 別の端末で、流している間
# プロファイル: 広い表示だけを流し、cpu-profile のスキルの手順で VSDiagnostics の下で起動する
.dev/e2e/HyperPlot.E2E.exe --dir <データのフォルダ> --series 1 --rounds 30 --min-span 1e8
```

データのファイルは 1 系列 4 GB で、なければ最初の回に作る（`BillionSeries` と同じファイル）。計測の後に消す。
