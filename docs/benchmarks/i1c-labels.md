# I1c: ズーム中の新しい目盛りのラベルの確保

行 I1c（Issue #270）の計測の記録。ズームやパンで新しい目盛りのラベルが出続けるときの 1 フレームの確保を、行 I1c の前と後で比べた（設計 §4.6・§5.6、不変条件 3）。

## 条件

| 項目 | 値 |
| --- | --- |
| 機械 | 開発機（Windows 11）。WARP |
| 描画先 | 1,280 × 720、倍率 1、`Theme.Light` |
| データ | 1e5 点（前）と 1e4 点（後）の線。y の domain は [−5,000, 5,000] で固定 |
| 場面 | x の domain を毎フレーム 1,370 ずらし（[1,370 i, 1,370 i + 1,000]）、x のラベルがすべて新しくなる |
| 測る範囲 | 温まった後の連続するフレームの `GC.GetAllocatedBytesForCurrentThread()` の差の和を、フレームの数で割る。後の値は、確保が 0 になるまで慣らし（300 フレームを最大 4 回）、続く 300 フレーム（どれも初めての domain） |
| ビルド | Release（前、設計 PR #267 のスクラッチのテスト）、Debug と Release（後、`LabelAllocationTests`） |

## 結果

| 描き方 | 前（1 フレーム） | 後（300 フレーム） |
| --- | --- | --- |
| DirectWrite | 8.0 KB | 0 B |
| 偽の文字のバックエンド | 11.2 KB | 0 B |
| 偽の文字のバックエンド、利用者の書式 | — | 0 B |
| 偽の文字のバックエンド、time の軸（4,570 s ずつ） | — | 0 B（整形のキャッシュを先にいっぱいにした場合） |

- **前の内訳**: 新しいラベルごとに、文字列の表の `string`、整形のキャッシュの項目、`ShapedText` とその配列。DirectWrite の `Shape` だけで 7 文字のラベル 1 つに 480 B（`ShapedText` の配列を含む）
- **DirectWrite の残り**: `Shape` を使い回す `ShapedText` に書かせた後、1,000 個の新しいラベルの整形で 1 つ 0.6 B（集める `List` の伸び。温まれば 0）。描画の場面では 0 B
- **項目の場所**: 整形のキャッシュの項目は長さの違う文字列を順に運ぶ。はじめは配列を文字列の長さちょうどで作っていたので、短いラベルを持った項目が長いラベルを受けるたびに伸び、いっぱいのキャッシュでも 1 つの新しいラベルに 146 B 確保した。項目にはじめから 16 グリフと 2 行の場所を持たせて 0.2 B（1,000 個の平均）にした
- **time の軸**: 時と分のラベル（1,440 通り）は繰り返すので、ラベルだけでは整形のキャッシュがいっぱいにならず、新しい日付のラベルのたびに項目を 1 つ作る（568 B）。キャッシュがいっぱいなら 0 B。テストは、長く使った後と同じく、先に 8,192 個の別の文字列で満たしてから測る
