# G4: Geom の計測

行 G4（Issue #124）の計測の記録。設計書 §5.5.3 の Geom を、少ないデータ（要素ごとに描く道）と、画素列ごとにまとめる大きなデータで、1 フレームの CPU 時間を要件 §5 の参照機で測った。

## 条件

| 項目 | 値 |
| --- | --- |
| 機械 | 参照機（要件 §5）: Core i5-13400F、GeForce RTX 3060 Ti、Windows 11 |
| ビルド | NativeAOT の Release（スクラッチのハーネス、この PR の作業ツリー。測った後に消した） |
| 描画先 | 1,920 × 1,080、ハードウェア、倍率 1、ガイドなし（`ShowAxes`・`ShowGrid` が偽、`Padding` 0）、ワーカー 2 本 |
| データ | 等間隔の X、シードつきの正弦波と雑音の `float` の Y（band と errorbar は Y + 1 + 雑音を上に）。rule は 0 からの整数の保存された `double` の列 |
| 要素の数 | 1e3 と 1e7。segment と rect は上限（§5.5.3）があるので 1e3 と 131,072 |
| 測る範囲 | `HeadlessRenderer.Render(PlotSpec)` の 1 回（コンパイル・M4・記録・`Clear`・`Draw`）。毎フレーム新しい x の domain（データの 99〜100 % の 64 通り）で、M4 と記録をやり直す。600 フレームのうち最初の 100 を捨てた 500 フレーム。100 フレームごとに `ReadPixels` で GPU を待つ（測る範囲の外） |
| CPU | プロセスを固定しない回を 2 回と、論理プロセッサ 2 に固定して優先度 High の回を 1 回 |

## 結果

固定しない 2 回（中央値 / p95、µs）:

| Geom | 1e3（1 回目） | 1e3（2 回目） | 1e7・131,072（1 回目） | 1e7・131,072（2 回目） |
| --- | --- | --- | --- | --- |
| line（比べる基準） | 78 / 112 | 82 / 116 | 1,380 / 1,615 | 1,374 / 1,621 |
| step（Middle） | 98 / 118 | 89 / 128 | 1,495 / 1,739 | 1,413 / 1,631 |
| area（縁つき） | 187 / 236 | 188 / 229 | 1,642 / 1,908 | 1,585 / 1,833 |
| band | 228 / 265 | 208 / 273 | 1,862 / 2,104 | 1,919 / 2,294 |
| bar | 104 / 128 | 104 / 122 | 1,415 / 1,669 | 1,370 / 1,625 |
| errorbar | 134 / 171 | 148 / 203 | 1,664 / 1,949 | 1,599 / 1,868 |
| 縦の rule | 46 / 107 | 46 / 77 | 782 / 994 | 777 / 915 |
| 横の rule | 45 / 69 | 46 / 123 | 425 / 499 | 411 / 539 |
| segment | 45 / 62 | 60 / 70 | 2,775 / 3,166 | 2,729 / 3,041 |
| rect | 51 / 61 | 57 / 88 | 4,041 / 4,579 | 4,065 / 4,574 |

固定した 1 回（中央値 / p95、µs）: 1e3 は 362〜560（どれも固定しない回より約 300 µs 遅い）。1e7 は line 1,620 / 1,733、step 1,735 / 1,860、area 1,888 / 2,101、band 3,494 / 3,890、bar 1,763 / 2,010、errorbar 3,202 / 3,563、縦の rule 1,132 / 1,317、横の rule 767 / 906。131,072 は segment 3,035 / 3,333、rect 5,264 / 5,636。

- **1e7 の Geom**の時間の大半は、線と同じ M4 の抽出である（line 1.4 ms）。step・area・bar・errorbar が線に足すのは 0.1〜0.3 ms で、M4 の点を画素列の台形・矩形・線に組み立てる分である。band と errorbar は Y の列を 2 本引くので M4 も 2 系列で、2 本のワーカーで並べて引く
- **縦と横の rule**は M4 を使わず、画素列（行）の境界ごとに二分探索で要素の有無を数える。1e7 で 0.4〜0.8 ms のうち、縦の rule は境界が 1,920 本、横は 1,080 本で、その比になっている
- **segment と rect の 131,072 個**: segment は 1 フレーム 2.7〜2.8 ms、rect は 4.0〜4.1 ms。内訳は下の「segment と rect の内訳」
- **固定した回**はどれも約 300 µs 遅い。G3 の計測と同じ、プロセスの固定が GPU のドライバのスレッドも同じ論理プロセッサに乗せる影響である（`bench.mdc`）。band と errorbar はさらに約 1.5 ms 遅い。2 系列の M4 を並べて引くワーカーが、1 つの論理プロセッサに押し込まれるためで、1 系列の Geom にはこの差がない
- **確保**: 毎フレーム新しい domain の 500 フレームで、どの Geom も 0 バイト。ただし 2 回のうち 1 回ずつ、errorbar（1 回目）と line（2 回目）で 56 B と 104 B が出た。出どころは下の「確保の出どころ」。どちらも M4 を引く Geom の、計画ごとに 1 回だけの確保で、この PR の変更によるものではない。同じ仕様の描き直しと 2 つの domain の交互の描き直しは、Geom ごとに 0 バイト（`GeomCustomTests.Record_Warm_AllocatesNothing`）

## 確保の出どころ

PR #125 のレビューで、56 B と 104 B の出どころを段ごとに数えた。スクラッチの写し（測った後に戻した）で、`Render(PlotSpec)` の段（索引の待ち・配置・`Extract`・記録・描画）と `PlotWorkerPool.Extract` の中の段の前後で `GC.GetAllocatedBytesForCurrentThread()` を数え、NativeAOT で line と errorbar の 1e3 を 10 回ずつ走らせた（上と同じ 600 フレーム、捨てるのは最初の 100）。

- 確保が出たのは 20 回のうち 3 回で、どれも 1 回に 1 フレームだけ、`Extract` の中の `M4Batch.Wait` だった（104 B が 2 回、56 B が 1 回）。索引の待ち・配置・記録・描画は、どの回も 0 バイト
- `M4Batch.Wait` は、計画の `M4Batch` の `_sync`（`object`）に `lock` をかけ、ワーカーがまだジョブを持っていれば `Monitor.Wait` で待つ。スクラッチのプログラム（NativeAOT）で、一度待ったことのあるスレッドが新しいオブジェクトに初めて `Monitor.Wait` すると、3 回とも 104 B だった（同じオブジェクトの 2 回目は 0 B）。ほかのスレッドの競合で膨らんだ後のロックでは 40 B、自分が競合して入ると 120 B（S2 の記録と同じ）なので、104 B はロックを膨らませる 64 B と待ちの 40 B である。56 B は、膨らんだ `_sync` に初めて競合して入るときの、S2 で調べた待ちのイベント（`s2-e2e.md` の「確保とメモリ」）
- `_sync` は計画ごとに 1 つなので、この確保は計画ごとに 1 回である。1e3 点ではジョブが小さく、呼び出し側のスレッドがたいてい自分で終えるので、本当に待つ最初のフレームが温まった後のどこかになる。M4 を引かない rule・segment・rect には出ない。`M4Batch` はこの PR で変えていない
- 最初の計測で、捨てるフレームを 50 にした予備の回の errorbar に出た 56 B を、点のバッファの伸びと書いたのは誤りだった（伸びなら数 KB 以上）。数の合うこの待ちの分と見られる

## segment と rect の内訳

131,072 個の segment の 1 フレーム（2.9 ms、Visual Studio の収集器と `xperf` で NativeAOT のバイナリを標本化）は、プロセスの標本の 49 % が HyperPlot のコード、残りがドライバ（`nvwgf2umx.dll` 12 %）とカーネル（`ntoskrnl.exe` 18 %、`dxgkrnl.sys` 6 %）だった。HyperPlot の分は、`RenderList.DrawPolyline` の記録（393,216 点から 131,072 本の線分と長さを作る）が 41 %、列の読み出しと写し（`ReadDifferences` と `CartesianTransform.Map`）が 30 %、NaN で区切った 1 本の折れ線の組み立てが 12 % である。ドライバとカーネルの分は、毎フレーム新しい 2.6 MB の線分を GPU に送る分で、同じリストを描き直すと 0.1 ms になる。

rect は、同じ数の矩形を記録するだけで 1.3 ms（`DrawRect` を 131,072 回）、記録したリストを描くだけで 1.2 ms（4 MB の矩形を送る）、残りの約 1.5 ms が 4 本の列の読み出しと写しと、要素ごとの角の並べ替えである。

測る前の実装は、要素ごとに 4 回、列から 1 個を読み（ストレージのインターフェースの呼び出しとチャンクの切り出し）、1 個を写していた。segment は 6.9 ms、rect は 6.0 ms だった。列をチャンクの span で読み、軸ごとにまとめて写すように直した（`Column.ReadDifferences`、`RecordContext.ElementPixels`）。写しの小さな関数がインライン化されていなかったので、まとめて写すループの中の写しをインライン化し、列の型の分岐をループの外に出した。

## NativeAOT

| サンプル | main（`2f89845`） | この PR |
| --- | --- | --- |
| `HelloPlot` | 1,788,928 B | 1,805,824 B（+16,896 B） |
| `SpecPlot` | 2,155,008 B | 2,246,656 B（+91,648 B） |

どちらも警告 0。`SpecPlot` はハードウェアと WARP、倍率 1 と 1.5 で 3 枚の PNG を書いた。ライトとダークの 2 枚と `HelloPlot` の PNG は、main のものと画素まで同じだった。

ILC の map ファイル（`IlcGenerateMapFile`）の節の長さを名前で分けると、`HelloPlot` の増分は、列の台形のシェーダのバイトコード（`ColumnsVS`・`ColumnsPS`）が +8,412 B、`D3D11ColumnPipeline` などの D3D11 の節が +5,633 B、Core の節（`ColumnInstance`、`TextEngine` の段の併合、`RenderList.DrawColumns`）が +2,572 B、メタデータが +198 B、ランタイムと BCL が +536 B で、節の和は +17,351 B である。ファイルの増分との差 −455 B は、PE の節の揃えである。`HelloPlot` は `PlotSpec` を使わないので、Geom のコードは入らない。

`SpecPlot` の増分は、Core の節（Geom の仕様・ビルダ・計画・変換）が +52,268 B、ランタイムと BCL（Geom の型の総称の具体化）が +11,577 B、シェーダが +8,412 B、D3D11 の節が +5,633 B、サンプルが +4,690 B、メタデータが +3,473 B で、節の和は +86,053 B である。差の +5,595 B は PE の節の揃えである。
