# R3c: 散布のヒットテストと選択の計測

行 R3c の計測（Issue #526）の記録。設計書 §9 の「散布のヒットテストと選択（行 R3c、Issue #471）」の場面を、要件 §5 の参照機で測り、要件 P-5（1e9 点のホバーのヒットテストが p99 で 1 ms 以下）と P-6（マウス移動だけのフレームが p95 で 2 ms 以下）を判定する。比べるのは要件の値である（main は索引の道の層に答えない）。

結論を先に書く。

- **P-5**: 密度で描いている画面と、生の点で描いている画面の `HitMode.XY` は収まる。`HitMode.X` は、拡大した表示で超えた（一様な 1e9 点の 0.01 % の表示で p99 5.1〜5.7 ms、1e-6 の表示で 27.2〜28.2 ms）。Issue #569 で、point の層がパネルの中に描いた点だけに答える形に直し、同じ場面を測り直した。一様と塊の場面の `HitMode.X` は p99 340 µs 以下で収まる（下の「Issue #569 の測り直し」）。縦線の場面（限界として測る場面）の `X` は、カーソルが線から 1 画素以上離れると、y の全体の表示で p99 36.6〜56.2 ms になり、収まらない
- **P-6**: 1e7 点をすべて選んで強調したマウスだけのフレームは、CPU 時間の p95 が 0.43 ms 以下、GPU 時間の p95 が 0.94 ms 以下で収まる
- **答えの正しさ**: 全部の葉を読む参照と比べた 20,988 か所で、食い違いは 0 件だった。測り直しでは、参照をパネルの中に描いた点だけにして、42,532 か所で 0 件だった
- **投げ縄でパネルを覆う葉の塗り**: ほかのプロセスが 6.2 コア以下の周で、選択を置いたフレームの CPU 時間は p50 12.3〜13.2 ms で、同じ負荷の周の矩形の選択（0.26〜0.33 ms）の 38〜50 倍である。投げ縄を置いたままビューを替えるフレームも、同じ負荷の周で p50 12.3・14.0 ms かかる（9.5 コア以上の周の値は本文に別に書く）。Issue #576 で直し、前後を交互に測って、ほかのプロセスが 6.2 コア以下の回で、2 つのフレームの p50 が 12.6〜13.3 ms から 2.8〜3.1 ms になった（下の「投げ縄の葉の塗りと確保の直し」）。Issue #591 で、マスクのビットを語の単位で立てる形に直し、葉の塗り・タイル・生の点の投げ縄の 2 つのフレームの p50 が 3.2〜5.3 ms から 1.2〜2.3 ms になった（下の「マスクのビットを語の単位で立てる直し」）
- **確保**: ヒットテストと、強調したマウスだけのフレームは 0 B。投げ縄の選択を置いたフレームと、投げ縄を置いたままビューを替えるフレームは、NativeAOT で 1 フレームに 99,360 B を確保する（Issue #570）。同じ直しで 0 B になった

### 機械の状態

- ほかのプロセスが使ったコアは、区間ごとに 1.7〜15.6 だった（表の「ほか」）。`watch-machine.ps1` の記録では、多かったのは別のセッションの XylemUI の試験（`XylemUI.Rendering.D3D11.Tests`、`XylemUI.Platform.Windows.Tests`）と C++ のコンパイラ（`cl`）、`VBCSCompiler` である
- 1e9 点の `hittest` の間、場面のプロセスのワーキングセットは 19.3〜19.6 GB（x と y のファイル 8 GB と索引の写し 12 GB の写像）で、機械の空きメモリは 1.8〜2.7 GB まで下がった。ヒットテストの値は、この状態での値である
- 索引の構築（最初の表示）は、ほかのプロセスが 4.3〜6.2 コアを使う中で、確定の公開まで一様 80.4 秒・57.8 秒、塊 170.7 秒・156.1 秒、粗い密度まで 7.0〜8.2 秒だった。一様の 80.4 秒（ほか 4.3 コア）は要件 P-15 の 75 秒を超えるが、P-15 は、ほかのプロセスが 2 コア以下の機械での値である
- GPU のクロックの記録は、どの回も最後の数秒が切れている（スクリプトが最後に `nvidia-smi` を止めるときに、残りの標本が書かれない。行 R3b1 の記録と同じ）。1 回目の最後の場面（1e6 点の密度の 3 周目の、投げ縄を替えるフレームとビューを替えるフレーム）は標本がない

### X のモードが超える理由

`SpatialSnapshot.Nearest` は、セルを、カーソルからセルの箱までの距離の順に取る。X のモードの距離は x の差だけなので、カーソルの x を含むセルは、y の範囲の全体にわたって距離 0 になる。探しは、最良の点の距離から 0.5 画素を引いた値より近いセルを取り続ける（決定 21）ので、x の差が 0.5 画素以内の点が見つかるまで、その列の葉を読み続ける。

- 葉（4,096 点まで）の点が、x の 1 画素あたり 1 点より密な表示では、葉を 1 つ読めば 0.5 画素以内の点が見つかり、そこで終わる。一様な 1e9 点の 1 % の表示がこれで、読んだ点は p99 3,953 点だった
- 葉の点が疎になる拡大では、葉を読んでも 0.5 画素以内の点がなく、画面の外の葉も、y の範囲の全体にわたって読む。一様な 1e9 点では、0.01 % の表示で p99 210,280 点（セル 118 個）、1e-6 の表示で p99 1,178,324 点（セル 626 個、最大 992 個・1,885,338 点）を読んだ
- 時間は読んだ点に比例する。1e-6 の表示の p99 は 27.2〜28.2 ms で、1 点あたり約 24 ns である
- 試作（Issue #496）の X のモードは、探しに表示の矩形を渡し、矩形の外の点を調べなかった。製品の `Nearest` には表示の制限がない。CPU の道（131,072 行まで、`HitScan.Points`）の X のモードも、画面の外の点を含めて答える
- Issue #569 で直す。`X` を、パネルの中に描かれた点だけを答える形にし、CPU の道とそろえる設計の変更を先に出す（オーナーの決定、2026-11-21、Issue #526 の Decision）

## Issue #607: CPU の道の遅れ

上の「CPU の道（131,072 点）」で、main も後のビルドも行 R3a の記録の 6〜7 倍の p50 だった件を、二分探索で分け、プロファイルで関数まで追って直した。

### 条件

- 場面: `run-r3c-hittest.ps1` の CPU の道の手順と同じ `points 131072 6 1 uniform 600`（一様）と `points 131072 6 0.6 cluster 600`（中央の塊）。1,920 × 1,080、半径 8 DIP、シードつきの 1,000 か所を 2 巡して 2 巡目を読む。時間は ms、p50 / p99 / 最大
- ビルド: コミットごとに `.dev/` の下の worktree から `HyperPlot.E2E` を NativeAOT Release で発行した（.NET SDK 10.0.404）。プロセスの優先度は高（場面が自分で上げる）
- 並べ方: ビルドを A・B・B・A の順に交互に流した（3 つなら A・B・C・C・B・A）。待ち行列（`.dev/out/queue.log`、接頭辞 `f607`）で、ほかの測りと重ならないようにした
- ほかのプロセスのコア: 場面が出す `other_cores`。行 R3a の後のハーネスが足した数なので、`101402a`・`5ab4e9e`・`676a953` などの古いビルドは出さない。同じ回の新しいビルドは 6.1〜15.6 コアで、機械は終始混んでいた
- `676a953` は、そのコミットの `ISpatialScreen.cs` が解析器の SA1615 で通らないので、`-p:TreatWarningsAsErrors=false` で発行した

### 並べ替えの確保

何が確保するかを、並べ替えだけを呼ぶ小さなプログラムで数えた（.NET SDK 10.0.403、ランタイムと ILCompiler 10.0.14。10 回呼んでから `GC.Collect()` を呼び、続く 1,000 回のスレッドの確保を数える。出力は `.dev/out/fix576-sortprobe-aot.txt` と `fix576-sortprobe-jit.txt`）。

| 呼び方 | NativeAOT | JIT |
| --- | --- | --- |
| `Span<float>.Sort()`（2 個） | 48 B / 回 | 0 B |
| `Span<double>.Sort()`（4 個のうちの 2 個、4 個） | 48 B / 回 | 0 B |
| `List<double>.Sort()`（3 個） | 48 B / 回 | 0 B |
| `Span<T>.Sort(Comparison<T>)`（静的なラムダ。`float` 2 個、`double` 4 個、構造体 3 個） | 0 B | 0 B |
| `List<T>.Sort(Comparison<T>)`（静的なラムダ。`double` 3 個、組 3 個） | 0 B | 0 B |
| `Span<float>.Sort(TComparer)`（構造体の比較子） | 72 B / 回 | 88 B / 回 |

- 比べる関数を渡さない並べ替えは、NativeAOT だけで 1 回 48 B を確保する。確保 0 の試験は JIT で走るので、これを数えない
- 原因はランタイムのソースで読める（dotnet/runtime のタグ `v10.0.0`）。NativeAOT の `ArraySortHelper<T>.Default` は、いつも比較子を通す実装である（`ArraySortHelper.NativeAot.cs`）。その `Sort(Span<T>, IComparer<T>?)` は、呼ばれるたびに `comparer.Compare` からデリゲートを作って `IntrospectiveSort` に渡す（`ArraySortHelper.cs` の 25〜26 行）。JIT（CoreCLR）は、`IComparable<T>` を持つ型に `GenericArraySortHelper<T>` を選び（`ArraySortHelper.CoreCLR.cs`）、デリゲートを作らない
- 比べる関数を渡す並べ替えは、渡したデリゲートをそのまま同じ `IntrospectiveSort` に渡す（`ArraySortHelper.cs` の 54〜61 行）。NativeAOT では、前も後も同じ並べ替えの道を通り、違いは呼ぶたびのデリゲートの有無だけである
- 同じプログラムで、`Comparer<float>.Default.Compare` から `Comparison<float>` を 1 つ作ると、NativeAOT で 48 B（JIT で 64 B）だった。表の 48 B は、このデリゲート 1 個である
- 表の最後の行（構造体の比較子を渡す `MemoryExtensions.Sort<T, TComparer>`）は、`src` にある `Data/SpatialTableBuilder.cs` の `Resolve` の形（`frontier.Sort(new CodeOrder(...))`。タイルの構築のワーカーで、水準ごとに 1 回）を確かめるために足した。この形は JIT でも確保する。`MemoryExtensions.cs` の `Sort<T, TComparer>` は比較子を `IComparer<T>?` として `ArraySortHelper<T>.Default.Sort` に渡すので、構造体は箱に入る（ソースの注に「value-type comparer will be boxed」）。その先で、NativeAOT も CoreCLR も、既定でない比較子には `comparer.Compare` からデリゲートを作る（CoreCLR は `GenericArraySortHelper<T>.Sort` の else の枝）。PR #584 のレビューのあとに、同じ形の小さなプログラムで分けた（.NET SDK 10.0.403、1,000 回。`.dev/out/rev584-sortprobe-aot.txt`、`rev584-sortprobe-jit.txt`）。フィールドのない比較子は NativeAOT 72 B・JIT 88 B で表と同じ、その構造体の箱だけを作ると 24 B だった。72 B = 24 B + 48 B、88 B = 24 B + 64 B で、箱 1 個とデリゲート 1 個である。`CodeOrder` と同じ 16 B のフィールド（ポインタと `int`）を持つ比較子は NativeAOT 80 B・JIT 96 B で、箱が 32 B になる分だけ多い。フレームの経路ではないので、この PR では変えていない（下の「ほかの並べ替え」）
- Issue #570 が「測っていない」とした 6 か所は、次のとおりである
