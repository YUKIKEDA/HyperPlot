# 設計判断（却下した代替案）

現行の仕様は [design.ja.md](./design.ja.md) だけを正とする。ここには「今は採用していない案」と、それを捨てた理由だけを残す。

形式:

```text
Decision: 採用した契約
Reason: なぜそれか
Rejected: 捨てた案
```

---

## GPU のバックエンド

Decision:
  Windows は D3D11 を TerraFX.Interop.Windows の宣言で直接呼ぶ。macOS は Metal、Linux は wgpu-native を、後の行で決まった数のパイプラインの抽象（§5.2）の下に足す。

Reason:
  最初のホストの WPF は D3D9Ex の D3DImage で共有テクスチャを受け取れ、D3D11 からの共有が一番素直に組める。WPF の要素をプロットの上に重ねられる。
  D3D11 は VM・リモートデスクトップ・WARP でも動き、CI で決定論的な画素のテストができる。
  compute shader（CS 5.0）が LOD・密度の集計に十分で、XylemUI の D3D11 のレンダラと同じ API なので、後で XylemUI に載せるときに資産を共有できる。
  追加の DLL がなく、NativeAOT の単一バイナリを壊さない。

Rejected:
  - Silk.NET の OpenGL 4.5（POC の構成）: WPF との共有に WGL_NV_DX_interop か readback が要り、ドライバの差が大きい。macOS は OpenGL 4.1 止まりで compute が使えない。リモートデスクトップ・VM で 4.5 がないことがある。XylemUI は OpenGL を持たない
  - wgpu-native に一本化: 全 OS が 1 実装で済むが、外部のテクスチャとの共有がほぼできず、WPF では子 HWND になり WPF の要素を重ねられない。Windows でも DLL（10〜20 MB）の配布が要る。Windows の内部では D3D12 / Vulkan を使い、DX12 のない環境に弱い
  - D3D12 / Vulkan の直接呼び出し: 資源の寿命と同期を自分で管理する分のコストに見合う性能上の利点が、2D のプロットの負荷では見込めない
  - Vortice.Windows: 生成した宣言の上にマネージドのラッパーの層が載り、呼び出しのコストと寿命の管理が手元から離れる

## 10 億点の扱い

Decision:
  O(N) の仕事はワーカーで一度だけ行い、索引（チャンクの統計、min / max の LOD ピラミッド、Morton 順のタイル索引、密度タイル）を作る。フレームは索引を使い、画面の大きさに比例する仕事だけをする。

Reason:
  10 億点の float32 の x, y だけで 8 GB あり、GPU に全部は載らない。毎フレーム全点を GPU で集計する方式は、帯域だけで 60 fps に届かない。

Rejected:
  - 全点を GPU に置いてインスタンス描画（POC の方式の延長）: VRAM に載らない。載る規模でも、引きの表示では 1 画素に数十万点が重なり、描画の大半が無駄になる
  - 毎フレームの全点の集計（datashader の方式をそのまま）: 対話的な速さにならない。中間の規模（1e7〜1e8）で GPU の集計を足す余地は §5.5.2 に残す
  - LTTB などの見た目の近似の間引き: ピーク・外れ値を落とすことがあり、計測の用途で使えない。M4 は画素列ごとの min / max を保つ

## 散布の空間索引

Decision:
  点を Morton 順に並べ直した写しと、セル＝連続範囲の四分木の表（§3.4）。

Reason:
  並べ直せば四分木のどのセルも連続した範囲になり、表は葉の数（点の数 / 4096 程度）の行で済む。GPU への転送もタイル単位の連続領域になる。

Rejected:
  - 点ごとのノードを持つ QuadTree（POC）: 10 億点ではノードのメモリが元データを超える。ポインタを辿るのでキャッシュの効率も悪い
  - GPU の ID バッファでのピッキング: 密度の領域では点が画素に描かれていない。readback の待ちが UI のスレッドに入る

## WPF への組み込み

Decision:
  D3D11 の共有テクスチャ → D3D9Ex → `D3DImage`。ソフトウェア描画のときは readback → `WriteableBitmap`。

Reason:
  WPF の要素をプロットの上に重ねられる（ツールチップ・注釈の編集 UI を WPF で作る利用者がいる）。

Rejected:
  - `HwndHost` の子ウィンドウ: いわゆる airspace の問題で WPF の要素を上に重ねられない
  - 毎フレームの readback と `WriteableBitmap` だけ: GPU → CPU → GPU の往復が大きな画面で重い。ソフトウェア描画のときの逃げ道としてだけ使う

## テキスト

Decision:
  Core のテキストの契約と、Windows では DirectWrite で整形とラスタライズ。アトラスは自作。グレースケールのアンチエイリアス。

Reason:
  軸のラベル・凡例・ツールチップをライブラリ自身が描けば、どのホストでも同じ見た目になる（POC はホストの UI で軸のラベルを描いており、ホストごとに作り直しになった）。
  日本語のフォールバックを OS に任せられ、追加の DLL がない。

Rejected:
  - ホストの UI でラベルを描く（POC）: ホストごとに実装が要り、ヘッドレスの画像に文字が入らない
  - SkiaSharp: ネイティブの DLL が要り、NativeAOT の単一バイナリを壊す
  - Direct2D でオーバーレイを描く: D3D11 の上の D2D は便利だが、Metal / wgpu のバックエンドで同じものを作れない。描画を IR（§5.1）に揃えるほうが移植しやすい
  - ClearType: 前乗算アルファで任意の背景に重ねる層では正しく描けない

## API の形

Decision:
  不変の仕様の木と流れるようなビルダ。列は型付きの参照（`ColumnRef<T>`）。利用者の計算はチャンク単位のデリゲート。

Reason:
  型の誤りがコンパイル時に出る。リフレクションも式木のコンパイルも要らないので NativeAOT で動く。

Rejected:
  - `Expression<Func<...>>` で列を指して実行時にコンパイル: NativeAOT で動かない（インタプリタに落ちて遅い）
  - JSON の仕様（Vega-Lite の形そのまま）を主な API にする: 型の誤りが実行時まで分からない。JSON からの読み込みは後で足せる（source-generated のシリアライザで）
  - 要素ごとの `Point` オブジェクトの並び: 10 億点でヒープとキャッシュの効率が成り立たない。列指向（SoA）にする

## 3D の時期

Decision:
  3D は v1.x で入れる。v1 は座標系・ビュー・描画 IR・ヒットテスト・空間索引の契約を 3D に耐える形にするだけ（設計書 §13、不変条件 12）。

Reason:
  v1 は WPF・XylemUI・GoG・インタラクションで既に大きい。3D で公開 API が壊れる原因（2D だけの範囲・3×3 の行列・2D の点を前提にしたヒットテスト）は、v1 の契約で先に取り除ける。

Rejected:
  - v1 に基本の 3D（散布・線・面、1e7 点）を入れる: v1 の公開が遅れ、10 億点の 3D は結局 v1.x になる
  - v1 で 10 億点の 3D（八分木の LOD）まで入れる: 作業量が最も大きく、v1 のほかの要件が大きく遅れる
  - 3D を対象外のままにする: 後から足すと座標系とビューの公開 API を変えることになる
  - v1 のシェーダが深度と 3 成分の位置を実装する: K1 でパイプラインに手を入れずに済むが、v1 で描かない経路のコード・テスト・GPU 時間の計測を R2 が負い、v1 の要件に根拠がない。v1 の備えは契約の形（コマンドの記録と資源の種類）に限る（設計書 §5.2）

## 10 億点の 3D 散布の索引

Decision:
  2D のタイル索引と共通の並べ直し（Morton 符号・数え上げソート）を 3 次元で行い、八分木の節点ごとに間引いた代表の点を持つ。点の予算まで、画面上で大きく見える節点から描く。

Reason:
  2D と同じく、O(N) の仕事を一度だけ行い、フレームの仕事を点の予算で抑えられる。並べ直しの部品を 2D と共有できる。

Rejected:
  - 3D の密度（ボクセルの集計）だけで描く: 回転のたびに投影が変わり、2D の密度タイルのように前もって作れない
  - 毎フレームの全点の投影と間引き: 10 億点では帯域だけで対話的な速さにならない

## プロジェクトの分け方

Decision:
  データ・GoG・インタラクション・描画 IR を 1 つの `HyperPlot.Core` に置き、名前空間で分ける。

Reason:
  v1 の間は層の境界がまだ動く。アセンブリをまたぐと internal の最適化（構造体の直接の受け渡し）がしにくい。

Rejected:
  - 最初から `HyperPlot.Data` を別アセンブリにする: 利用者からデータ層だけを使いたいという要求が出たら分ける
