# 設計判断（却下した代替案）

現行の仕様は [design.ja.md](./design.ja.md) だけを正とする。ここには「今は採用していない案」と、それを捨てた理由だけを残す。

形式:

```text
Decision: 採用した契約
Reason: なぜそれか
Rejected: 捨てた案
```

---

## GPU のバックエンド

Decision:
  Windows は D3D11 を TerraFX.Interop.Windows の宣言で直接呼ぶ。macOS は Metal、Linux は wgpu-native を、後の行で決まった数のパイプラインの抽象（§5.2）の下に足す。

Reason:
  最初のホストの WPF は D3D9Ex の D3DImage で共有テクスチャを受け取れ、D3D11 からの共有が一番素直に組める。WPF の要素をプロットの上に重ねられる。
  D3D11 は VM・リモートデスクトップ・WARP でも動き、CI で決定論的な画素のテストができる。
  compute shader（CS 5.0）が LOD・密度の集計に十分で、XylemUI の D3D11 のレンダラと同じ API なので、後で XylemUI に載せるときに資産を共有できる。
  追加の DLL がなく、NativeAOT の単一バイナリを壊さない。

Rejected:
  - Silk.NET の OpenGL 4.5（POC の構成）: WPF との共有に WGL_NV_DX_interop か readback が要り、ドライバの差が大きい。macOS は OpenGL 4.1 止まりで compute が使えない。リモートデスクトップ・VM で 4.5 がないことがある。XylemUI は OpenGL を持たない
  - wgpu-native に一本化: 全 OS が 1 実装で済むが、外部のテクスチャとの共有がほぼできず、WPF では子 HWND になり WPF の要素を重ねられない。Windows でも DLL（10〜20 MB）の配布が要る。Windows の内部では D3D12 / Vulkan を使い、DX12 のない環境に弱い
  - D3D12 / Vulkan の直接呼び出し: 資源の寿命と同期を自分で管理する分のコストに見合う性能上の利点が、2D のプロットの負荷では見込めない
  - Vortice.Windows: 生成した宣言の上にマネージドのラッパーの層が載り、呼び出しのコストと寿命の管理が手元から離れる

## 10 億点の扱い

Decision:
  O(N) の仕事はワーカーで一度だけ行い、索引（チャンクの統計、min / max の LOD ピラミッド、Morton 順のタイル索引、密度タイル）を作る。フレームは索引を使い、画面の大きさに比例する仕事だけをする。

Reason:
  10 億点の float32 の x, y だけで 8 GB あり、GPU に全部は載らない。毎フレーム全点を GPU で集計する方式は、帯域だけで 60 fps に届かない。

Rejected:
  - 全点を GPU に置いてインスタンス描画（POC の方式の延長）: VRAM に載らない。載る規模でも、引きの表示では 1 画素に数十万点が重なり、描画の大半が無駄になる
  - 毎フレームの全点の集計（datashader の方式をそのまま）: 対話的な速さにならない。中間の規模（1e7〜1e8）で GPU の集計を足す余地は §5.5.2 に残す
  - LTTB などの見た目の近似の間引き: ピーク・外れ値を落とすことがあり、計測の用途で使えない。M4 は画素列ごとの min / max を保つ

## 散布の空間索引

Decision:
  点を Morton 順に並べ直した写しと、セル＝連続範囲の四分木の表（§3.4）。

Reason:
  並べ直せば四分木のどのセルも連続した範囲になり、表は葉の数（点の数 / 4096 程度）の行で済む。GPU への転送もタイル単位の連続領域になる。

Rejected:
  - 点ごとのノードを持つ QuadTree（POC）: 10 億点ではノードのメモリが元データを超える。ポインタを辿るのでキャッシュの効率も悪い
  - GPU の ID バッファでのピッキング: 密度の領域では点が画素に描かれていない。readback の待ちが UI のスレッドに入る

## 散布の空間索引の作り方と置き場所（行 C3、Issue #401）

Decision:
  索引は、点を Morton 順に並べ直した写し（x、y、元の位置）と、四分木の表と、密度タイルである。スケールの空間に軸あたり 32 ビットの格子を張って作る（§3.4）。写しは要件 P-8 の 10 % の例外とし、10 % は表と密度タイルの合計に当てる。メモリマップの列の写しは一時ファイルに、ほかの列の写しはネイティブメモリに置く。構築は 2 段で公開し、`Invalidate` では全体を作り直す。実装は行 C3a（写し・表・問い合わせ）と行 C3b（密度タイル）に分ける。

Reason:
  写しがあれば、どのセルの点も続けて読める。元の位置があれば、選択とツールチップが元の行を指せる。スケールの空間で作れば、ビンが画面で等しい幅になる。2 段の公開は 1 回目の数え上げの結果をそのまま使うので、余分な仕事がない。行の分け方は、行 B1 がピラミッドを描画より先に作ったのと同じである。

Rejected:
  - 写しを持たず、元の位置だけを並べて持つ（元データの 50 %）: 葉 1 つを読むのに 4,096 回の離れた読み出しになり、生の点 1e7 点を描くのに 1e7 回の離れた読み出しになる。メモリマップの列では、そのたびにページを読むことがある
  - 元の位置をいつも `long` で持つ: 1e9 点の `float` の x, y で写しが 16 GB（元データの 200 %）になる。行の範囲が 2^32 行以下なら 4 バイトで足りる
  - 元の位置を持たない: 選択（要件 I-3）とツールチップは元の行を指すので、写しの点から元の行を引けなければならない
  - 置き場所を空きメモリの量で決める: 同じデータが、動かす機械とそのときの空きで違う振る舞いになる
  - データの値で量子化する: log の軸では、ビンが画面で等しい幅にならない。6 桁にわたる log の軸では、下の桁が数個のビンに集まる
  - 軸あたり 16 ビットの格子: データが [0, 1] で番兵の値が −9999 のとき、データは軸あたり約 6.5 目に入り、1e9 点が約 43 個のセルに集まる。32 ビットなら軸あたり約 43 万目である
  - 写しに格子の座標（`uint` × 2）を持つ: どの型の列でも 1 点 8 バイトになり、GPU にそのまま送れる。しかし精度が範囲の 2^-32 に落ちる（10 年の時間軸で約 73 ms の刻み。幅 2,000 画素の画面では、約 200 万倍の拡大で 1 画素ずれる）。不変条件 6 を散布だけが守れなくなる
  - エンコードの列（色・大きさ）を写しに入れる: x と y が同じで色の列が違うレイヤーが、索引を使い回せない。色の列を替えるたびに並べ直しになる
  - `Invalidate` で古い索引を先に捨てる: 作り直しが終わるまで、散布が描けない
  - `Invalidate` でチャンクごとに一部だけを直す: 並べ直しは全体で 1 つの結果で、1 つのチャンクの点が変わると、写しのほかの点の位置も動く
  - 変わった部分を、ピラミッドのように未構築に戻す: 索引の構築は全体を何回も走査するので、変わり続けるデータでは完了しない
  - 索引への追記を後の行に回す: その行がロードマップになく、名前のない先送りになる（`.cursor/rules/defer.mdc`）。v1 では作らないと決め、要件 §7 の対象外に書いた。追記する散布は、生の点で描ける 1e7 点までである（§3.5）
  - 密度タイルのカウンタをすべて `uint` で持つ: 一様なデータで元データの約 16.7 % になり、P-8 の 10 % を超える（§3.4 の計算）
  - 密度タイルのカウンタの幅を `byte`・`ushort`・`uint` の 3 つにし、`uint` の最大で止める: 同じ位置に 2^32 を超える点が重なるデータで、ビンの値が正しくなくなる。そのタイルだけを `ulong` で持てば、ほかのタイルの大きさは変わらない（決定 16）
  - 四分木の表に上限を置かず、表も P-8 の例外に書く: 深く入れ子になった塊のデータで、表が `float` の x, y の約 12.5 % になる。例外が 2 つになり、10 % が密度タイルだけの値になる（決定 14）
  - 四分木の表に上限を置かず、表が収まるまで索引全体の `LeafCapacity` を上げる: すべての葉が大きくなり、塊のない場所でも、ヒットテストと生の点の読み出しが読む点が増える（決定 14）
  - 水準 8 のセルまで書いてから、セルごとに葉まで並べ直して表を作る（決定 11 のはじめの並び）: 写し（1e9 点で 12 GB）を 2 回書くか、その場で並べ替えることになる。数え上げを葉が決まるまで繰り返せば、書くのは 1 回で済む（決定 8・15）
  - 次の起動で、残った一時ファイルを探して消す: ライブラリが、自分が今作ったファイルのほかを消すことになる。閉じると消える指定（Windows）と、開いた直後に名前を消す手順（Linux）で、プロセスが落ちてもファイルは残らない
  - 一時ファイルの大きさを先に確保しない: Linux では、空きがなくなったときに、写像への書き込みでプロセスが終わる（§3.4 の「確かめたこと」）
  - 点のない索引（n = 0、有限な点が 1 つもない列）を引数の例外か失敗にする: 長さ 0 の列と空の行の範囲は正しい引数で、すべての値が NaN の列も正しいデータである。呼び出し側が、索引を作る前に点の数を調べることになる。点の数が 0 の確定のスナップショットなら、問い合わせはほかの索引と同じ形で答える（PR #402 のレビュー）
  - 幅が `double` に収まらない範囲（`-double.MaxValue` から `double.MaxValue`）を失敗にする: `double.MaxValue` を番兵に使うデータで索引が作れなくなる。値を 2 で割ってから量子化すれば、式は単調のままで計算できる

## WPF への組み込み

Decision:
  D3D11 の共有テクスチャ → D3D9Ex → `D3DImage`。ソフトウェア描画のときは readback → `WriteableBitmap`。

Reason:
  WPF の要素をプロットの上に重ねられる（ツールチップ・注釈の編集 UI を WPF で作る利用者がいる）。

Rejected:
  - `HwndHost` の子ウィンドウ: いわゆる airspace の問題で WPF の要素を上に重ねられない
  - 毎フレームの readback と `WriteableBitmap` だけ: GPU → CPU → GPU の往復が大きな画面で重い。ソフトウェア描画のときの逃げ道としてだけ使う

## テキスト

Decision:
  Core のテキストの契約と、Windows では DirectWrite で整形とラスタライズ。アトラスは自作。グレースケールのアンチエイリアス。

Reason:
  軸のラベル・凡例・ツールチップをライブラリ自身が描けば、どのホストでも同じ見た目になる（POC はホストの UI で軸のラベルを描いており、ホストごとに作り直しになった）。
  日本語のフォールバックを OS に任せられ、追加の DLL がない。

Rejected:
  - ホストの UI でラベルを描く（POC）: ホストごとに実装が要り、ヘッドレスの画像に文字が入らない
  - SkiaSharp: ネイティブの DLL が要り、NativeAOT の単一バイナリを壊す
  - Direct2D でオーバーレイを描く: D3D11 の上の D2D は便利だが、Metal / wgpu のバックエンドで同じものを作れない。描画を IR（§5.1）に揃えるほうが移植しやすい
  - ClearType: 前乗算アルファで任意の背景に重ねる層では正しく描けない

## API の形

Decision:
  不変の仕様の木と流れるようなビルダ。列は型付きの参照（`ColumnRef<T>`）。利用者の計算はチャンク単位のデリゲート。

Reason:
  型の誤りがコンパイル時に出る。リフレクションも式木のコンパイルも要らないので NativeAOT で動く。

Rejected:
  - `Expression<Func<...>>` で列を指して実行時にコンパイル: NativeAOT で動かない（インタプリタに落ちて遅い）
  - JSON の仕様（Vega-Lite の形そのまま）を主な API にする: 型の誤りが実行時まで分からない。JSON からの読み込みは後で足せる（source-generated のシリアライザで）
  - 要素ごとの `Point` オブジェクトの並び: 10 億点でヒープとキャッシュの効率が成り立たない。列指向（SoA）にする

## 3D の時期

Decision:
  3D は v1.x で入れる。v1 は座標系・ビュー・描画 IR・ヒットテスト・空間索引の契約を 3D に耐える形にするだけ（設計書 §13、不変条件 12）。

Reason:
  v1 は WPF・XylemUI・GoG・インタラクションで既に大きい。3D で公開 API が壊れる原因（2D だけの範囲・3×3 の行列・2D の点を前提にしたヒットテスト）は、v1 の契約で先に取り除ける。

Rejected:
  - v1 に基本の 3D（散布・線・面、1e7 点）を入れる: v1 の公開が遅れ、10 億点の 3D は結局 v1.x になる
  - v1 で 10 億点の 3D（八分木の LOD）まで入れる: 作業量が最も大きく、v1 のほかの要件が大きく遅れる
  - 3D を対象外のままにする: 後から足すと座標系とビューの公開 API を変えることになる
  - v1 のシェーダが深度と 3 成分の位置を実装する: K1 でパイプラインに手を入れずに済むが、v1 で描かない経路のコード・テスト・GPU 時間の計測を R2 が負い、v1 の要件に根拠がない。v1 の備えは契約の形（3 成分のコマンドを別の記録の形で足せることと、資源の種類）に限る（設計書 §5.2）

## 10 億点の 3D 散布の索引

Decision:
  2D のタイル索引と共通の並べ直し（Morton 符号・数え上げソート）を 3 次元で行い、八分木の節点ごとに間引いた代表の点を持つ。点の予算まで、画面上で大きく見える節点から描く。

Reason:
  2D と同じく、O(N) の仕事を一度だけ行い、フレームの仕事を点の予算で抑えられる。並べ直しの部品を 2D と共有できる。

Rejected:
  - 3D の密度（ボクセルの集計）だけで描く: 回転のたびに投影が変わり、2D の密度タイルのように前もって作れない
  - 毎フレームの全点の投影と間引き: 10 億点では帯域だけで対話的な速さにならない

## 3D の設計の進め方（行 K0）

Decision:
  3D の設計は、R3b1〜V1 のコードの行と並べて始める。行 K0 は K0a（共通の部分と八分木）・K0b（線の単純化）・K0c（面の LOD）・K0d（半透明とメッシュ）・K0e（ボリューム）の 5 つに分け、実装の行 K1〜K6 は対応する設計の行の後に置く。性能の目標は P-11〜P-14 に加えて、欠けた目標（K-3 の線の回転、K-7 のレイのヒットテスト、八分木の構築時間、写しと節点の表のメモリ）も K0 で足し、試作で確定する（Issue #470 の決定 1・2・4、要件 §5、設計書 §13）。

Reason:
  K0 は文書だけで、R3b1〜V1 のコードとファイルが重ならない。方式ごとに行を分けると、ブロックの大きさ 64³（設計書 §13.6）のように決める行のなかった点が行を持つ。

Rejected:
  - Grill だけ始める: 文書だけの行で、コードの行とファイルが重ならないのに、手が空く
  - V1 の後まで待つ: 同じく、コードの行とファイルが重ならないのに、手が空く
  - K0 を 1 行のままにする: 4 種の試作が 1 つの PR にかかり、K1 が最後の試作まで待つ
  - 共通の部分だけを K0 にし、方式は各 K 行で決める: 行の文と設計書 §13 の「K0 で決める」を全部書き換えることになる
  - 性能の目標を P-11〜P-14 だけにする: 要件 §5 の「3D の目標は K0 で確定する」と合わない

## 3D の仕様の形（行 K0a）

Decision:
  3D の cartesian は `CoordSpec` の新しい種類にし、`PlotSpec` に z のスケール、層に Z チャネルを足す。ファセットと要件 G-6 のすべての軸の種類（カテゴリも）を受け、flip・polar・二次軸・identity 以外のすべての Position（fill も）・identity 以外の Stat は仕様の検査で例外にする（Issue #470 の決定 3・13・15、設計書 §13.2）。

Reason:
  設計書 §4.4 は、3D の cartesian が同じ契約で変換を返すとしている。§13.1 の G1 の行は、z のチャネルを後から足しても既存のコードが壊れない形を v1 に持たせた。

Rejected:
  - 別の `Plot3DSpec`: 図とリンク（要件 K-7）に別の道が要り、§4.4 の契約が 2 つに分かれる
  - ファセットも断る: 3D の小さな図を並べられない
  - Stat も受ける: 要件にない仕事が増える

## 3D の線の単純化: 軸ごとの誤差、頂点ごとの重要度、固定の区間、予算（行 K0b）

Decision:
  単純化の誤差を軸ごとの成分 (ex, ey, ez) で持ち、画面上の誤差は ‖(kx·ex, ky·ey, kz·ez)‖ に投影の倍率を掛けて抑える。頂点ごとに Douglas–Peucker で入ったときの誤差を持ち（BLG 木）、部分木の最大を伝える。区間は 2 の冪の頂点の数で固定する。誤差の上限に加えて頂点の予算を置き、止まったら上限まで描き足す（Issue #481 の決定 1〜4、設計書 §13.4）。

Reason:
  3D のズームとパンは軸ごとに範囲を変える（Issue #470 の決定 10）ので、軸ごとの成分なら、拡大の度合いが軸ごとに違っても上限を保てる。頂点ごとの重要度は、八分木の加法方式（Issue #470 の決定 6）と同じ形になる。予算は、八分木の止まったときの描き足し（同決定 8）と同じ形で不変条件 4 を守る。

Rejected:
  - 1 つの 3D の距離で誤差を測る: 回転だけなら成り立つが、軸ごとのズーム（Issue #470 の決定 10）で K-3 の上限が破れる
  - ズームごとに作り直す: 1e8 頂点で O(N) かかり、止まるまで粗い
  - 段ごとに単純化した列の写しを持つ: 段の合計で最大およそ +100 % のメモリになる
  - 八分木のセルの境で区間を切る: 区間の大きさがばらばらで、作り方が別になる
  - 予算を置かずに上限を常に守る: 1 フレームの時間に上限がない

  理由は Issue #481 の 2026-11-13 の採らなかった案の理由と細部のコメント による。

## 深度のモードの置き場所（行 K0a）

Decision:
  深度のモード（なし・検査・検査と書き込み）は、位置が 3 成分のコマンドだけが持つ。2D のコマンドはいつも深度「なし」で、記録に深度の欄を持たない（Issue #469、Issue #470 の決定 5、設計書 §5.1・§5.2・§13.1）。

Reason:
  v1 のコードの記録には深度の欄がなく、設計の「各コマンドの記録が深度のモードの欄を持つ」と食い違っていた。2D のマークの記録に使わない欄を持たせないのは、使わない z を持たせないのと同じ理由である（設計書 §5.1）。

Rejected:
  - 深度のモードを状態のコマンド（`SetDepthMode`）にする: 行 K1 で、2D のシェーダとパイプラインにも深度の出力が要る
  - 設計どおり、各コマンドの記録に深度のモードの欄を足す: v1 の行が要り、v1 で描かない経路を持たせない趣旨（設計書 §5.2）と合わない

## 面の LOD: タイルの四分木、2 つ飛ばしの間引き、高さのテクスチャ、辺を縫う（行 K0c）

Decision:
  格子をタイルの四分木にし（Ulrich 2002 の Chunked LOD、行 G9 のラスタと同じ形）、段は元の格子の点を 2 つに 1 つ残す間引きで作る。タイルと段ごとに z の最大のずれを z のスケールの空間で持ち、画面上の誤差の上限で段を選ぶ。タイルは z の `R32_FLOAT` のテクスチャで置き、頂点シェーダが格子の番号と座標の列から位置を作る。隣のタイルとの段の差を 1 以下に制限し、辺の形ごとの索引の列で縫う（Issue #482 の決定 1〜4、設計書 §13.5）。

Reason:
  カメラは軸の箱の外にあり（Issue #470 の決定 16）、箱の外の切り取りをタイルの単位で捨てられ、非等間隔の格子（要件 K-4）もそのまま扱える。段の頂点が元の点なので x と y の誤差は 0 で、軸ごとの拡大（Issue #470 の決定 10）に耐える。縫うと余分な形がなく、半透明とワイヤーフレームで縫い目が見えず、決定的である。

Rejected:
  - Geometry Clipmaps（Losasso と Hoppe 2004）: 視点を中心にした入れ子の正則格子が前提で、外から箱を見るプロットと非等間隔の格子に合わない
  - スカート（Ulrich 2002、スライド 30）: 半透明で 2 重に塗り、ワイヤーフレームに余分な線が出る
  - モーフィング（Ulrich 2002 スライド 27、CDLOD）: 隙間そのものは消えない。不変条件 11 のため、時刻でなく視点だけで決める必要がある
  - 2 × 2 の平均の段（行 G9 と同じ）: 頂点が面の上から外れ、x と y の誤差も要る
  - min と max を保つ間引き: 三角形を作れない
  - xyz の頂点バッファ: 転送が 3 倍になる

  この 3 つの理由は Issue #482 の 2026-11-13 の採らなかった案の理由と細部のコメント による。

## 八分木の代表の点・間引き・描き足し・描き方（行 K0a）

Decision:
  加法方式で、元の点はどれか 1 つの節点にだけ入り、代表の点は写しの並べ替えで持つ。決まったシードでシャッフルした入力の、128³ の格子のセルごとに最初の 1 点を節点に残す。視点が止まったら予算を上げ、画面で大きい節点から順に、次の節点を残した色と深度へフレームをまたいで足す。点の描き方は、印のパイプラインに深度を足す形と計算シェーダのラスタ化を試作して測ってから決める（Issue #470 の決定 6〜9、設計書 §13.3）。

Reason:
  追加のメモリが節点の表だけになる。シードが決まっているので八分木は決定的で、描く節点の集合は視点と予算だけで決まる（不変条件 11）。

Rejected:
  - 代表の点を別の列に写す（置換方式）: 追加のメモリが 1/(r − 1)（表面状のデータで約 33 %、推論）で、生成も遅い
  - 格子のセルの中心に最も近い点を残す: 規則的な模様が出る
  - 近似の Poisson-disk で間引く: 生成が遅く、節点の境では守られず畝の模様が出る（Schütz 2016 §3.3.1）
  - 再投影とランダムな部分集合で描き足す: 画が通ってきた視点の履歴に依り、不変条件 11 に反する
  - 止まっても毎フレーム描き直す: 止まっているのに、1 フレームが予算の分だけ長くなる
  - 印のパイプラインだけで描く: 2D の 1e7 点は重なる画面で 17.5〜19.2 ms で、P-11 の 16 ms を超える

## 3D のズームとパン（行 K0a）

Decision:
  ホイール、ドラッグのパン、`SetView` は x・y・z の軸の範囲を変え、軸の箱は画面に固定し、箱の外のデータは切り取る。回転と決まった視点はカメラを動かす。3D の矩形ズームは置かない（Issue #470 の決定 10・11、設計書 §6.2・§13.8）。

Reason:
  2D と同じ `ViewRange`（`long` の原点、要件 R-6 の精度）・履歴・リンクの意味になり、目盛りは新しい範囲で引き直される。画面の矩形は奥行きが決まらず、どの軸をどう狭めるかが一意でない。

Rejected:
  - 範囲を変え、修飾キーでカメラを動かす: 履歴とリンクで 2 種の変化を扱うことになる
  - カメラだけを動かす: 寄ると箱が画面からはみ出し、目盛りとラベルが見えなくなる。範囲は仕様と `SetView` だけになる
  - matplotlib と同じ矩形ズーム: 奥行きの軸の狭め方が利用者に分かりにくい

## 半透明: WBOIT、不透明度のチャネルを持つ層は全部を OIT に通す（行 K0d）

Decision:
  描く順によらない半透明の合成は WBOIT（McGuire と Bavoil 2013）にする。不透明度のチャネルを持つ層は、α = 1 の点も含めて全部を OIT に通す。止まった後の描き足しで不透明の点を足したフレームは、WBOIT の 2 枚を捨てて半透明の層を描き直す（Issue #483 の決定 1・2・4、設計書 §13.3・§13.7）。

Reason:
  1 パスで、メモリは画面に比例する（1 画素 9 B）。合成が加算なので、フレームをまたいで足しても一度に描くのと同じ結果になる。同じ投入順なら WARP で決定的と推論する（D3D11.3 §4.2）。全部を OIT に通すと、層の中では、半透明を累積した後に不透明の点が手前に足されても、結果は描く順に依らない。層をまたいで不透明の点が足されるときは、WBOIT を描き直せば、結果が描き足しのフレームの分け方に依らない（不変条件 11）。不透明の点を足すフレームの数は限られる。

Rejected:
  - MBOIT（Münstermann ら 2018）: 解くパスが要り、描き足しのたびに全部を描き直す
  - 連結リスト（Yang ら 2010）: 上限がなく、あふれたときに落ちる断片が決定的でない
  - 不透明の点が足されたら半透明を描き直す: 止まった後の 1 フレームが重い
  - 混ざる誤差を受け入れる: 画が描き足しの順に依り、不変条件 11 に反する
  - 層をまたぐ描き足しで、どの層も WBOIT に通す: 不透明の層の隠し方まで近似になる（Issue #483 の決定 4）
  - 層をまたぐ描き足しを行 K0d の残りとして開けておく: その間、結果が描き足しのフレームの分け方に依り、不変条件 11 に合わない（PR #494 のレビュー）

## メッシュ: 索引つきの三角形、両面の画素ごとの Blinn-Phong、CPU で直す法線（行 K0d）

Decision:
  メッシュは索引つきの三角形のリストで描き、陰影は画素ごとの Blinn-Phong を両面に当てる。法線は CPU で軸ごとの拡大の逆転置をかけて渡し、法線のない入力はワーカーが面積の重みで作る（Issue #483 の決定 3、設計書 §13.5）。

Reason:
  開いた面は裏も見える。軸ごとに拡大が違う（Issue #470 の決定 10）と、位置と同じ変換をかけた法線は歪む。

Rejected:
  - Gouraud: 粗いメッシュでハイライトが崩れる

## 3D の点を GPU に送る形（行 K0a）

Decision:
  八分木の節点（セル）の基準からの 32 ビットの整数を x・y・z で送り、節点ごとの基準と倍率は CPU が倍精度で持って変換に入れる（Issue #470 の決定 12、設計書 §3.6・§13.2）。

Reason:
  行 R3a の常駐の点（セルの中の整数、PR #432）を 3 軸に広げた形で、3D のズームも軸ごとの範囲を変えるので、軸ごとに拡大の度合いが違う画面を守る必要がある。

Rejected:
  - カメラの原点からの float32 の差: 軸ごとに違う拡大で崩れる（行 R3a と同じ理由）

## ボリューム: 3 つの描き方、`R16_UNORM`、CPU が選ぶ段、ずらしのあるレイマーチ（行 K0e）

Decision:
  描き方は要件 K-6 の 3 つ（伝達関数のレイマーチ、断面、等値面）だけで、データは作るときの最小と最大で正規化した `R16_UNORM` で置く。2 倍の平均の段を持ち、CPU が視点と切り取りから、投影したボクセルが 1 画素以下になる段を選ぶ。レイマーチの刻みは 0.5 ボクセルで、ずらしは画素の座標のハッシュで決める（Issue #484 の決定 1〜3、設計書 §13.6）。

Reason:
  512³ の全解像度がちょうど 256 MiB で `R32_FLOAT` の半分になり、刻み 1/65,535 は伝達関数に足りる（Issue #484 の 2026-11-13 の細部のコメント）。等値面は元の値から作るので形式に依らない。選ぶ集合が視点だけで決まり、ずらしが時刻や乱数に依らないので決定的である（不変条件 11、要件 N-7）。

Rejected:
  - `R32_FLOAT` で置く: 同じ解像度で `R16_UNORM` の倍のメモリになる（Issue #484 の決定 1）
  - 最大値投影（maximum intensity projection、MIP）なども足す: 要件 K-6 にない描き方で、`.cursor/rules/scope.mdc` に合わない
  - レイが要るブロックを知らせる方式（Fogal ら 2013）: 頼む集合が前のフレームに依り、決定的でない
  - ずらしを使わない: 年輪の模様が出る

## LOD ピラミッドの構築と置き場所

Decision:
  ピラミッドは列と別のオブジェクト（`MinMaxPyramid<T>`）で、`PlotWorkerPool` がチャンクごとにネイティブメモリに作る。まだできていないチャンクは、チャンクの統計で暫定に答える（設計書 §3.3）。

Reason:
  要件 P-2（8 コアで 1 GB/s 以上、構築中も操作できる）と N-8（UI のスレッドを O(N) で止めない）を、C2 の行で満たして測れる。ピラミッドは元データの約 3.6% なので、データが RAM に載らなくてもピラミッドは載る。
  比べた実装の索引は、ScottPlot 5 の `SegmentedTree` がデータの 2〜4 倍、Perfetto の `ImplicitSegmentForest` が約 2.5 倍である（読んだファイルとコミットは `docs/references.md` の「時系列の間引き（比べた実装、C2）」の行）。

Rejected:
  - ワーカーを後の行にして、C2 は同期の並列構築だけにする: P-2 の「構築中も操作」を C2 で確かめられず、行が 1 つ増える
  - メモリマップの列では、ピラミッドも一時ファイルに写像する: 問い合わせのたびにページを読む。3.6% の RAM を惜しむ理由がない
  - 暫定の経路で、まだないチャンクの統計を計算する: ワーカーがまだ触っていないチャンクを呼び出し側のスレッドで走査し、構築の直後の全体表示でフレームの経路が O(N) になる（Issue #20）
  - バケットごとに 2 ビットの NaN の状態だけを持ち、`Count` は一部が NaN のバケットを生データまで降りて数える: NaN がまばらなデータで `Count` が区間の長さに比例する。数は 1e9 点で約 20.1 MB（設計書 §3.3）で、外す 2 ビットの状態の約 4.5 MB を引いた約 16 MB の増になり、P-8 の内（Issue #20）
  - 構築中の問い合わせで生データを読む（ScottPlot 5 の `SegmentedTree` が木のできる前にすること。`SegmentedTree.cs` の `MinMaxRangeQuery`、`docs/references.md` の同じ行）: 10 億点ではフレームが O(N) になる（不変条件 2）
  - 作り終わるまで問い合わせを待たせる: P-2 の「構築中も操作」に反する
  - ピラミッドを `Column<T>` に持たせる: 列の型がワーカーに依存し、C1 の契約が変わる。同じ列に複数のピラミッドを持てない

## M4 の入出力

Decision:
  画素列の境界を X のデータの単位で W + 1 個受け取り、半開区間で区切る。出力は呼び出し側の `Span` に、位置の順で重複なく書き、表示範囲の直前と直後の要素を足す。NaN は既定で線を切る（設計書 §5.5.1）。

Reason:
  境界を受け取れば、スケールの変換（log・時刻）は逆変換した境界を渡すだけで同じ抽出を使える。範囲の外の点がないと、線が画面の端まで届かない。

Rejected:
  - 論文の式 (2) の round で区切る: 鍵が w + 1 個になり、§4.4 の w 個の組と合わない
  - tsdownsample のように、データの範囲を等分した区切りや、要素の位置を等分した区切り: 表示範囲と描画側の変換に合わない
  - 重複した位置を返す（tsdownsample の M4）: 同じ点を 2 度描く頂点が増える
  - X の列のチャンクの統計を、M4 が初めて読むときに計算する: 1e9 点の X では、最初の 1 フレームが X の全体（`long` で 8 GB）を走査する（不変条件 2）。M4 は計算済みの統計だけを読み、`PlotWorkerPool.PrecomputeStats` が裏で計算する（PR #19）
  - min / max を誤差つきの問い合わせで求める（両端を「s/64 以下」の水準で止め、バケットを中心で含める）: min / max の要素が列の外になることがあり、点が時間の順に並ばない。省けるはずの両端の生データの読み出しは、first / last の読み出しと同じページにあるので、ほとんど省けない（Issue #14）
  - 範囲の内側の点だけを返す（Jugel ら、tsdownsample、plotly-resampler）: 端の列と画面の外をつなぐ線が欠ける
  - 間引いた後の X の間隔から切れ目を推定する（plotly-resampler の `MedDiffGapHandler`）: 推定の閾値で描く線が変わる。HyperPlot は NaN で切る（要件 D-7）

## プロジェクトの分け方

Decision:
  データ・GoG・インタラクション・描画 IR を 1 つの `HyperPlot.Core` に置き、名前空間で分ける。

Reason:
  v1 の間は層の境界がまだ動く。アセンブリをまたぐと internal の最適化（構造体の直接の受け渡し）がしにくい。

Rejected:
  - 最初から `HyperPlot.Data` を別アセンブリにする: 利用者からデータ層だけを使いたいという要求が出たら分ける

## ページキャッシュに載る前の状態の作り方

Decision:
  計測のデータの生成器がファイルをバッファなし（`FILE_FLAG_NO_BUFFERING`）で書き、書いた直後を冷えた状態とする。冷えていることは、ファイルを読む速さで毎回確かめる（設計書 §9、Issue #26）。

Reason:
  管理者権限も再起動もなしに、冷えた状態を何度でも作れる。`bench.mdc` の交互の比較（A, B, B, A）が冷えた状態でもできる。試作では、バッファなしで書いた直後の 1 回目の読みは 1.9〜2.1 GB/s、キャッシュから読む 2 回目は 4.4 GB/s で、見分けられた。

Rejected:
  - スタンバイリストを管理者権限で空にする（RAMMap など）: 計測のたびに昇格かオーナーの操作が要る
  - 再起動の後に測る: 1 回ごとに再起動が要り、交互に何度も測れない

## End-to-end の計測を作る行

Decision:
  行 B1 はデータの経路（`benchmarks/HyperPlot.DataPath`、GPU を使わない）とカーネルの計測だけを作り、`benchmarks/HyperPlot.E2E` は描画が通る行 S1 で作る（Issue #26）。

Reason:
  B1 の時点では描画がなく、E2E の枠を作っても測るものがない（`scope.mdc` の半分だけの機能）。データの経路の場面（構築、暫定が替わるまで、冷えた 1 フレーム）は描画なしで測れる。

Rejected:
  - B1 で E2E の枠も作る: 中身が S1 まで空に近い

## チャンクの統計と水準 1 の走査

Decision:
  ピラミッドの構築は、統計がまだないチャンクで、統計と水準 1 を生データの 1 回の走査で作る（設計書 §3.3、Issue #30）。統計がすでにあるチャンクは水準 1 だけを走査する。

Reason:
  行 B1 の計測（参照機、P コアに固定、L3 に収まらない 64 チャンク、交互に 3 回の最良）で、1 回の走査は別々の 2 回の 0.53〜0.72 倍の時間だった。結果の値は同じで、`Sum` はビットまで同じである（min / max は 0 の符号だけが違いうる）。数は `docs/benchmarks/b1-data-layer.md` にある。

Rejected:
  - 統計を先に計算し、水準 1 を別に走査する（C2 の形）: 2 回目の走査がチャンクを L3 から読み直し、min / max と NaN の判定を 2 度行う
  - 統計がすでにあるチャンクでも 1 回の走査を使う: 水準 1 だけの走査の方が速い

## M4 の first / last を水準 1 のバケットに持つ

Decision:
  持たない。M4 の first / last は、列ごとに境界の要素を生データから読む（設計書 §5.5.1、Issue #30、オーナーの判断 2026-10-28）。

Reason:
  得があるのは、構築の後にページがキャッシュから追い出されたときだけである。そのとき M4 が生データを読む分は、参照機で 1 フレーム約 0.2 s（1e9 点、1,920 列、3,840 ページ、1 回だけ）だった（`docs/benchmarks/b1-data-layer.md`）。追い出しはメモリが足りないときだけ起きる。冷えたファイルを開いた直後のフレームは、ピラミッドがまだないので、この案でも速くならない。

Rejected:
  - 水準 1 のバケットごとに first / last の値を持つ: メモリが元データの約 6.7% 増える（P-8 の内だが、常に払う）。列の間をつなぐ点の y も変わる

## D3D11 のデバイスと喪失（行 R1）

Decision:
  デバイスはプロセスに 1 つ（`D3D11Backend.Shared`）で、テスト用に自分のバックエンドも作れる。喪失は 4 つの HRESULT で検出し、当たった呼び出しは `GpuDeviceLostException` を投げ、次の `BeginFrame` でデバイスと描画先を記述から作り直す。描画先は `B8G8R8A8_UNORM`・前乗算アルファで、sRGB の値をそのまま合成する（設計書 §5.3、Issue #34）。

Reason:
  最初の `D3D11CreateDevice` は XylemUI の計測で 160〜175 ms かかり、図ごとに作るとこれを図の数だけ払う。喪失を黙って直すと、描画先の中身が失われたことが呼び出し側に伝わらない。WPF の `D3DImage` は前乗算の BGRA の sRGB の値をそのまま合成する。

Rejected:
  - 図（ビュー）ごとにデバイスを持つ（XylemUI の形）: 作成の時間とメモリを図の数だけ払う
  - 喪失を中で作り直してやり直し、呼び出し側に見せない: 描き直しが要ることが伝わらない
  - §5.2 の契約を全部いま公開し、まだないものは `NotSupportedException`: 半分だけの機能（`scope.mdc`）
  - `_SRGB` のビューで線形の空間で合成する: WPF の合成と結果が変わる。線の見た目の調整は R2 のシェーダで行う

## `HeadlessRenderer` の置き場所

Decision:
  `HeadlessRenderer` と PNG の書き出しは Core の `HyperPlot.Rendering` に置き、`IGpuBackend` を受け取る（設計書 §7.5、Issue #34、オーナーの判断 2026-10-28）。

Reason:
  使うのは GPU の契約と BCL の `ZLibStream` だけで、バックエンドに固有の readback（D3D11 の staging と `RowPitch`）は描画先の実装の側にある。Metal / wgpu のバックエンドを足すときに書き直さない（要件 N-6）。

Rejected:
  - `D3D11Backend` を受けて `HyperPlot.Rendering.D3D11` に置く: バックエンドごとに同じ型と PNG の書き出しを書くことになる

## `WritePng` の画素の確保

Decision:
  `HeadlessRenderer.WritePng` は、画像 1 枚分の画素（幅 × 高さ × 4 バイト、最大 1 GiB）を読んでから PNG に書く（設計書 §7.5、Issue #38、オーナーの判断 2026-10-28）。

Reason:
  `IRenderTarget.ReadPixels` は画像全体を読む形である。PNG の書き出しはフレームの経路ではなく、普通の画像（4K で約 33 MB）では問題にならない。

Rejected:
  - `IRenderTarget` に行の範囲を読む `ReadPixels` を足し、確保を 1 行と 64 KiB に抑える: 公開の契約が 1 つ増える

## 折れ線のアンチエイリアスと結合（行 R2）

Decision:
  線分ごとの四角形と、カプセル（と破線）までの距離から覆う割合を求めるピクセルシェーダで描く。すべての折れ線は、覆う割合を R8 の中間テクスチャに MAX で合成し、色を 1 回だけ乗せる。結合と端は丸、破線はオン・オフ 1 組、切り抜きはシザー矩形、有限でない点で折れ線を切る（設計書 §5.1・§5.3、Issue #42）。

Reason:
  覆う割合の式は XylemUI と同じで、1 画素より細い線も面積の分だけ薄く描ける。M4 の線は結合がほぼ全画素にあり、線分を直接描くと、半透明の線は二重に濃くなり、不透明の線でも結合の縁のアンチエイリアスの画素が二重に合成される。MAX で合成すると、折れ線は 1 つの形として 1 回だけ塗られる。

Rejected:
  - MSAA（4×）でふつうの三角形として描く: 描画先と中間の層に 4 倍のメモリが要り、R1 の描画先は MSAA なしである
  - POC と同じく太さに対する固定の割合でぼかす（`HighPerfPlotPOC/HighPerfPlot.Core/Shaders/line.frag` 12〜15 行目）: 線の芯が名目の太さより細くなり、細い線では実質ぼけない
  - 線分を直接描き、半透明の重なりを受け入れる（XylemUI の線と線の重なり）: M4 の線が全体に濃くなる
  - 不透明の線だけ直接描く: 結合の縁のアンチエイリアスの画素が二重に合成され、CPU の基準と 1 を超えて違う（Grill の後のオーナーの判断）
  - 線分ごとに隣との二等分線で受け持つ範囲を切る: シェーダが重くなり、全画素が遅くなる
  - 破線を後の行に回す: 要件 R-4 が求めている
  - シェーダの中で距離で切り抜く（XylemUI の形）: プロットのパネルは軸に沿った整数の矩形で、シザーで足りる
  - NaN の点を例外にし、切れ目を別の引数で渡す: M4 の結果と利用者の点で、切れ目の渡し方が 2 つになる

## 系列ごとの M4 の並列（行 S1）

Decision:
  公開の `M4Batch` に系列を 1 度登録し、`PlotWorkerPool.Extract` が系列ごとの仕事をワーカーに配って全部の終わりを待つ。フレームの仕事はチャンクの構築より先に取り、呼び出し側も仕事を取る。例外は全部が終わった後、最も小さい番号の失敗をそのまま投げ直す（設計書 §5.5.1・§8.1、Issue #50）。

Reason:
  設計 §8.1 の「事前に確保した仕事の構造体で fork-join」を、フレームで確保しない形にする。呼び出し側も仕事を取るので、ワーカーがチャンクの構築でふさがっていても、待つのは構築中のチャンク 1 つ分までである。

Rejected:
  - 呼び出し側が `Parallel.For` などで並べる: 確保が起き、プールと別のスレッドが動く
  - 並列にせず、系列を順に抽出する: 系列の数だけフレームの CPU の時間が伸びる
  - 1 系列を画素列の範囲でも分ける（S1 では）: 範囲の外の点（`Before` / `After`）と出力の順が絡む。要るかは行 S2 の計測で決める
  - 構築とフレームの仕事を区別せず順に取る: フレームが、積まれたチャンクの構築を待つ
  - すべての例外を `AggregateException` にまとめる: フレームの経路で確保する

## S1 のサンプルと行の分け方

Decision:
  行 S1 をサンプル・NativeAOT の検査・系列ごとの並列にし、End-to-end の計測と GPU 時間を行 S2、ゴールデン画像と `HyperPlot.Testing` を行 S3 に分ける。サンプルは `HelloPlot`（1e6 点、NativeAOT と P-10）と `BillionSeries`（1e9 点のメモリマップ）の 2 つで、データの線と格子の線だけを描く。値から画素への変換は、サンプルのコードが倍精度で行う。`RenderList` は物理画素しか受けず、`SetTransform` は行 G1 で足すためである（Issue #50）。（その後、`SetTransform` は Issue #76 で行 G4 へ移った。行 G1 の線は CPU が画素まで計算するので使わない）

Reason:
  6 つの仕事はどれも 1 つの PR になる大きさで、S2 は S1 のサンプルの場面を測り、S3 は S1 の画像を基準にする。NativeAOT の検査は数秒で終わる小さなサンプルで回したい。

Rejected:
  - S1 を 1 つの PR で作る: レビューの範囲が大きすぎる
  - `HelloPlot` 1 つにファイルの引数を持たせて兼ねる: NativeAOT の検査に 4 GB のファイルの生成が絡む
  - 軸の目盛りの数字をサンプルの中で描く: 文字の描画（行 T1）がまだない。ライブラリに中途半端なスケールの API も足さない

## End-to-end の計測と GPU 時間（行 S2）

Decision:
  `benchmarks/HyperPlot.E2E` は表示の範囲の列を台本どおりに流し、P-1 は 1 系列で判定する。GPU 時間は公開の `IGpuBackend.LastFrameTime`（4 フレームの輪、待たずに読む）で、`BeginFrame` / `EndFrame` は入れ子にできる。P-1 を満たさなければ、内訳を測ってオーナーに選択肢を出す（設計書 §5.2・§5.3・§9、Issue #58）。

Reason:
  入力のモデル（I1）とホバー（I2）はまだないが、P-1 のズームとパンは表示の範囲の列で表せる。要件 P-1 は 1 本の時系列を指している。GPU 時間は S2 の E2E のあとも、ホストと利用者の診断に要る。同じフレームで待つと GPU のクロックが下がる（R2 の計測）。

Rejected:
  - 入力のモデルの簡易版を S2 で作り、ホバーも流す: I1・I2 の設計を先取りする
  - 複数の系列で P-1 を判定し、要件の文を直す: 要件は 1 本の時系列を指している。複数は参考として記録する
  - GPU 時間を公開せず、E2E の中だけで internal に測る: ホストと利用者がフレームの GPU 時間を見る手段がなくなる
  - P-1 を満たさなかったら S2 の中で速くする: 設計に関わる直しをオーナーの判断なしに入れることになる
  - `BeginFrame` / `EndFrame` の組で、対応のない `EndFrame` を `InvalidOperationException` にする（最初の設計）: 同じ型の違う段階で呼んだから投げる形で（`csharp.mdc`）、例外の後に閉じ忘れると入れ子が残る。`FrameScope` を返して `using` で閉じる形にした（オーナーの判断、PR #59 のレビュー）

## 1 系列を画素列の範囲で分けない（行 S2）

Decision:
  `M4Batch` は系列を 1 つの仕事にし、系列が少なくてコアが余るときも、1 系列を画素列の範囲で分けない（設計書 §5.5.1、Issue #62、オーナーの判断 2026-10-29）。

Reason:
  1e9 点の 1 系列で、フレームの CPU の p95 は 4.4〜5.8 ms で、P-1 の 8 ms まで 2 ms 以上の余裕がある。p95 を決めるのは 1e8 点より広い表示の抽出（p95 5〜7 ms）で、分ければ縮む見込みはあるが、仕事の分け方と結果のつなぎ目の扱いが増える（`docs/benchmarks/s2-e2e.md`）。

Rejected:
  - 系列が少ないとき、1 系列を画素列の範囲でワーカーに分ける: P-1 の内で、得るものが要件にない。系列が多い場面（16 系列で p95 12〜13 ms）にも効かない

## ゴールデン画像の比較と `HyperPlot.Testing`（行 S3）

Decision:
  `HyperPlot.Testing` に公開の `GoldenImage`（比べる・合わなければ投げる）と `ImageTolerance` を置き、xUnit に依らない。画素ごとの各チャネルの許容差と、それを超えてよい画素の数で比べる。基準はテストのプロジェクトの `Golden/*.png` に git で持ち、`HYPERPLOT_UPDATE_GOLDEN=1` のときだけ書き直す。場面は `HelloPlot` の場面（1e5 点）と、R2 の線の種類を並べた 1 枚。PNG は Testing の internal の復号器で読む（設計書 §10.1、Issue #66）。

Reason:
  ゴールデン画像の役目は、記録から readback までの経路全体の、知らないうちの変化を見つけることで、線の画素の正しさは R2 の CPU の基準がすでに見ている。設計書 §2.1 は Testing を利用者のテストも使うものとしている。全体の値は、線の切れや端の 1 画素の崩れを、画像全体に埋もれさせる。基準を書く PNG は自前の書き手で、読むのはその形だけでよい。

Rejected:
  - R2 の各ケースも画像で持つ: CPU の基準との比較と重なり、基準の画像の数だけ更新の手間が増える
  - 比較をテストの中の internal な補助にとどめる: 設計書 §2.1 の「利用者のテストが使う」に合わない
  - 平均の差や PSNR で比べる: 小さな場所の崩れが全体の値に埋もれる
  - ImageSharp などの外部の画像ライブラリで読む: 読むのは自前の書き手の 1 つの形だけで、依存を足す理由がない（`.cursor/rules/dependencies.mdc`）
  - `WalkFile` のランダムウォークで新しい場面を作る（Grill の Q7 の推奨の文）: `HelloPlot` の中身の取り違えで、`HelloPlot` と同じ場面を共有するほうが、サンプルの画像の変化も見つけられる（オーナーの確認、2026-10-29）

## 行 G1 の範囲: 描ける線のプロットまで（行 G1）

Decision:
  行 G1 の終わりに、`DataTable` の列から線のプロットを宣言し、`HeadlessRenderer.Render(PlotSpec)` で描けるところまで作る。位置のスケールは linear（domain の明示と学習）だけを G1 に入れる。仕様の型は G1 が実装する分だけを、init のプロパティで持つ。`SpecId` と新旧の比較（要件 G-13）は G1 で作る。`SetTransform` は、それを最初に使う Geom の行 G4 へ移す（設計書 §4.1・§4.8・§5.1、Issue #76）。

Reason:
  仕様とコンパイルだけでは利用者は何も描けず、`scope.mdc` の「半分だけ出す機能」になる。§4.1 の全メンバーを先に置くと、まだない部分を公開することになる。G1 の線は M4 の経路で、CPU が倍精度で画素まで計算するので（§3.6）、`SetTransform` を使うものが G1 にない。比較の仕組みは、仕様の型の形と一緒に作らないと合わなくなる。

Rejected:
  - 仕様のモデルとコンパイルだけを作り、描画は G2 以降でつなぐ: G1 の終わりに何も描けない
  - G2 のスケールをすべて G1 に入れる: G1 が大きくなりすぎ、目盛りと組の nice まで入る
  - §4.1 の全メンバーを先に置き、まだないものは例外にする: まだない部分を公開する（`scope.mdc`）
  - ホストとヘッドレスが共有する公開のランタイムの型を G1 で作る: ホストの形は W1（W1a）と I1 で、使う側と一緒に決める
  - `SetTransform` を G1 に入れ、テストだけで使う: 使う側のない契約になる
  - 変わった部分だけの再計算を、仕様が出そろう後の行にまとめる: 比較の仕組みが仕様の型の形に合わなくなる
  - `SpecId` を持たず、参照の同一性で比べる: 設計書 §4.1 の「仕様の各ノードは同一性を持つ」とずれ、ホストとツールが仕様のノードを指す手段がなくなる

## スケールの空間の精度: 原点と差（行 D2）

Decision:
  スケールの空間の値は、CPU では `long` の原点と `double` の差の組で扱う。原点は範囲の下端の整数部で、ビューが変わるたびに付け直す。X と Y の両方に使う。M4 は必須の引数 `ScaleOrigin(long X, long Y)` を受け、境界と出力の点は原点からの差で書く。`long` の列は `Int128` の正確な差を 1 回だけ `double` に丸める。整数の等間隔の列 `Column.UniformInteger` を足す。日時の `long` の単位と起点は time のスケールが持ち、既定は .NET のティック（設計書 §3.1・§3.6・§4.2・§5.5.1・§6.2、Issue #11、オーナーの決定 2026-10-29）。

Reason:
  2026 年の .NET のティック（約 6.39e17）の `double` の 1 ulp は 128 ティック（12.8 µs）で、幅 1,920 画素なら表示範囲が約 24.6 ms より狭いと画素列の境界が増加しない（要件 R-6）。原点からの差なら、`double` の 53 ビットがビューの中の位置に使われ、M4 の形は変わらず、追加の仕事は値ごとの引き算 1 回である。GPU に原点からの差を送る §3.6 の方式と同じ考え方で、CPU と GPU で原点の扱いが揃う。

Rejected:
  - 128 ビットの固定小数点（`Int128`）でスケールの空間を表す: M4 の二分探索の比較と画素への写像のすべてが 128 ビットになり、フレームの経路を重くする。原点と差で足りる精度に、それだけの費用を払う理由がない
  - `double` のままにして、精度の限界を要件 R-6 の但し書きに書く: µs や ns の計測データを深くズームできず、R-6 を満たさない
  - 原点を列の型で持つ（`long` の列は `long`、`double` の列は `double`）: M4 の引数の型が列ごとに変わり、規則が 2 つになる。`double` の列の値は、整数の原点からの差でも同じ精度で表せる
  - 原点をデータの domain の始まりに固定する: データの幅が 2^53 単位（.NET のティックで約 28.5 年）を超えると、終わりのほうで差がまた丸まる。ビューごとに付け直せば、差は常に小さい
  - 原点を X だけに使い、Y は `double` のままにする: 日時を Y に置く場合や、大きな `long` のカウンタを深くズームする場合も、同じように崩れる。要件 R-6 は軸を限らない
  - 原点を `M4Options` に入れ、既定を (0, 0) にする: 日時の列を原点なしで渡しても黙って精度を落とす。`M4Options` は「どう抜き出すか」の設定で、「どの座標で答えるか」とは別である
  - 整数の等間隔の列を `Column.Uniform(long start, ...)` の多重定義にする: `Column.Uniform(0, 1, n)` のような整数の引数が `long` 版に解決され、今の呼び出しの意味が変わる（スクラッチでコンパイルして確かめた）
  - 整数の列の正確な値を、`IsInteger` が偽なら `InvalidOperationException` を投げる `long` のプロパティで読ませる（PR #86 のレビューの例）: 型の種類の取り違えで公開のメソッドが投げる（`.cursor/rules/csharp.mdc`）。`TryGetInteger(out long start, out long step)` は投げずに同じ値を返す
  - 等間隔の日時を `Column<long>` に値を入れて持つ: 1e9 点で 8 GB を余分に払い、要件 D-5（値を持たない等間隔の列）を日時で使えない
  - コンパイルの中の domain を `double` のままにし、境界を作るときだけ原点を引く: `long` の列の学習した端が最大 64 ティック丸まり、データの最初と最後の点が画面の端からずれる
  - 日時の `long` を .NET のティックに固定し、要件 G-10 の「ナノ秒」を外す: 計測機器・Arrow・numpy の ns の Unix 起点の列を描けない

## 行 G2 の範囲と位置のスケール（行 G2）

Decision:
  行 G2 は位置のスケールに絞る: linear の zero・reverse・clamp、log・symlog・sqrt・power・time（単位と起点）、変換を足す口 `IScale`。色とカテゴリのスケール（band・point・ordinal・sequential・diverging）、名前つきの色とパレット、列で色を分けるチャネル、`CategoricalColumn` は新しい行 G7 に分け、G4 の後に置く。目盛りと nice は行 G3 で軸と一緒に作る。`IScale` は値の列をまとめて変換する `Forward` と `Inverse` を持ち、狭義に単調増加を契約にする（設計書 §4.1・§4.2・§4.6、Issue #94、オーナーの決定 2026-10-29）。

Reason:
  band と point のスケールは、それを使う Geom（bar・point、行 G4）がないと試せず、色分けは凡例（行 G3）がないと読めない。`CategoricalColumn` を作る行がなかったので、それを使う行にまとめた。目盛りの選び方は文字の幅を使うので（§4.6）、テキストの計測（行 T1）と軸の配置（行 G3）なしでは決まらず、G2 で作ると使う側のない関数になる。nice は目盛りの刻みの端まで domain を広げることなので、目盛りと同じ行にする。位置のスケールは、今の線のプロットにそのまま効き、画素で確かめられる。まとめて変換すれば、仮想呼び出しはレイヤーごとに数回で済み、点ごとに呼ばない（§4.1）。

Rejected:
  - 行 G2 のまま、色とカテゴリと目盛りまで全部を作る: band・point・色の凡例・目盛りのラベルを、使う側（G4・G3・T1）より先に作ることになる
  - 色の行を G2 の直後（T1 の前）に置く: 線の色分けはすぐ使えるが、凡例がなく、どの色がどの値かを画像から読めない
  - 目盛りを G2 で、文字の幅を使わない版（数を指定）として作り、G3 で文字の幅を足す: 軸がないので使う側のない内部の関数になる
  - nice を G2 で、目盛りの数を固定した刻みで作る: G3 の目盛りは文字の幅で別の刻みを選びうるので、domain の端が目盛りに乗らないことがある
  - `IScale` を値 1 つずつの変換にする: 点ごとに仮想呼び出しになる
  - `IScale` を G2 で公開しない: 要件 N-6（足せること）を満たさない
  - 非線形のスケールで原点を使わない: ビュー範囲と境界の扱いがスケールの種類で分かれる。データを原点 0 で読み、変換した後の空間で原点と差を取れば、全部のスケールで同じ扱いになる
  - log の 0 以下の値のために、チャンクの統計に「正の最小値」を足す: 統計のカーネルとメモリが増える。今の統計で学習でき、0 以下の端は ±∞ と同じく `WithDomain` で明示する道を残す。0 をまたぐデータには symlog がある
  - 0 以下の値がある log をいつも例外にする: 明示の domain で 0 以下の値を欠損として描く使い方を閉ざす
  - time の単位を `TimeSpan` の刻みで受ける: `TimeSpan` は ns を表せない
  - zero の既定を真にする: 時系列の線では 0 を含めないのがふつうで、今の G1 の描画が変わる
  - zero・reverse・clamp を linear だけに持たせる: log の軸の反転や、time の外れ値を端に寄せる使い方を閉ざす
  - symlog を自然対数（log1p）にする: log の空間（log10）と値の大きさがそろわない
  - power の負の値を欠損にする: 0 をまたぐデータで線が切れる
  - 有限でない変換の結果の扱いをスケールごとに決める: 利用者が足すスケールに当てはまる規則がなくなる
  - 利用者のスケールを `ScaleSpec` の派生の record で足す: コンパイルは知らない派生を拒む（§4.8）。口を `IScale` 1 つにすれば、検査を変えずに済む

## テキスト: 描くときに整形し、DirectWrite の配置とコールバックで受け取る（行 T1）

Decision:
  行 T1 は、文字列を描いて測れる公開の口（`RenderList.DrawText`・`HeadlessRenderer.MeasureText`）と、バックエンドが実装する契約 `ITextBackend`（整形・グリフの寸法・ラスタライズ）を出す。`RenderList` は文字列とスタイルを記録し、描くときにバックエンドが整形して、Core のアトラス（2,048 × 2,048 の 8 ビットの頁、最大 8 頁）に載せる。グリフの横の位置は 1/4 画素の 4 段で、回転は 0° と ±90°。D3D11 は `IDWriteTextLayout` と自前の `IDWriteTextRenderer` で整形し、`IDWriteFactory3::CreateGlyphRunAnalysis`（グレースケール、`NATURAL_SYMMETRIC`、グリッドフィットなし、`ALIASED_1x1`）でラスタライズする。テストは、偽のバックエンドで画素まで、DirectWrite は性質で確かめる（設計書 §5.1・§5.2・§5.3・§5.6・§7.5、Issue #103、オーナーの決定 2026-10-30）。

Reason:
  T1 の時点でテキストを使うライブラリの部品はない（軸は G3）ので、利用者が描けて測れる口を出さないと、使う側のない機能になる。`RenderList` はどのバックエンドとも独立した命令の列で、記録のときに整形すると、それが崩れる。DirectWrite の画素は Windows の版で変わりうるので、ゴールデン画像にすると OS の更新のたびに基準を書き直すことになる。配置とコールバックの道は、コールバックのオブジェクトが 1 つで済み、日本語のフォールバックと双方向の文字を DirectWrite の処理に任せられる。1/4 画素の段は、字の間隔を整えたまま、にじませない。

Rejected:
  - 契約とアトラスを internal にとどめ、G3 まで公開しない: T1 の終わりに使う側がなく、`scope.mdc` の「半分だけ出す機能」になる
  - 記録のときにグリフの並びにして記録する: `RenderList` が `ITextBackend` を持つことになり、バックエンドから独立した命令の列でなくなる
  - DirectWrite の画素もゴールデン画像にし、許容差を CI と手元の差から決める: OS の更新で画素が変わるたびに基準を書き直すことになり、本当の変化と区別できない。許容差の広さも決められない
  - 任意の角度の回転: 回したグリフは補間でぼける。G3 の y 軸のタイトルに要るのは ±90° だけ
  - 回転を G3 に送る: G3 で要る形が決まっているので、テキストの行で作る方が試しやすい
  - フォントを解決済みの型（`FontFace`）で受ける: 記録がバックエンドを知ることになる（名前で受ければ知らないまま）
  - 1 行だけにし、改行を含む文字列を例外にする: G3 のタイトルや凡例に複数行が要りうる
  - アトラスを 1 頁に固定し、あふれたグリフを描かない: 大量の注記で黙って字を落とす
  - グリフの横の位置を整数の画素に丸める: 字の間隔が最大 0.5 画素ずれる
  - 小数の位置のまま補間して描く: 字がぼける
  - 計測を `RenderList` に置く: `RenderList` がバックエンドを知ることになる
  - 受け入れを画素の一致と確保だけにする: 目盛りのラベルはズーム中に毎フレーム変わるので、フレームの経路の時間を測る必要がある
  - `IDWriteTextAnalyzer` と `IDWriteFontFallback::MapCharacters` で自前に整形する: コールバックのオブジェクトが 2 つ要り、文字の種類の分割・フォールバックの区切り・改行・位置の計算も自前になる
  - `IDWriteFactory2`（Windows 8.1）でラスタライズする: 要件の対応範囲（Windows 10 1809 以降）より古い OS のための道で、得るものがない
  - グリッドフィットを有効にする: 小さい字はくっきりするが、1/4 画素の段が効かないおそれがある
  - `IGpuBackend.Text` を `ITextBackend` そのものにし、`HeadlessRenderer` が自分の整形のキャッシュを持つ: 計測と描画で同じ文字列を 2 度整形し、フェイスの番号がバックエンドごとなのに、キャッシュの持ち主が描画の側と分かれる。Core の `TextEngine` がバックエンドごとにキャッシュとアトラスを持つ形にした（PR #105 のレビュー、オーナーの決定 2026-10-30）
  - 整形のロケールを "ja-jp" か "en-us" に固定する: DirectWrite のフォールバックは漢字に当てるフォントをロケールで選ぶので、どちらに固定しても、日本語か中国語のどちらかで別の言語のフォントが当たる。OS のカルチャは `InvariantGlobalization` で読めないので、`TextStyle.Locale` で利用者が渡す（PR #105 のレビュー、オーナーの決定 2026-10-30）

## ガイドと配置: 軸の設定はスケールに、目標は密度で、ズーム中の確保 0 は I1 へ（行 G3）

Decision:
  行 G3 は、x（下）と y（左）の軸、プロットのタイトル、線のレイヤーの離散の凡例（パネルの右）、配置、テーマ（`Theme.Light`・`Theme.Dark`）、nice、行 G2 の 6 種のスケールの目盛りと書式を作る。軸のタイトル・nice・書式はスケールに持つ（`WithTitle`）。長さは DIP で、`HeadlessRenderer` の倍率を掛ける。linear の目盛りは Talbot ら 2010 の拡張アルゴリズムで、目標は密度（テーマの DIP の間隔）、legibility は重なりの項だけ、ラベルの範囲は nice で分ける。log は 10 の冪、time は暦の段。書式は確保しない `TryFormat` の形だけ。パネルの背景のために `RenderList.DrawRect` を作る。新しいラベルで確保しないことは行 I1 で作る（設計書 §4.1・§4.6・§4.7・§4.8・§5.1・§5.3・§7.5、Issue #111、オーナーの決定 2026-10-30）。

Reason:
  軸の中身はスケールの種類（数か日時か）で決まり、スケールと軸は 1 対 1 なので、設定をスケールに持てば組み合わせの検査が要らない。論文の拡張アルゴリズムは目盛りの数でなく密度を入力にし、密度の項は文字の長さを見ない（§4.3・§7）ので、文字の幅から目標の数を作ると、ラベルがほぼ触れ合うまで目盛りが詰まる。HyperPlot は domain の外に目盛りを描けないので、端のラベルが内にも外にも出る論文の形はそのままでは使えない。ズームはまだなく、新しいラベルで確保しないには `ITextBackend` の契約（T1 で公開した）を変える必要があるので、ズームとその計測を作る I1 で、測りながら作る。パネルの色をテーマに持つには、矩形を塗る命令が要る。

Rejected:
  - `PlotSpec` に別の軸の仕様（`AxisX`・`AxisY`）を持つ: スケールと軸の組み合わせの検査（日時の書式を数のスケールに付けるなど）が要る
  - `Func<double, string>` の書式も持つ: 新しいラベルのたびに文字列を作らせる形で、口が 2 つになる
  - 行 G3 で、span を受ける `DrawText` と確保しない整形まで作る: ズームがなく、確保 0 の場面を測れない
  - 目標の目盛りの数を、軸の長さを「ラベルの幅 + 最小の間隔」で割って決める: 論文の入力は密度で、この数では目盛りが詰まりすぎる（Grill の Q14 の案、Q16 で替えた）
  - 論文の legibility の 4 項（書式・文字の大きさ・向き・重なり）をすべて使う: HyperPlot は書式を 1 つに決め、大きさと向きを変えないので、3 項はいつも同じ値になる
  - 論文の重みを §5 の疑似コードの値（simplicity 0.2・coverage 0.25）にする: §4 の本文が勧める値と違い、論文はその違いに触れない。本文の値を使う
  - 端のラベルが domain の内にも外にも出る論文の形（§3.1）をそのまま使う: domain の外の目盛りは描けず、nice の真偽で範囲を分ければ両方の使い方が残る
  - nice を既定で真にする: 時系列の x が、データのない範囲まで広がる
  - 日時の軸の端に、別の行で日付を出す（matplotlib の `ConciseDateFormatter` の offset）: 配置に 1 行増える。目盛りごとに乗る境の書式を選べば、日付の手がかりが出る
  - パネルの色をテーマから外す（`DrawRect` を作らない）: Grill で決めたテーマの中身を削ることになる
  - 太い線でパネルを塗る: 線の端は丸く（§5.1）、矩形にならない
  - 小さすぎる描画先で例外を投げる: ホストがウィンドウを小さくしただけで投げる
  - 凡例やタイトルを順に省いてパネルを残す: どこまで省くかの規則が増える
  - 凡例の置き場所を選べるようにする（上・下・左）: 要件 G-10 は置き場所を求めず、G3 の配置の順（§4.6）で右に置けば足りる
  - `HelloPlot` を `PlotSpec` に書き直す: ゴールデン画像の場面（§10.1 の (1)）を共有していて、基準が変わる

## Geom: 数の列の 8 つに絞り、CPU で写し、並びのないものは画素の数で抑える（行 G4）

Decision:
  行 G4 は、step・area・band・bar（数の x）・rect・rule・segment・errorbar と、Geom を足す口 `IGeom`（`CustomLayerSpec`）を作る。どれも CPU が倍精度で画素まで写す（座標系の cartesian の 4×4 は Core の internal の型）。x が並ぶ Geom は、見える要素が 4W を超えたらピラミッドで画素列ごとにまとめ、並びのない segment と rect は要素の総数が 131,072 以下のときだけ描く（PR #121 のレビューで、パネルの大きさに依る W × H / 16 から定数に替えた）。area と band は画素列ごとの台形の命令 `DrawColumns` で塗る。多数の線は NaN で区切った 1 本の折れ線にする。point は R3、text の Geom は G8、image は G9、線の結合・端・破線は R4、座標系の公開の契約は G10、GPU の `SetTransform` は R3 に移す（設計書 §4.1・§4.2・§4.4・§4.8・§5.1・§5.3・§5.5.3、Issue #120、オーナーの決定 2026-10-30）。

Reason:
  要件 R-1 と不変条件 2 は、1 フレームの転送と走査を画素の数で抑える。散布の点は GPU に置き続けないと抑えられず、その仕組みは R3 にある。GPU で写す利点は、データを GPU に置き続けるときにしか出ない。x が並ぶ Geom は、線と同じピラミッドで画素列ごとにまとめられる。並びのない要素は見えるものを数えるにも全走査が要るので、総数で抑える。W × H では 1,920 × 1,080 で 1 フレーム約 66 MB を送り、R-1 の「数 MB 以下」を破る。

Rejected:
  - 10 の Geom を全部 G4 で作る: point は常駐、text は文字列の列、image はラスタの型、カテゴリの bar は band のスケールがなく、半分だけ出す機能になる
  - G4 で GPU の常駐のバッファと `SetTransform` を作る: R3 の常駐の仕組みを先に別の形で作ることになる
  - segment と rect の見える要素を数える: 毎フレーム全要素の走査で、不変条件 2 を破る
  - segment と rect の上限を W × H にする: 1 フレームの転送が R-1 の「数 MB 以下」を超える
  - segment と rect の上限を W × H / 16 にする: パネルの大きさに依り、ウィンドウを縮めただけで投げる（行 G3 の小さい描画先の扱いと逆）。R-1 は量の条件なので定数で守れる
  - 多数の線を 1 本ずつの折れ線にする: 描画の呼び出しが線の数の 3 倍になる
  - area と band を画素列ごとの矩形で塗る: 斜めの縁が 1 画素の階段になる
  - bar の幅の既定を隣り合う x の差の最小にする: 保存された列で全要素の走査が要る
  - 座標系の公開の契約を G4 で出す: 使う側（flip・polar）がなく、使われない型になる

## 線の結合と端: 丸でない線は 32 点の覆いの和集合で塗る（行 R4）

Decision:
  `LineStyle` に `Join`（`Round`・`Miter`・`Bevel`）・`Cap`（`Round`・`Butt`・`Square`）・`MiterLimit`（既定 4）を足し、`LineDash` は最大 8 区間をインラインで持つ。既定は丸で、行 R2 の距離の式とシェーダのまま描く。丸でない線は、形を部品（平らに切れた線分の長方形、結合の三角形と四角形、端）の和集合とし、被覆の段で部品ごとに画素の中の 32 点の内側を判定して `R32_UINT` の中間テクスチャに `InterlockedOr` で足し、色の段で立ったビットの数 / 32 を被覆にする（設計書 §5.1・§5.3、Issue #128、オーナーの決定 2026-10-30）。

Reason:
  部品の和集合を点の単位で正確に作れるので、部品が辺で接する所に筋が出ず、鋭い角・短い線分の連続・自分と重なる線でも形が外れない。CPU の試作で、真の面積との差は 0.08 以内だった。丸の線は R2 のまま変えないので、丸の線の時間と画素は変わらない。

Rejected:
  - 部品ごとの被覆を距離の式（R2）で求め、最大値で合わせる（Grill の Q3・Q5・Q11 で一度決めた形）: 線分の長方形は結合の点で平らに切れ、結合の部品とは辺で接するだけなので、その辺にかかる画素の被覆が両方とも半分ほどになり、最大値でも半分のまま残る。太さ 6 画素の 30° の結合で、真の面積との差 0.32（線の内側の筋）
  - 各線分が隣の領域まで伸びて重なる凸の形（半平面の交わり）にし、距離の式で塗る: 90° までの角と直線では差 0.13 以内（尖った角の近くだけ）だったが、90° を超える角と短い線分の連続で形が外れた（差 1.0）。直す形が閉じていない
  - 線分ごとに隣との二等分線で受け持つ範囲を切る: 行 R2 で、全画素が遅くなるとして退けた形。短い線分が続くと、二等分線が線の太さの中で交わり、受け持つ線分のない画素が出る
  - 破線の区間を配列か別のクラスで持つ: 確保が要り、等しさが参照になって、§4.8 の差分が区間の変更を見落とす
  - 中間テクスチャを MSAA（4× か 8×）にして、部品の判定を `SV_Coverage` で書き、ハードウェアの点の和を被覆にする: 段が 5 か 9 で 32 点より粗く、16× はどの GPU でも使えるとは限らない。点の数ごとに中間テクスチャの大きさが増え、被覆を読むのに解決（resolve）の段が要る
  - 画素ごとに部品の和集合の面積を多角形の切り抜きで正確に求める: 重なる部品の和集合の面積は部品ごとの面積の和にならず、1 つの画素にかかる部品をすべて集めて切り抜き合う必要がある。線分ごとのインスタンスでは、ほかの部品が見えない
  - CPU で輪郭を多角形にして塗る: 行 R2 の線分のインスタンスと別の、多角形を塗る部品が要る。M4 の線はほぼ画素ごとに結合があり、輪郭の計算が点の数に比例して CPU に乗る

## 座標系: flip は記録の段で入れ替え、polar は別の行、4×4 の公開は R3（行 G10）

Decision:
  行 G10 は、公開の仕様 `CoordSpec`（`PlotSpec.Coord`）と cartesian の flip を作る。Geom は「沿う向き × 横切る向き」の座標で flip によらず計算し、記録の段で横と縦を入れ替える（折れ線と矩形は CPU で点を、台形は `DrawColumns` の `ColumnAxis.Horizontal` で）。flip では M4 と画素列ごとの Geom が画素行ごとになる。polar は新しい行 G11、4×4 の変換の公開の契約は R3 の `SetTransform` と一緒（設計書 §4.1・§4.4・§4.6・§5.1、Issue #136、オーナーの決定 2026-10-30）。

Reason:
  flip は今の道の横と縦を入れ替えるだけで、Geom の計算と大きなデータの道を 1 通りのまま保てる。polar は扇形の塗り、角度と半径の目盛り、円のグリッドと、今の部品で描けないものが多い。変換を受け取る公開の使い手は R3 まで現れない。

Rejected:
  - flip と polar を G10 で作る: polar の新しい部品（扇形の塗り、角度の軸）が大きく、flip の出荷が遅れる
  - flip の Geom を画素行の版として書き分ける: 同じ計算を Geom ごとに 2 通り持つことになる
  - 4×4 の変換の型を G10 で公開する: 使う公開の口がなく、使われない型になる（G4 と同じ理由）
  - `GeomFrame.Map` を `double` と `long` の組み合わせで多重定義する: 4 つに増える。`long` は軸ごとの口で正確に写せる

## カテゴリ: band だけを作り、使われないカテゴリも出し、カテゴリごとの最小・最大で描く（行 G7b）

Decision:
  行 G7b は、カテゴリの列 `CategoricalColumn`（番号と名前の並び、名前の昇順が既定）、band のスケール（Vega-Lite の bar の余白、d3 の band の意味）、カテゴリの x の bar を作る。軸には列のカテゴリの並びを全部出し、1 つのカテゴリに複数の行があれば、カテゴリごとに根元から最大と最小までの棒を描く。最小と最大はワーカーが版ごとに作る（設計書 §3.1・§4.2・§5.5.3、Issue #159、オーナーの決定 2026-10-31）。

Reason:
  band の写像と棒の幅は d3 と Vega-Lite と同じ意味にして、使い手の知っている形にする。カテゴリごとの最小・最大なら、フレームの仕事がカテゴリの数（画素より多ければ画素）で抑えられ、行の数によらない（要件 R-1）。

Rejected:
  - point のスケールを G7b で作る: 使う Geom（散布の point）は行 R3 で、G7b では使い手がない。カテゴリの x の line・step を作れば使えるが、番号の並びは単調でなく M4 を使えないので、別の大きなデータの道が要る。行 R3 に送った
  - 使われないカテゴリを落とす（ggplot2 の `drop = TRUE`）: 使われているかを知るには、版ごとにデータを O(N) なめる。並びを与えて列を作り直せば落とせる
  - 画素より多いカテゴリを、カテゴリごとの最小・最大の並び（n 個）を毎フレーム読んでまとめる: フレームの仕事がカテゴリの数で増える（PR #160 のレビュー）。並びの上にピラミッドを作り、画素列ごとの区間を水準から引く
  - 行を 1 本ずつ重ねて描く: フレームの仕事が行の数で増える。半透明の塗りでは重なりの濃さが違うが、数の x の bar の 4W を超えた道と同じ扱いにした
  - カテゴリの x の errorbar・rule を G7b で作る: 並べ（dodge）と一緒に行 G5a に送った

## 色: 仕様の色は null で「指定していない」を持ち、層の位置でパレットの色を当てる（行 G7a）

Decision:
  仕様の線を `StrokeSpec`（色が `Color?`）に、塗りを `Color?` にし、null をテーマのパレットの色としてコンパイルで決める。i 番目の層の色は `Theme.Palette[i mod Count]`。既定のパレットは tab10（設計書 §4.1・§4.7、Issue #153、オーナーの決定 2026-10-31）。

Reason:
  今の仕様は色を必ず持ち（線は黒、塗りは半透明の黒）、テーマの色を当てる場所がない。null なら、描画の型 `LineStyle` に仕様の意味を持ち込まずに済む。層の位置で当てれば、ある層の色を指定しても外しても、ほかの層の色と記録が変わらない。

Rejected:
  - `Color` か `LineStyle` に「自動」の値を持たせる: 透明や黒と区別できず、描画の型（§5.1）に仕様の意味が漏れる
  - 色を指定していない層だけで数える（matplotlib の色の巡回と同じ考え）: ある層の色を指定すると、後ろの層の色がずれる
  - G7 を 1 行のまま作る: 仕様・データ層・スケール・ガイド・記録のすべてに触れる PR になり、レビューとミュータントの確認が 1 回で回らない。G7a（色とパレット）・G7b（カテゴリの列と band・point）・G7c（色を分けるチャネルと色のスケールとカラーバー）に分けた

## 座標系: polar は伸ばした空間で M4 と今の Geom を使い、記録の段で写す（行 G11）

Decision:
  行 G11 の polar は、x に沿った画素の区切り（theta = x なら外周の長さ L 画素の角度、theta = y なら半径の画素）で M4 を引き、Geom は伸ばした（角度の画素, 半径の画素）の空間で cartesian と同じに計算する。記録の段で CPU が極座標へ写し、折れ線は極座標で線形に補間し、弦とのずれが 0.25 物理画素以下になる数の小片に分け、矩形と台形は公開の命令 `RenderList.DrawSectors`（極座標の台形、32 点の被覆の和集合で 1 回の呼び出しを 1 回だけ塗る）で塗る。仕様は `PolarCoordSpec`（`Theta`・`Start`・`Clockwise`・`InnerRadius`）で、扇の一部と flip との組み合わせは持たない（設計書 §4.1・§4.4・§4.6・§5.1・§5.3、Issue #145、オーナーの決定 2026-10-31）。

Reason:
  画素の区切りは外周でも 1 画素以下なので、M4 が元の線と同じ画素を覆う理由がそのまま成り立ち、1 フレームの仕事と GPU への転送が画素で抑えられる（要件 R-1、`perf.mdc`）。G4 の大きなデータの道と Geom のコードを 1 通りのまま使える（行 G10 の flip と同じ考え）。極座標の台形 1 つで、bar・rect・area・band の塗りが描ける。

Rejected:
  - すべての要素を CPU で写して記録する（行 G10 までの設計の文、1e7 点まで）: 1e7 本の線分で 1 フレームに約 200 MB を GPU に送り、フレームの仕事がデータの量で増える
  - 点と点を弦で結ぶ: 円のグリッドや角度に沿った bar の縁が丸くならず、半径の区切りの中の M4 の点を結ぶ線が輪を横切る
  - 線分を決まった長さ（2 物理画素、ggplot2 の `coord_munch` と同じ考え）で分ける（Grill の決定を PR #146 のレビューで替えた）: M4 の線は区切りごとに横切る向きを往復するので、1,920 × 1,080 で小片が 140 万〜270 万本（1 フレーム 28〜55 MB）になる。弦とのずれは曲がりで決まり、M4 の線分はほとんど曲がらない
  - 極座標の台形を台形ごとに合成する（`DrawColumns` と同じ）: 台形の境が画素の境に乗らず、境の画素が 2 つの台形に分かれて合成後のアルファが 1 − ab になり、塗りの中に放射線の筋が出る
  - 極座標の台形を外接矩形で描く（行 G11 の実装の PR で替えた）: 中心から斜めに延びる細い楔の外接矩形は約 R² / 2 画素（R = 540 で約 15 万）になる。π / 16 以下の小片に切り、両辺と外接線と内側の弦の四角形で描く
  - polar の rect と bar を要素ごとに 1 回の呼び出しにする（cartesian の `DrawRect` と同じく重なりを 2 回塗る）: 隣り合う棒の境に筋が出て、131,072 個の rect で 39 万回の描画になる。層ごとに 1 つの形にする
  - 扇・輪などの形ごとの命令と、式で求める被覆: 部品が増え、縁の傾いた area と band の塗りを描けない
  - 扇の一部（ggplot2 の `coord_radial` の `end`・`thetalim`）: 要件にも行にもない


## 色のチャネル: カテゴリは系列に分け、連続の色は塗りの要素だけ、写像は matplotlib の表（行 G7c）

Decision:
  行 G7c は、列で色を分けるチャネル `ColorBy`・`FillBy` と、それが共有する色のスケール（ordinal・sequential・diverging）を作る。カテゴリの列は層をカテゴリごとの系列に分け（256 カテゴリまで）、Geom のふだんの道で描く。系列の行は、カテゴリが 1 つの区間に並べば写さずに区間で、混ざればワーカーが集めた列で引く。数の列は bar と rect の要素ごとの色だけで、131,072 要素まで。12 の連続の写像は matplotlib の 256 色の表と引き方にする。連続の色はカラーバーで示す（設計書 §4.1・§4.2・§4.6・§5.5、Issue #168、オーナーの決定 2026-10-31）。

Reason:
  カテゴリで分ければ、系列ごとに今の M4 と Geom の道がそのまま使え、1 フレームの仕事は系列の数 × 画素で抑えられる（要件 R-1）。長い形のデータはカテゴリの順に並ぶことが多く、そのときは足すメモリがない。matplotlib の表は知覚的に一様な写像の原典で、引き方まで同じにすれば、使い手が matplotlib と同じ色を得る。

Rejected:
  - 連続の列で線の色を変える（ggplot2 の線分ごとのグラデーション）: M4 は画素列ごとに点を選ぶので、線に沿った色の値が決まらない
  - rule・segment・errorbar の要素ごとの連続の色を G7c で作る: 線の記録は折れ線ごとに 1 回の描画で色も 1 つなので、要素ごとに折れ線を作ると 131,072 本で約 39 万回の描画になる。線分ごとの色は、点ごとの色と一緒に行 R3 で線のパイプラインに足す（Grill の後に見つけた事実で、オーナーが決めた）
  - いつも集めた列で分ける: 区間に並ぶデータでもメモリがデータと同じだけ増える
  - 区間に並ぶデータだけを受ける: 行ごとに混ざるデータ（センサーの読みを時刻の順に記録したもの）が描けない
  - ColorBrewer の写像を d3-scale-chromatic から取る: d3 は B スプラインで補間するので、matplotlib と値が違う。12 の写像の出どころを 1 つにした
  - 色で分けた bar と area を積み上げる（Vega-Lite と ggplot2 の既定）: 積み上げと並べは Position で、行 G5a で決める。G7c はカテゴリの順に重ねる（行 G5a で、既定を積み上げにした）
  - 独自 Geom で色のチャネルを使う: `IGeom` は自分で列を読み、系列に分ける口を持たない。使い手が出てから足す

## 軸の端のラベル: F を越えるときだけ内側へ寄せる（行 G3b）

Decision:
  下の軸と左の軸の目盛りのラベルは、目盛りの中心に置いた箱が図の矩形 F の端を越えるときだけ、越えない所まで内側へ寄せる。目盛りの線・グリッド・帯の幅は変えない。目盛りを選ぶときの重なりの値は、寄せた後の箱で測る（設計書 §4.6、Issue #176、オーナーの決定 2026-10-31）。

Reason:
  配置の順（帯 → パネル → 目盛り）をそのままにでき、端の目盛りのラベルも消えない。越えないラベルは動かないので、今のゴールデン画像は越えている場面（13）だけが変わる（どの場面もタイトルか凡例を持つ。タイトルのない左の軸の一番上と、凡例のない下の軸の最後のラベルは、ふだんから寄る。設計書 §4.6）。

Rejected:
  - はみ出す分を帯に取る: 帯の幅がパネルの幅を変え、パネルの幅が目盛りを変えるので、目盛りを 2 度選ぶことになる
  - はみ出すラベルを隠す（Vega の `labelBound`）: 端の目盛りの値が読めなくなる
  - 端のラベルをいつも軸の端にそろえる（Vega-Lite の `labelFlush` の既定）: 越えていない画像まで変わる
  - 描画先の端を限りにする（切れるラベルだけ動く）: 今の画像はほぼ変わらないが、ラベルだけが余白 P の中へはみ出す例外が残る。タイトル・凡例・帯はすべて F の中という配置の約束に、ラベルも合わせた（オーナーの決定、PR #177 のレビュー）

## text の Geom: カテゴリの列と数の列のラベル、プロットの総和 4,096、重なりは避けない（行 G8）

Decision:
  行 G8 は、行ごとにラベルを 1 つ置く text の Geom を作る。ラベルはカテゴリの列の名前か、数の列を書式で書いた文字列で、文字列の列の型は作らない。プロットの text の層の行の総和が 4,096 を超えたら `InvalidOperationException`。ラベルどうしの重なりは避けず、domain は基準点だけで学ぶ。整形のキャッシュの上限を 4,096 から 8,192 に上げる（Issue #184）

Reason:
  カテゴリの列なら文字列の種類がカテゴリの数で抑えられ、名前は列が持つので、描くたびに整形も確保もしない。数のラベルは列の版が変わったときだけ文字列にする。文字列はグリフごとに転送するので、上限は要素の数でなく転送の量（要件 R-1）で決まる。4,096 のラベルは 8 文字で約 1.6 MB である

Rejected:
  - 文字列の列の型を作る: 行ごとに違う文字列が無数にありうる列は、整形のキャッシュに収まらず、描くたびに整形して確保する（不変条件 3）。メモリマップの列にもならない
  - 上限を segment・rect と同じ 131,072 にする: 8 文字のラベルで 1 フレームに約 50 MB のグリフの記録を送り、要件 R-1 を破る
  - 見えるラベルだけを数える: 毎フレーム全行の走査になり、不変条件 2 を破る（segment・rect と同じ）
  - 重ならない位置を探して置き、置けないラベルを出さない（Vega の Label 変換、`packages/vega-label/src/Label.js`）: 行 G8 の範囲はラベルを置くことまでで、要件に重なりの回避はない
  - ラベルの箱を domain に入れる: domain が文字の画素の大きさに依り、パネルの大きさが domain を変え、配置を 2 度やり直すことになる
  - 上限を層ごとに数える: 転送の量も整形のキャッシュもフレームの総量で決まる。text の層が 3 つで 1 フレームの文字列が 8,192 を超え、描くたびに整形し直して確保する（PR #185 のレビュー、オーナーの決定）
  - 整形のキャッシュを 4,096 のままにする: 4,096 のラベルと軸・凡例・タイトルの文字列が 1 フレームに収まらず、描くたびに追い出した文字列を整形し直して確保する

## image の Geom: 列を包むラスタ、2 × 2 の平均の段、見えるタイルだけを予算の中で送る（行 G9）

Decision:
  行 G9 は、`Column<T>` を包む行優先のラスタ `Raster<T>`（数と RGBA）と、それを `Extent` の矩形に描く image の Geom を作る。ワーカーが 2 × 2 の平均のミップマップを 256 × 256 のタイルに作り、見えるタイルだけを常駐キャッシュ（行 G9 で作る）に 1 フレーム 4 MB まで送り、届いていない所は粗い段で仮に描く。色の写しは GPU で行う（Issue #196）

Reason:
  1 フレームの仕事と転送が、ラスタの大きさでなく見えるタイルの数で抑えられる（要件 R-1、不変条件 2）。列を包むので、メモリマップと写さない包みがそのまま使える

Rejected:
  - 2 次元専用のストレージを作る: 列の 3 つの置き方と `Invalidate` を作り直すことになる
  - matplotlib の `imshow` のように、毎フレーム CPU で画面の大きさへ再標本化する（`lib/matplotlib/image.py` の `_make_image`）: 1 フレームの仕事がラスタの見える要素の数になり、2 万 × 2 万では画素で抑えられない
  - ミップマップを 10 % に収める（段 1 を持たず元の段から読む）: 2 倍に縮めた表示で 4 倍のデータを送り、1 フレームの転送の予算を超える。要件 P-8 の例外にした（オーナーの決定）
  - 見えるタイルを一度に全部送る: 1,920 × 1,080 で最大約 44 MB になり、要件 R-1 の「数 MB」を超える
  - matplotlib と同じく、既定の extent で y を逆にして行 0 を上に出す: 層がスケールの向きを変える例外ができる。画像の向きを画面で決め、y のスケールは変えない（オーナーの決定、Issue #196）
  - Hanning の補間（matplotlib の既定の auto）: 縮小はミップマップの平均が受け持ち、拡大は nearest と bilinear で足りる
  - polar と、log・symlog・pow・`IScale` の位置の軸: 画像の矩形が平行四辺形に写らず、画素ごとの逆写像が要る
  - 利用者の `IScale` の色のスケール: シェーダで走らせられない
  - 常駐キャッシュを行 R3 まで待つ: ラスタのタイルが先に要る。行 R3 は生の点と密度タイルでそれを使う
  - 段を ⌈log₂ max(sx, sy)⌉ で選ぶ（どのテクセルも飛ばさない）: 1 : 1 に近いズームで段 1 になり、画面の解像度があるのに 2 × 2 の平均が 2 画素の塊で出る。⌊⌋ で細かい方の向きを最大 2 倍まで間引く（PR #197 のレビュー）

## Position: 層ごとの指定、色のカテゴリをグループに、分けた bar と area は既定で積む（行 G5a）

Decision:
  行 G5a は、層ごとの `LayerSpec.Position`（identity・stack・fill・dodge）を作る。グループは `ColorBy` か `FillBy` のカテゴリで、層の中だけで働く。分けた bar と area の既定は stack。カテゴリの x はワーカーがセルごとに正と負の和を作り、数の x はワーカーが系列の X を併合して累積の列を作る（area は ggplot2 の `stat_align` と同じ補間）。dodge の場所は全体で固定する（Issue #204）

Reason:
  §4.1 の表と要件 G-1 が Position を層の要素に数える。ggplot2 と Vega-Lite がどちらも色で分けた bar と area を積み、行を 1 本ずつ積む（段は行の和）。積んだ結果をワーカーが作れば、フレームの仕事は今の道と同じく画素とカテゴリの数で抑えられる

Rejected:
  - Vega-Lite の形（y のチャネルの `stack`、`xOffset` のチャネル）: チャネルが増え、§4.1 の表の「層の Position」と合わない
  - `Group` のチャネルを作る: 層を系列に分けるのは `ColorBy` と `FillBy` だけで、色と違うグループで積むと、同じ色の段が離れて凡例と合わない
  - 層をまたいで積む: ggplot2 の Position も層の中だけで、層ごとの計画が別の層の結果を待つことになる
  - セルの中で行の最大を積む（行 G7b の棒の延長）: ggplot2 と Vega-Lite の積み上げ（行の和）と違う意味になる
  - M4 の画素列の範囲を積む（ワーカーの併合なし）: 最大の和は和の最大でなく、積んだ形が正しくない
  - 欠けた x を 0 で埋める area（Vega-Lite の `impute`）: 時刻のずれた系列が櫛の形に積まれる。ggplot2 も 3.4 から補間（`stat_align`）を既定にした
  - x ごとにあるグループで等分する dodge（ggplot2 の既定の `preserve = "total"`）: x ごとにセルが空かを数える仕事が要り、同じ色の棒の位置が x ごとに変わる
  - 負の値を絶対値にして上へ積む fill（vega の normalize）: 負の値が正と区別できず、和が 0 の x で NaN を出す
  - 分けない bar も既定で積む（Vega-Lite）: 行 G7b のカテゴリごとの最大と最小の棒の意味が変わる
  - 数の x の errorbar と縦の rule を並べる: ずらす幅をデータの単位で決めるものがない（ggplot2 は `position_dodge(width = …)` で与えさせる）

## Stat: 層ごとの指定、ワーカーが作る派生の表、Vega の刻み、厳密な type 7（行 G5b）

Decision:
  行 G5b は、層ごとの `LayerSpec.Stat`（bin・count・summary）と `IStat` を作る。Stat の結果はワーカーが列の版ごとに作る派生の表で、層はその表の上で Geom のふだんの道と Position で描く。bin は Vega の刻み（最大 10 個、[a, b)、最後は [a, b]）、quantile は厳密な type 7 を radix select で求める（Issue #214）

Reason:
  §4.1 の表と要件 G-1 が Stat を層の要素に数え、G5a の Position と同じ置き方になる。派生の表は区切りかセルの数の大きさで、フレームの仕事が行の数によらない。区切りの端が軸の目盛りと同じきりのよい数になる。参照にした実装（numpy・R・d3・Vega）の quantile はどれも厳密な type 7 で、radix select はメモリを値の数でなくセルの数で抑える

Rejected:
  - Vega-Lite の形（x の `bin`、y の `aggregate`）: チャネルが増え、§4.1 の表の「層の Stat」と合わない
  - ggplot2 の既定の 30 個の区切り（`R/bin.R`）: 端が範囲から決まる半端な数で、ggplot2 自身も既定のまま使わないよう促す表示を出す
  - numpy と matplotlib の、範囲の端そのものの 10 個: 端が半端な数になり、軸の目盛りと合わない
  - (a, b] の区間（ggplot2 の `closed = "right"`）: numpy・matplotlib・Vega の [a, b) と逆になる
  - 数の x の count（ggplot2 の `stat_count` は値ごとに数える）: 1e9 行では値の種類に上限がない。区切って数えるのは bin
  - 近似の quantile（t-digest、KLL、Spark の Greenwald-Khanna、Vaex の格子）: 値が厳密でなく、参照にした実装の値と合わない
  - セルごとに値を集めて並べる quantile: メモリがデータと同じ桁になり、要件 P-8 の考え（索引は元の 10 % 以下）に合わない
  - ggplot2 の既定の `mean_se`: 標準偏差が要件 G-4 にない。`IStat` で書ける
  - bin の bar を棒の幅 1 つの bar の層で描く: log と time の x では区切りの幅がそろわない。矩形で描き、Position は Stat の中で当てる

## Stat: R の density() の手順の KDE、x の単位の窓の移動平均、rect の 2D の bin（行 G5c）

Decision:
  行 G5c は、density（KDE、1D）・smooth（移動平均）・bin（2D）を行 G5b の枠の上に作る。density は R の `density()` の手順（格子への線形の配りとガウスの核の畳み込み、既定の帯域幅は `bw.nrd0`）、smooth は x の単位の窓の中の y の平均を `Points` 個の点で、bin 2D は軸ごとの `BinStatSpec` のセルを rect で数で塗る（Issue #222）

Reason:
  1e9 行で、仕事が行の数に比例する 1 度なめ（帯域幅の自動は quantile の段を足す）で済み、派生の表は点かセルの数の大きさになる。density は ggplot2 の `stat_density` が呼ぶ R の `density()` と同じ値になり、R の出力を基準にできる。smooth の窓の端の間の区間に行を配る形は、x の並びによらず厳密

Rejected:
  - Vega の KDE（出力の点ごとに全行の核を足す厳密な和）: 1e9 行 × 200 点 = 2e11 回の `exp` で、要件 P-2 に届かない
  - Vega の Scott の帯域幅（1.06 倍）: ggplot2 と R の既定の `bw.nrd0`（0.9 倍）と値が違う
  - R の既定の `cut = 3`（範囲の外へ 3 h 延ばす）: ggplot2 はデータの範囲で評価する。範囲の幅が 0 のときだけ使う
  - 近似の IQR（格子のヒストグラムから読む）: `bw.nrd0` の値が R と合わない。帯域幅を数で与えれば、quantile のなめは飛ばせる
  - FFT の畳み込み: 格子は 4,096 点までで、直接の和で約 1.7e7 回の積和。FFT の実装を持たずに同じ値になる
  - 行の数の窓の移動平均（pandas の `rolling`、Vega の `window`）: 出力が行ごとの 1e9 行の派生の列になり、メモリが数 GB 増える
  - G9 の画像の層で 2D の bin を描く: log の軸や time の暦の段の不等幅の区切りに合わない
  - ggplot2 の 2D の bin の `density`（数 / 数の和）: 1D の密度（積分が 1）と形がそろわない
  - 2D の bin の層に新しい `X`・`Y` のチャネルか、専用の層の型を足す: 行 G5b の summary の errorbar と同じく、今のチャネル（`XMin`・`YMin`）に置く（オーナーが決定）

## 軸: 置き場所はスケールに、二次軸は独立したスケールと変換の軸の両方、グリッドは主だけ（行 G6a）

Decision:
  行 G6a は、軸の置き場所をスケールの `Side` に持ち、二次軸を、独立したスケール（`PlotSpec.ScaleX2`・`ScaleY2` と層の `SecondaryX`・`SecondaryY`）と、主の軸の変換の軸（`WithSecondaryAxis`）の 2 種類で作る。グリッドは主の軸の目盛りだけから引く。行 G6 は G6a（軸）・G6b（ファセット）・G6c（複数のプロット）に分ける（Issue #230）

Reason:
  単位の違う量を並べる用途（独立したスケール）と、単位の換算（変換の軸、ズームしても主に従う）は別の用途で、matplotlib は `twinx` と `secondary_yaxis` の両方を持つ。軸の設定をスケールに持つのは行 G3 の決定と同じ。行 G6 は要件 G-8 と G-9 にまたがり、1 つの PR では大きい

Rejected:
  - 独立したスケールだけ（Vega-Lite の `resolve`）: 単位の換算の軸が、ズームで主の軸と合わなくなる
  - 変換の軸だけ（ggplot2 の `sec_axis`）: 単位の違う量を 1 つの図に並べられない
  - 二次軸にもグリッドを引く: 2 組のグリッドが重なり、どちらの線か見分けにくい。ggplot2 の二次軸もグリッドを持たない
  - 軸の置き場所を `PlotSpec` の軸の仕様に持つ: 行 G3 で軸の設定をスケールに持つと決めた（軸とスケールが 1 対 1）
  - time のスケールの変換の軸: 日時の値を `double` の変換に渡す形がない。時差のある時刻の軸は、要る使い手が出たら足す

## ファセット: 行 G7c の分けた層の道、文字だけの見出し、ggplot2 の並べ方と軸（行 G6b）

Decision:
  行 G6b は、ファセット（wrap と grid）を、分ける列のカテゴリごとに行 G7c の分けた層の道で作る。軸の共有は `Fixed`・`FreeX`・`FreeY`・`Free`、並べ方は R の `n2mfrow`、行のないカテゴリは落とし、共有の軸は外側のパネルにだけ描く。見出しは文字だけ（Issue #238）

Reason:
  区間に並ぶデータは写さずに読め、パネルが行 G7c の系列と同じ形になる。並べ方と軸と落とし方は ggplot2 の既定と同じで、利用者の予想に合う。文字だけの見出しはテーマを増やさない

Rejected:
  - 値ごとの選択ベクトル（§4.5 の以前の文）: 1e9 行で 8 GB の位置の並びに加え、ピラミッドのために Y を集めることになる
  - ggplot2 の灰色の箱の見出し: テーマに見出しの色を足すことになる。Vega-Lite の header も文字だけ
  - 行のないカテゴリもパネルにする（ggplot2 の `drop = FALSE`）: 空のパネルが並ぶ。行 G7b の band は使われないカテゴリも出すが、ファセットではパネルの数が増えて読みにくい
  - 共有の軸をどのパネルにも描く: 同じ目盛りが並ぶ。ggplot2 の既定は外側だけ（`axes = "margins"`）

## ファセットの区間のパネル: 行の区間を Stat・積み上げ・色の分割に通し、区間の範囲を学ぶ（行 G6b、Issue #243）

Decision:
  区間に並ぶパネルでは、Stat・積み上げ・色の分割の計画も行の区間を受け取り、写さない。区間の系列は、列の全体の統計でなく区間の範囲を学ぶ。image と custom の層はどのパネルにも描く

Reason:
  1e9 行の Stat や積み上げをパネルに分けても、データと同じ桁のメモリを使わない。区間の範囲を学ばないと、free の domain がパネルでなく列の全体になる

Rejected:
  - Stat・積み上げ・色の分割の層だけパネルの行を集める: コードは小さいが、1e9 行の Stat で約 12 GB を集めることになる
  - free の向きがあるとき区間のパネルも集める: 同じくデータと同じ桁のメモリが要る
  - image と custom の層をファセットで拒む: ggplot2 は分ける列を持たない層をどのパネルにも描き、背景のラスタや注記の geom をパネルごとに出せなくなる

## 複数のプロットの図: 同じ大きさのセル、セルごとに独立した配置、入れ子なし（行 G6c）

Decision:
  行 G6c は、`FigureSpec` の concat と grid（またぎつき）で複数のプロットを並べる。セルは同じ大きさで、各プロットは自分のセルの中で 1 枚の図と同じ配置をし、スケール・凡例はプロットごとに独立。図の中に図は置かない。同じ列のピラミッドは図の中で共有する（Issue #254）

Reason:
  Vega-Lite の concat の既定（`align: "all"`、`bounds: "full"`、位置のスケールは独立）と同じで、1 枚の図の配置をそのまま使える。セルのまたぎで matplotlib の `GridSpec` の大きいプロットを作れる

Rejected:
  - パネルの端をセルの間でそろえる配置（ggplot2 の patchwork）: 各プロットの軸と凡例の帯を行と列で合わせる配置が要り、1 枚の図の配置を使えない
  - 行と列の大きさの比（matplotlib の `width_ratios`・`height_ratios`）: またぎで大きいプロットを作れるので、型と検査を増やさない
  - 色のスケールと凡例の共有（Vega-Lite の色の既定）: プロットごとに色の列と表が違い、共有の domain を学ぶ道が要る。同じ domain を与えれば同じ色になる
  - 入れ子の図（Vega-Lite の concat の入れ子）: 並べ方の木を配置する道が要る。grid のまたぎで同じ形を作れる

## 対話: `PlotEngine` と 4 つの層の拡張点（行 I1、Issue #266）

Decision:
  対話は新しい `PlotEngine` で行い、`HeadlessRenderer` は変えない。入力・割り当て（`InputBindings`）・ツール（`IPlotTool`）・ビューの操作の API の 4 つの層に分け、どの層も公開して差し替えられる。組み込みのツールも同じ API だけを使う。ビューは `PlotEngine` が持ち、仕様は変えない。慣性は自前で作らない。

Reason:
  対話の見た目と操作はアプリの UI/UX で決まる（オーナーの指摘）。OxyPlot は入力の形からコマンドへの表を、ScottPlot 5 は入力に応える部品の一覧をアプリに差し替えさせる。層を分けて公開すれば、アプリがツールバーやメニューを自前で作っても、組み込みと同じ規則（原点の付け直し、制約、履歴、通知）を通る。
  仕様は不変で、差分で描く（§4.8）。ビューを仕様の domain に書き戻すと、ズームのたびに新しい仕様のノードができ、「スケール」の段（学び直し）が走る。
  慣性はホスト（WPF のマニピュレーション、タッチパッドのドライバ）が持っていて、自前の慣性は二重になる。

Rejected:
  - `HeadlessRenderer` に入力とビューを足す: 1 回描いて読み出す道具と、状態を持って要るときだけ描く入口の契約が混ざる
  - 決まった操作だけを持ち、ツールの型を公開しない: アプリが操作を足すには、入力をホストの側で横取りするしかなく、組み込みの規則を通らない
  - ズームでスケールの domain を書き換える（Plotly の relayout の形）: 上の Reason のとおり、学習の段が毎フレーム走る
  - 自前の慣性スクロール: ホストの慣性と二重になり、時刻に依る動きがテストで追いにくい
  - OS のダブルクリックの判定（WPF の `ClickCount`）を使う: ホストごとに判定が変わり、記録した入力の再生で同じにならない

## WPF のホスト: エンジンの描画先を共有テクスチャへ写す、待たない読み出し、待たない暫定の表示（行 W1、Issue #282）

Decision:
  `PlotEngine` は自分の描画先に描き、`D3D11SharedSurface` が共有テクスチャ 2 枚へ写して、完了した方を D3DImage へ渡す。ソフトウェア描画とアダプタの不一致では、2 枚の staging から待たずに読み出す。`HyperPlotView` は仕様を `Spec` 1 つで受ける。暫定の表示は、暫定の間フレームを要求し続けて調べる。層のテクスチャでの合成は行 I2（今は I2b、Issue #337）で作る

Reason:
  Core の描画先の契約（`IGpuBackend`・`IRenderTarget`）を変えずに済み、Metal / wgpu のホスト（要件 N-6）に同じ形を求めない。写しは 1080p で 8 MB で、GPU の上の時間は行 W1a で測る。
  UI のスレッドは GPU とワーカーを待たない（不変条件 7）。暫定の間のフレームの仕事は画素で抑えられ（§5.5）、アニメーションと同じ道で済む。
  マウスを動かしただけのフレームを作るのは行 I2（今は I2b）のホバーとクロスヘアで、P-6 もそこで測る

Rejected:
  - 共有テクスチャに直接描く: 写しは要らないが、Core の描画先の契約に「共有」と「交互の 2 枚」が入り、ほかのバックエンドとホストにも同じ形が要る
  - 読み出しを待つ（不変条件 7 の例外に足す）: ソフトウェア描画の機械（リモートデスクトップなど）で、UI のスレッドが毎フレーム GPU を待つ。2 枚の staging なら 1 フレーム遅れるだけで待たない
  - `Plot` と `Figure` の 2 つの依存関係プロパティ: XAML で両方を置くと、どちらが勝つかが書く順で決まる
  - ワーカーから UI のスレッドへ終わりを知らせる（`SynchronizationContext` を捕まえる）: Core が UI のスレッドの仕組みを知ることになり、ホストごとの違いを持ち込む。暫定の間フレームを要求すれば、ホストの描画の時機で調べられる
  - 層のテクスチャでの合成を W1 で作る: W1 にはマウスを動かしただけのフレームを作るものがほとんどなく（矩形ズームの枠だけ）、P-6 を測れない

## 層を作る段の待たない形: 計画ごとのスレッドプールのタスク、層ごとの M4 の一括、上書きの集め直し（行 W1b2、Issue #297）

Decision:
  層を作る計算を、今の同期の形のまま、計画ごとに 1 つの .NET のスレッドプールのタスクで回す。作り終えた層は計画のスレッドで系列を登録し、層ごとの M4 の一括を取り替えて差し替える。列の版が変わった層だけを作り直し、新しい層ができるまで古い層を描く。分けた系列とファセットは同じ列に上書きで集め直し、途中の値を暫定として描く。作っている途中で計画を捨てても、タスクを待たない。

Reason:
  今の計算をほぼそのまま移せて、呼んだスレッドでの全走査もタスクに移る。層ごとの一括にすると、差し替えが 1 つの層の中で閉じ、ほかの層のワーカーの結果を捨てない。上書きの集め直しは、1e9 点で数 GB のメモリを増やさない。

Rejected:
  - 依存する仕事の連なりを、フレームごとに 1 歩ずつ進める: スレッドは増えないが、仕事の段の数だけフレームが要り（密度の帯域幅の選び出しは 8 回まで続く）、計算の書き直しが大きい
  - 層ごとにタスクを立てる: ファセットの 256 パネルで、ワーカーの仕事を待って止まるスレッドが数百になる。ワーカーの数は変わらず、計算は速くならない
  - 列の版が変わったら、今のとおり全部の層を作り直す: ほかの層のワーカーの結果を毎回捨て、決定 4（作り直しの間は前の版を描く）がほかの層で守れない
  - パネルの一括を空にして全部の層の系列を登録し直す: 系列を持つすべての層を、系列の番号を取り替えられる参照に書き換える必要がある
  - 計算が終わったらすぐ差し替え、ピラミッドができるまで暫定の M4 で描く: 数の x の積み上げのピラミッドが粗い間、前の版より粗い絵になる
  - 別の列に集め直して差し替える: 前の版をきれいに描けるが、集め直しの間 O(N) のメモリが増える
  - 集め直しの間は描かない: データを流し込むたびにちらつく
  - 計画を捨てるときにタスクを待つ: UI のスレッドが 1e9 点の Stat の計算（数秒）を待ち、不変条件 7 に反する

## ラスタのミップマップの待たない更新: つなげた Task、更新の間は送らない、解放を延ばす（行 W1b3、Issue #314）

Decision:
  段ごとの平均の仕事の Task に次の段をつなげて更新を進め、待つスレッドを作らない。更新の間は、段 0 を含めてそのミップマップのタイルを送らず、置いてあるタイルとその上の段で描く。世代は平均が成功してから記す。途中で捨てるときは待たず、段のメモリの解放を仕事の終わりまで延ばす（§3.7・§4.8・§5.5.3）。

Reason:
  段は 2 × 2 の平均を下から順に作るので、つなげた Task で順が守れ、止まるスレッドがない。段は同じメモリに上書きするので、更新の間に送らなければ、半分古いタイルが GPU に置かれない。メモリを増やさない。

Rejected:
  - 行 W1b2 の層を作るタスク（`MakingQueue`）に積む: そのスレッドが段ごとに待ち、大きなラスタの更新が同じ保管庫の層を作る仕事を待たせる
  - 書き終えた段だけ送ってよいことにする: 段ごとに送ってよいかを持つ形が要り、古い段と新しい段のタイルが画面に混ざる
  - 段 0 は送ってよいことにする: 段 0 は元の列なので `Invalidate` の時点で新しいが、新しい段 0 と古い段 1 が画面に混ざる
  - 別のメモリに作って差し替える: 2 万 × 2 万の `float` で約 530 MB のメモリが増える
  - `Dispose` が走っている帯（64 行）の仕事を待つ: 不変条件 7 の例外が増える。解放を延ばせば待たずに済む

## プロットの要約の知らせ方: 止まってから 1 回、暫定の印、カテゴリの名前（行 W1c、Issue #323）

Decision:
  `HyperPlotView` は、仕様の変化はすぐ、ビューの変化は最後の変化から 500 ms 止まってから 1 回だけ、`Name` の変化を知らせる。暫定のフレームの要約には「(provisional)」と書き、暫定でなくなったらもう一度知らせる。カテゴリの軸は見えるカテゴリの名前と数で書き、描かない層は「not drawn」と添えて残す（§7.1・§7.2）。

Reason:
  パンやアニメーションではビューが毎フレーム変わる。毎回知らせると、スクリーンリーダーが読み上げを始め直し続け、最後の範囲が読まれない。止まってからの 1 回なら、聞き手は動いた後の範囲を聞ける。

Rejected:
  - 毎フレーム知らせる: 読み上げが始め直し続ける
  - 暫定かどうかを書かない: 索引ができる前の範囲を、確かな値として読み上げる
  - カテゴリの軸を band の位置の数で書く: 聞き手に意味のない数になる
  - 描かない層を要約から外す: 仕様にある系列が、失敗したことを知らされずに消える

## ヒットテストの API: 呼び手のバッファ、x と y の欄、待たない答え（行 I2a、Issue #337）

Decision:
  `int PlotEngine.HitTest(Vector2 pixel, float radius, HitMode mode, Span<SeriesHit> results)` は呼び手のバッファに書く。`SeriesHit` は x と y の欄を持つ構造体で、不変条件 12 の例外とする。索引がまだない系列は、作ってある分で暫定の答えを返す（§6.3）。

Reason:
  ホバーはマウスを動かすたびに呼ぶので、確保しない形でないと不変条件 3 を守れない。x と y の欄なら、ツールチップが値をそのまま読める。

Rejected:
  - 配列を返す: ホバーのフレームごとに確保する
  - `SeriesHit` に行と画面の位置だけを持たせ、値は `PlotEngine.ReadHit` で読む: 例外なしで不変条件 12 を守れるが、呼び手はいつももう 1 回呼ぶ
  - 索引ができるまで、その系列は答えない: ピラミッドを作っている間、ホバーが何も示さない
  - 行 I2 を 1 つのまま作る: ヒットテストの索引の道と、層の合成と描画の道は、性質も計測（P-5 と P-6）も違う

## ホバーと層の合成: 残す層 1 枚と毎フレーム描く層、組み込みのホバーのツール（行 I2b、Issue #347）

Decision:
  背景・データ・ガイドを描画先と同じ大きさのテクスチャ 1 枚に残し、マウスだけのフレームはそれを写して、クロスヘア・印・ツールの枠・ツールチップだけを描く。ホバーは組み込みの `HoverTool` が `HitTest` を呼び、エンジンが最後のヒットを持つ（§5.4・§6.5）。

Reason:
  P-6 で効くのはデータを描き直さないことで、層を 4 枚に分けても、マウスだけのフレームで写す量は変わらない。ズームとパンでは全部の層が描き直しになるので、層の数を増やす得がない。

Rejected:
  - §5.4 の 4 層を別々のテクスチャにする: 写すテクスチャが増えるだけで、マウスだけのフレームの仕事は変わらない
  - パネルごとのテクスチャ: ファセットの 256 パネルでテクスチャが増え、ズームでは全部描き直す
  - ホバーをアプリに任せ、エンジンは `HitTest` だけを出す: 既定でホバーのないプロットになり、クロスヘアとツールチップを各アプリが作り直す

## 残した層を写してよいかの見分け方: 描いた元の比べ（行 I2b の実装、Issue #351）

Decision:
  残した層を写すのは、残したフレームと比べて、仕様のオブジェクト、倍率、各パネルのビュー、プロットが読む列の版の和、描画先の大きさ、デバイスの番号が同じで、残したフレームが暫定でないときである。毎フレーム、この比べで決める。

Reason:
  アプリは列を書き換えても、エンジンの口を呼ばない（列の版が動くだけ）。描き直す理由を知らせる旗では、列の書き換えとデバイスの作り直しを見落とし、古いデータや透明な層を写す。比べは列の数とパネルの数の分の足し算で、確保しない。

Rejected:
  - 描き直す理由のたびに旗を立てる（`SetPlot`・ビューの変化・`Resize`）: 列の書き換えとデバイスの作り直しは旗を立てる口がない
  - 層を毎フレーム残す（描くものがなくても写す）: 止まったプロットにも 2 枚目のテクスチャと写しを持たせる
  - 残す層に描いて描画先へ写す（今は描画先に描いてから残す層へ写す）: 写す回数は同じで、`HeadlessRenderer` の描き先を変える分だけ変更が広い

## 要素の層のヒットテスト: 系列と同じ最近傍、極値の行、矩形の総当たり（行 I2c、Issue #355）

Decision:
  数の x の棒とエラーバーの `X` は、系列と同じく x が最も近い行を返す。カテゴリの棒とエラーバーは、ワーカーの極値の仕事に行も持たせ、カーソルの側の端の行を返す。積み上げは派生の行（数の x は積み上げの表の行、カテゴリの x はセル）。矩形は、最後の記録で写した画素の矩形を全部調べる。

Reason:
  ホバーは棒の間の隙間でも値を読めるほうがよく、系列と同じ答え方なら同じ探索を使える。カテゴリの棒は全部の行の極値を描くので、描いた端の行を返せば、ツールチップがその行から値を読める。矩形は 131,072 要素までで、毎フレーム全部を画素へ写しているので、その画素を調べるのは 1 ms より十分に短い。

Rejected:
  - `X` は x の幅にカーソルが入る要素だけ（I2a の設計の出発点）: 棒の間の隙間でホバーが消え、マウスを動かすと点滅する
  - カテゴリの棒は行を返さない（行は −1）: ツールチップが値を表から読めず、ほかの層と形が違う
  - カテゴリの棒はカテゴリの最初の行を返す: 描いた端と違う行を指す
  - 矩形に格子の索引を作る: 要素の数に上限があり、作る仕事と記憶が、調べる仕事より大きい

## 選択: 述語で持ち、行の集合は区間かビット列、強調は範囲と線の一部（行 I3a、Issue #364）

Decision:
  選択はプロットごとに 1 つの述語（矩形・X の範囲・投げ縄・点）で持つ。行の集合は、X の範囲で x が並んだ系列は区間をその場で、矩形と投げ縄は要求されたときだけワーカーのビット列で返す。強調は、範囲を半透明で重ね、線の層は選んだ x の範囲の部分だけを太く描き直す。行 I3 は、選択の I3a とリンクの I3b に分ける。

Reason:
  時系列で最もよく使う X の範囲は、x の二分探索で区間が決まり、10 億点のビット列（125 MB）を作らずに済む。強調を範囲と線の一部にすると、データ層を記録し直さず、マウスだけのフレームの道（行 I2b）のまま描ける。選択とリンクはどちらも大きく、計測も別である。

Rejected:
  - 名前つきの選択を複数持つ（Vega-Lite の param）: リンクでも要らず、API と状態が増える
  - どの選択もビット列で返す: X の範囲でも 1e9 点で 125 MB を作る
  - 選んだ点だけ色を変えて線を描き直す: 1e9 点の線で、毎フレームの描く仕事が選択の大きさで増える
  - I3 を 1 つの行で作る: 選択とリンクの計測と契約が混ざる
  - `Selection` を x と y の範囲を持つ 1 つの型にし、不変条件 12 の 3 つめの例外にする（PR #365 のレビュー）: 型は簡単だが例外が増える。ビューの `PanelView` と同じく抽象と `Selection2D` に分ける（Issue #364 の決定 14）

## リンク: エンジンが持つグループで、値をそのまま写す（行 I3b、Issue #373）

Decision:
  リンクは `PlotEngine.Links` の `LinkGroup` で持ち、メンバーは `PanelId` かプロット全体である。ビューはスケールの空間の範囲をそのまま写し、種類の違う軸は飛ばす。制約は起点に返さず、リンクで動いたメンバーは履歴に積まない。カーソルはクロスヘアと印だけを広げ、選択は述語を広げて `Points` は広げない。

Reason:
  リンクは操作中の状態で、仕様の写像ではない（ビューと同じ）。値をそのまま写すと、時間の軸の原点と差の組が精度を落とさずに渡り、同じ値が同じ所に見える。制約を返さず履歴に積まなければ、広げる仕事は 1 回で終わり、履歴が二重にならない。

Rejected:
  - 仕様（`FigureSpec`）にリンクを書く: 仕様を変えずにリンクを足し外しできない。リンクは写像を変えない
  - 全体に対する割合で写す: 違う domain のパネルで、同じ値が違う所に見える。Plotly の `matches` も値を合わせる
  - 種類の違う軸は足すときに例外にする: 仕様は後から変わるので、足したときの検査は後で当たらなくなる
  - メンバーの制約が変えた値を起点に返す: 返した値がまた広がり、輪になりうる
  - リンクで動いたメンバーも履歴に積む: 同じ操作が各プロットに積まれ、戻るとリンクで二重に動く
  - メンバーのヒットも `Hover` で返す: ツールチップと `HoverChanged` がメンバーの数だけ増え、どのパネルの話かが分かりにくい
  - クリックの点（`Points`）も広げる: 行は表ごとの番号で、別の表では意味がない
  - `AddPlot` が足した時点のパネルを写し取る: ファセットの数が変わるたびに、アプリがリンクを組み直すことになる
  - 消えたパネルをグループから外して知らせる: 仕様を戻しても、リンクは戻らない

## 注釈: 仕様に持ち、軸ごとにデータかパネルの割合に固定する（行 I4a、Issue #382）

Decision:
  注釈は `PlotSpec.Annotations`（変わらない値の並び）に持ち、点の軸ごとに `Data`・`Data2`・`Panel` を選ぶ。ドラッグはエンジンが動かした値を持ち、離したときに知らせ、仕様に戻すかはアプリが決める。描くのはデータの層の後、残す層の中。行 I4 は注記と注釈の I4a と計測の I4b に分ける。

Reason:
  注釈は図の中身で、ヘッドレスの描画にもゴールデン画像にも出る。軸ごとの固定は、片方の軸だけをデータに付ける注釈（ある x の縦の線のラベルをパネルの上端に置く）を書ける。注釈を残す層に入れれば、マウスだけのフレームは注釈を描き直さない。

Rejected:
  - 注釈をエンジンに持つ（`PlotEngine.Annotations`）: ヘッドレスの描画に注釈が出ず、仕様だけで図が決まらない
  - 点ごとに 1 つの固定（x と y を同じ座標に）: 片方の軸だけをデータに付けられない
  - 画面の画素に固定する: 描画先の大きさが変わると、意味がずれる
  - 動いている注釈を毎フレーム描く層に描く: 記録の道が 2 つになる。全部を描き直しても P-1 の内に収まるかを §9 で測る
  - 矢印を持つ: 線とテキストで作れる
  - 端点や角をドラッグして大きさを変える: 要件 I-5 は「ドラッグで動かせる」だけである
  - I4 を 1 つの行で作る: 注釈と計測の契約と計測が混ざる

## 計測: その場で答え、平均は水準 3 のバケットの和で求める（行 I4b、Issue #390）

Decision:
  範囲の統計は UI のスレッドでその場で答える。min / max はピラミッド、和と件数はチャンクの統計と水準 3（4,096 要素）のバケットの和で求め、端は高々 2 × 4,096 個の元の値を読む。結果は選択と同じく抽象の `Measurement` と `Measurement2D` で表す。`MeasureTool` は既定の割り当てに入れない。

Reason:
  表示がドラッグの間もその場で決まり、ワーカーの完了を待つ表示が要らない。和を水準 3 だけに持てば、1e9 点で約 2 MB の追加で、端で読む元の値は 8,192 個に収まる。

Rejected:
  - 端のチャンクをワーカーで読み、`ValueTask` で返す: ツールは結果が届くまで待つ表示が要り、ドラッグの間に答えが遅れる
  - すべての水準のバケットに和を持つ: 水準 1（64 要素）の和だけで `float` の列の 3.125 %、全水準で約 3.6 % になり、ピラミッドの記憶が約 1.9 倍（約 4.1 % から約 7.7 %）になる。それで減るのは端で読む元の値（8,192 個から 128 個）だけで、8,192 個の読みは要件 P-5 の中に収まる見込みである（§9 で測る）。PR #391 のレビューで数字を直した
  - 計測の結果を x と y の 1 つの型にし、不変条件 12 の例外にする: 選択と同じく抽象と 2D の中身に分ければ、例外を増やさずに済む
  - `MeasureTool` を既定の割り当てに入れる: 左ドラッグ・Shift・Control は使われていて、空いた組がない
  - 散布や棒の統計を出す: 散布の索引は行 C3a・C3b・R3 で作る。棒はピラミッドを持たない層がある


## 裏の構築は CPU を譲る仕組みを持たない（行 S4、Issue #414・#422・#421）

Decision:
  ワーカーは通常の優先度のまま走り、CPU の配分は OS に任せる。機械の混み具合を見て休む仕組みも、優先度を下げる仕組みも持たない。本数は変えない。構築に使う CPU を抑えたい利用者は、本数の少ないプールを作って渡す（§8.1、`docs/adr/0003-no-yield.md`）。

Reason:
  何もしないプールで、全論理プロセッサを使う競合の横で 1e9 点の索引を構築すると（ワーカー 8 本、NativeAOT、2 回）、競合の速さは 79〜80 %、その 2 回の 16.7 ms を超えたフレームは 0、`GC.Collect()` は最大 45〜80 ms だった（`docs/benchmarks/s4-yield.md`）。
  譲る 2 つの方式は、実装して測ると、どちらもこれより大きな害があった。休む方式の害が、方式の性質か実装の誤りかは分かっていない。調べないと決めた（ADR 0003 の Decision 6）。

Rejected:
  - 混み具合を測って、裏の仕事の合間に休む（PR #423 の設計、ブランチ `feat/421-yield`）: 競合の速さは 100〜107 % に戻るが、休みの段の上限が 1 でも、1e9 点の構築が 786 秒と 1,179 秒になった（休まなければ 97 秒と 104 秒）。上限が 2 と 3 の回は、4 回のうち 3 回が 25 分で終わらなかった。ワーカー 8 本の延べ 6,285 秒のうち、走っていたのは約 310 秒、休みは 300 秒で、残りをどこで待ったかは分かっていない。休みの規則から計算すると、段が 1 の構築は約 200 秒のはずで、実測はその 4〜6 倍である。1e8 点でも 18.6 秒と 42.2 秒（休まなければ 8.4 秒と 10.1 秒）で、回ごとの差が大きい
  - 裏の単位の仕事の間だけ優先度を 1 段下げる（PR #418 の設計）: 競合の速さは 97 % 以上だが、`GC.Collect()` が 2.1〜2.2 秒かかった。GC は、低い優先度のスレッドが安全な点に着くまで待つ。UI のスレッドの確保が GC を起こせば UI が止まる。Linux では .NET の `Thread.Priority` が効かず、nice を別に呼ぶ必要もあった
  - ワーカーを常に低い優先度にする: 同じ GC の待ちに加えて、フレームの仕事を取ったワーカーとロックを持つワーカーを、フレームのスレッドが待つ
  - 既定のワーカーの本数を減らす: 空いた機械でも遅くなり、競合が全コアを使えば、少ない本数でも同じだけ取り合う
  - 休む仕組みを入れて、既定では使わない: 測った実装は構築が 8〜11 倍遅く、その理由が分かっていない。そのまま公開 API に残すことになる
  - 休む方式の試作で退けたもの（PR #423）: 休みを、仕事に実際にかかった時間から決める（競合に取られた分まで休む）。ワーカーの CPU 時間を、仕事を終えるたびに足す（長い仕事の間の CPU が「ほか」に数えられる）。Windows で `GetSystemTimes` と `GetThreadTimes` で読む（15.6 ms の刻みで進み、50 ms の間の機械全体の時間が 469〜1,031 ms と読めた。正しくは 800 ms）

## 散布の生の点: 層の行の数で 2 つの道、常駐の点は internal の命令で描く（行 R3a、Issue #431）

Decision:
  point の層は、行の数（分ける前）が 131,072 以下なら毎フレーム CPU で写し、それより多ければ、分けた部分ごとに索引を作り、Morton 順の写しを GPU に常駐させて頂点シェーダで写す。
  常駐の点には、四分木のセル（32,768 点以下の最大のセル）の中の位置を 32 ビットの整数で送り、頂点シェーダが、画面の中の基準との差を整数のまま引いてから画素にする。索引の道は、点を CPU で写さない。
  索引の道の層の部分は 64 までに限る。
  常駐の点を描く命令と変換は internal にとどめ、公開の `SetTransform` と 4×4 の変換の型は、行 K1 で作る。
  行 R3 は 6 行（R3a・R3f・R3b・R3c・R3d・R3e）に分け、行 R3a の間は 1e7 行を超える層を例外にする。

Reason:
  小さい散布は、索引の構築を待たずに最初のフレームから描け、ファセット・色の分け・flip・polar がほかの Geom と同じ形で通る。
  試作で、1e7 点の常駐の点の GPU 時間は、フレームの間を空けた実行で 10.4〜11.4 ms（最大 12.6 ms）、索引の構築は 0.15〜0.89 秒だった（参照機、§5.5.2）。要件 P-4 の 60 fps に届く見込みがある。
  整数の差は、画面の中の点どうしでは小さいので、どれだけ拡大しても、x と y の拡大の度合いが違っても正確である。誤りが 0.5 画素を超えるのは、セルの広がりが 2^31 画素（画面の約 110 万倍）を超えたときだけである。
  索引は点の数によらず約 0.7 MB を持つので、部分の数に上限が要る。64 で約 45 MB である。
  常駐のデータを指す命令は公開できないので、公開の `SetTransform` を使う公開の命令がない。使い手のない公開の型を先に決めると、3D（行 K1）で形が合わなくなったときに直せない。

Rejected:
  - 点の数によらず索引を作る: 100 点の散布でもワーカーの構築を待つ
  - 道を、分けた後の部分ごとに選ぶ（最初の設計、Issue #431 の決定 4）: 1e7 行を 256 のカテゴリに分けると、どの部分も 131,072 点以下で CPU の道になり、毎フレーム 1e7 点を写して 320 MB を記録する（PR #432 のレビュー）
  - 差の原点を、写しの 65,536 点の並びごとに取り、画面にかかる葉の点が 131,072 以下になったら全部を CPU で写す（最初の設計、決定 10 の最初の形）: 並びは塊の縁で遠くの外れ値と塊の点を一緒に持つ。範囲の 1 万分の 1 の幅の塊を画面いっぱいに拡大すると、その並びの数万点が 1 画素以上ずれる（PR #432 のレビュー）
  - 差の原点をセルの角に取る `float32` の差と、広がりが 2^23 画素を超えるセルを CPU で写す形（2 つ目の設計、決定 26）: x だけを深く拡大すると、縦に並んだセルがどれも広くなり、CPU で読む点が抑えられない。一様な 1e7 点で x だけ 14 万倍に拡大すると約 156,000 点で、縦の線に点が並ぶデータでは数百万点になる（PR #432 のレビュー）
  - 軸ごとに `float32` を 2 つずつ持つ（大きい差と残り）: 不変条件 6 は文どおり残るが、1 点 20 バイトで、1e7 点が 200 MB になる
  - 索引の道の部分の数に上限を置かない: 256 の部分で約 179 MB、6 パネル × 256 カテゴリで約 1 GB を、点の数によらず使う
  - 索引の保管庫（`SpatialIndexStore`、ピラミッドの保管庫と同じ形）を作る（設計の最初の形）: 部分の計画が自分の索引を持てば足りる。見た目だけの変更では計画が使い回され、索引は作り直されない。保管庫が効くのは、同じ列を 2 つの層か 2 つのプロットが描くときだけである（行 R3a の実装、Issue #438）
  - ページを、決まった大きさの枠（64 枠のバッファ）に置く（設計の最初の形）: 点の少ない部分のページも 1 枠（786,432 B）を使う。ページごとのバッファなら、予算を中身のバイトで数えられる（行 R3a の実装、Issue #438）
  - ページの点を写しの順（Morton 順）のまま置き、見える最初の点から最後の点までを描く（実装の最初の形）: 続けて描く印が同じ画素に重なり、1e7 点・直径 6 DIP の GPU 時間が 15.6〜16.8 ms になる。ページの中を並べ替えると 11.6〜12.5 ms（行 R3a の実装、Issue #438）
  - ページをまたいで点を散らす: 4 ページをまとめて 18.3 ms、全部で 20.9 ms と遅くなり、拡大した表示でも全部のページが要る
  - チャンクごとの写しを GPU に置く第 3 の道（§4.4 の前の文）: 131,072 行を超える層は索引で足り、道と試験が増えるだけである
  - 索引の 2^32 × 2^32 の格子の整数を GPU に送る: 範囲の全体を 2^32 に分けるので、範囲の 220 万分の 1 より深い拡大で点が格子に寄る。セルごとに 2^32 に分ければ、一様な 1e7 点でその 32 倍深くまで持つ
  - 行 R3a で `SetTransform` と 4×4 の型を公開する（Issue #136 の決定）: 公開の `DrawMarkers` がスケールの空間の点も取る必要が出て、公開の面が広がる
  - 索引ができるまで、列の先頭の 131,072 点を代わりに描く: 列の先頭は全体の分布を表さないことがある。1e7 点の索引は 1 秒未満でできる
  - 大きさと形のチャネルを行 R3a に入れる: スケール 2 種と凡例 2 種が要り、描画の仕事と重なって行が大きくなる（行 R3f）
  - 索引の道でエンコードの列を並べ直して、点ごとの色を行 R3a で描く: 新しい派生データが要る（行 R3d）。カテゴリの色は、部分に分ければ索引の道でも描ける
  - 1e7 行を超える層を受け付けて、画面内が 1e7 点を超える間は何も描かない: 全体表示が空になる状態を main に入れることになる
  - P-4 を「CPU 時間と GPU 時間がそれぞれ 8 ms 以下」で判定する（P-1 と同じ形）: 試作の GPU 時間は 10.4〜12.6 ms で届かない。和が 16.7 ms 以下で判定する（オーナーの決定）

## 点の大きさと形のチャネル: プロットに 1 つのスケール、形は 6 つ、索引の道は形だけ（行 R3f、Issue #448）

Decision:
  point の層の `SizeBy`（数の列）は点ごとの直径を、`ShapeBy`（カテゴリの列）は点ごとの形を、プロットに 1 つずつのスケール（`ScaleSize`・`ScaleShape`）で決める。
  大きさは面積が値に線形で、直径の範囲の既定は 2〜16 DIP、domain の既定はデータの最小〜最大である。
  形は、三角形・ひし形・斜めの十字を足して 6 つにし、7 つ以上のカテゴリの `ShapeBy` は例外にする。
  CPU の道は、点ごとの大きさと形を記録に入れる。索引の道は、`ShapeBy` で層を部分に分け、`SizeBy` は例外にする（行 R3d）。
  同じ列を指す色と形は 1 つの凡例にまとめる。注釈のマーカーは `DrawMarkers` で描く。

Reason:
  `DrawMarkers` の記録は、行 R3a から直径と形を点ごとに持つので、CPU の道は記録の形を変えずに済む。
  常駐の点（12 バイト）は大きさと形を持たない。形はカテゴリなので、色と同じく部分に分ければ索引の道で描ける。大きさは点ごとの値なので、エンコードの列を並べ直す行 R3d の仕組みが要る。
  面積に比例する写像は、値が 2 倍の点が 2 倍の大きさに見える。ggplot2 の `scale_size` と Vega-Lite の `size` が同じ形である。
  形で見分けられるカテゴリは少ない。ggplot2 は 6 を上限にして、それより多いと警告する。
  色のスケールがプロットに 1 つなので、大きさと形も同じ場所に置けば、同じ列を指す層が 1 つの写像と 1 つの凡例を共有する。

Rejected:
  - 索引の道でも `SizeBy` を描く（常駐の点を 16 バイトにして直径を足す）: 1e7 点で 40 MB 増え、行 R3a の P-4 の計測をやり直すことになる。点ごとの値を索引の道へ運ぶ仕組みは行 R3d で作る
  - `SizeBy` と `ShapeBy` をどちらも CPU の道だけにする: 形で分けた 131,072 行を超える散布が描けない
  - 値を直径に線形に写す（ggplot2 の `scale_radius`）: 値が 2 倍で面積が 4 倍になり、大きい値が強く見える
  - 面積と直径の 2 つのスケールを持つ: 口と試験が 2 つ分になる。直径に線形の写像は、要るようになったら足せる
  - 大きさの domain の既定を 0〜最大にする（Vega-Lite の既定、ggplot2 の `scale_size_area`）: 値が 100〜110 のようなデータで、どの点もほぼ同じ大きさになる。`WithDomain` で 0 から始められる
  - 形を 8 つにする（下向きの三角形と星を足す）: 小さい印で、三角形の向きと星が見分けにくい
  - 3 つめの形をプラス（+）にする（Grill の最初の案）: 今の `MarkerShape.Cross` が縦と横の線の + だった。斜めの十字（×）を足す
  - 形を足さない: `ShapeBy` が 3 カテゴリまでになる
  - 7 つ以上のカテゴリで形を使い回す: 違うカテゴリが同じ形になり、凡例で見分けられない
  - スケールを層ごとに持つ: 凡例が層ごとに分かれ、色のスケールと形がそろわない
  - カテゴリの列の `SizeBy` を、カテゴリの順に等分した大きさで許す: 順序のないカテゴリに大小の意味を付ける
  - 色と形の凡例を、同じ列でも別々に出す: 同じカテゴリの行が 2 回並ぶ
  - 索引の道で、`ColorBy` と `ShapeBy` が別の列なら例外にする: 大きな散布で、色と形を別の意味に使えない。組で分ける鍵は、ファセットの grid のものがある
  - 新しい形を点の層だけに限る: 注釈の検査に、新しい形を断る分岐と試験が要る。`MarkerShape` は点の層と注釈が共有する
  - 注釈の今の描き方（扇形・矩形・折れ線）に 3 つの形を足す: 形の描き方が 2 か所になり、三角形とひし形の塗りの命令が要る

## 散布の密度: 画面内の点の数の上限で切り替え、層の色の濃淡で描く（行 R3b1、Issue #462）

Decision:
  索引の道の point の層は、画面内の点の数の上限（`Inside + Touching`）がしきい値（既定 1e7）を超えたら密度タイルで、0.8 倍を下回ったら生の点で描く。利用者は層ごとに `Auto`・`Points`・`Density` を選べる。
  密度は、ビンの幅が 1 物理画素以上の最も深い水準のタイルを最近傍で描き、ビンの数を log（既定）・線形・立方根で、層の色の濃淡か選んだ写像の色にする。濃さの上端は、描くタイルの最大のビンの数である。
  行 R3b を、密度と切り替え（R3b1）と、重なり・予算・1e9 点の読み出し（R3b2）に分けた。

Reason:
  上限で比べれば、生の点が 1e7 を超えて描かれない（要件 P-3・P-4）。数える仕事は画面の周の画素の数に比例し、点の数によらない。
  層の色の濃淡なら、生の点と密度が入れ替わっても見た目がつながり、複数の層とカテゴリの部分を重ねられる。
  ビンを画素より細かくしなければ、数を取りこぼさず、足し合わせの段が要らない。タイルごとの最大を作るときに持てば、濃さの上端を毎フレームのビンの走査なしに決められる。

Rejected:
  - 行 R3b を 1 つのまま、または 3 つに分ける: 1 つでは論点が多すぎて設計の Grill と PR が長くなる。3 つでは、色の写像と描画を分けても、どちらも単独では要件を満たさない
  - 下限（`Inside`）で切り替える: 1e7 を少し超える点を生で描く画面がありうる
  - 上限と下限の真ん中で切り替える: どちらの約束もできない
  - 重なりを限界として書くだけにする、`RawThreshold` を下げる: 前者は重なる画面が 60 fps に届かないまま、後者は重ならない画面も早く密度になり、要件 P-3 の「生の点を描くのは画面内が 1e7 点以下のとき」と合わない
  - eq_hist（datashader の既定）を入れる: 見えるビン（1,920 × 1,080 で約 200 万個）のヒストグラムを毎フレーム作る仕事が要る
  - いつも viridis などの写像で描く、プロットの `ScaleColor` に従う: 前者は切り替えで色が大きく変わり、層を重ねると読めない。後者は `ColorBy` を持つ層と衝突する
  - ビンが画素より細かい水準を選び、画素ごとに足す: 読むビンが 4 倍になり、足し合わせの段が要る
  - 線形補間で写す: ビンの数がない所にも薄い色が出る
  - 見えるビンの最大を毎フレーム数える: 毎フレーム画面分のビンを読む。全体表示の最大で固定する: 拡大すると画面が薄くなる
  - 列挙だけでしきい値を固定する、プロットで 1 つにする: しきい値を層ごとに変えられない。層ごとに描き方を変えられない
  - カテゴリで分けた層を行 R3d まで密度にしない、部分を足して 1 つの密度にする: 前者は分けた大きな散布で要件 R-3 を満たせない。後者は色で分けた意味が消える
  - 入れ替わりを抑えない、時間で遅らせる: 前者は境でパンすると入れ替わり続ける。後者はその間に 1e7 を超える生の点を描く
  - 索引ができるまで何も描かない: 1e9 点では数十秒、何も見えない
  - `Points` の層が予算を超えたら密度に戻す、例外にする: 前者は利用者の指定と違う描き方になる。後者は大きな層を拡大して生の点を見る使い方ができない
  - 密度の層に数のカラーバーを出す: ビンの数は拡大で変わるので、数の目盛りに意味がない
  - 密度に専用の命令 `DrawDensityTiles`（記録・シェーダ・パイプライン）を作る（設計 PR #463 の最初の形）: ラスタの画像の命令が、`float32` のタイル・最近傍・変換・色の表・祖先の引き当て・不透明度をすでに持つ。画像に「0 を透明にする」印を足せば足りる（オーナーの決定、2026-11-13）
  - 数を「選んだ水準のビン 1 つあたり」（c / 4^k）にそろえる（設計 PR #463 の形）: 分けた層の部分は自分の範囲から水準を選ぶので、ビンの広さが部分ごとに違い、同じ密さが違う色になる。1 物理画素の面積あたりにした（Issue #464 の決定 9）
  - 水準を層で 1 つにする: 部分の範囲の比が 2 のべきでないと、ビンの広さはやはりそろわない
  - 密度でもクランプする軸の外の点を端の列に寄せる: 端の 1 列に外の全部が集まり、濃さの上端を支配する。クランプの層を密度にしない: 1e7 を超える点を生で描くことになる（Issue #464 の決定 10）
